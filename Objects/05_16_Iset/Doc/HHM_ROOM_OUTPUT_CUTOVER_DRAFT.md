# Исеть — исполнительное управление комнатным отоплением / K1–K11 + K4

**Issue #204; статус: ОФЛАЙН РЕАЛИЗАЦИЯ, ПНР И ПЕРЕКЛЮЧЕНИЕ НЕ РАЗРЕШЕНЫ.**
Дата: 18.10.2026. Это техническая спецификация нового **владельца**
комнатных приводов/насоса; она не является разрешением установки на WB.

## As-built из live-бэкапа HM2

Источник: копия действующего `23_heating_living_manager.js` от
18.10.2026 и `HeatingConfig.js`; фактическая карта в
`Objects/05_16_Iset/HHM/room_zones.js`. Текущий writer — HM2.
- NO-приводы `wb-mio-gpio_195:2/K1..K11`: `false/0=открыть`,
  `true/1=закрыть`, 8 комнат и 11 исполнительных каналов.
- Насос жилого контура: **`wb-mr6cu_37/K4`**, команда `true=ON`.
  Нельзя путать с K4 зоны коридора (`wb-mio-gpio_195:2/K4`).
- В действующем HM2 `CFG.ttl.actuatorOpen=180` секунд. Проверка
  контакта/реле не доказывает фактическое открытие штока или проток.
- HM2 на текущем объекте остаётся **единственным физическим writer**.
  Старый HA heartbeat нельзя переносить как отключающий всю жилую зону.

## Реализованный код в Draft PR #206

- `Objects/05_16_Iset/HHM/room_output_planner.js` — чистый ES5
  расчёт **упорядоченного плана** физического управления.
- `Objects/05_16_Iset/HHM/room_output_executor.js` — единый
  **инжектируемый** writer с точным allowlist (11 NO + K4):
  `SHADOW` ничего не пишет; `PHYSICAL` разрешается только при
  `commissioned=true` в объектной карте и runtime, плюс внешне
  подтверждённый `exclusiveOwnershipConfirmed=true`.
  Физический WB `dev[path]=value` адаптер не включён в live.
- `Objects/05_16_Iset/Wirenboard/wb-rules/28_hhm_rooms_shadow.js` —
  кандидат теневой визуализации: показывает запросы комнат,
  **предполагаемые** команды NO/K4, состояние готовности,
  а не фактические физические команды нового алгоритма.
  Читает состояния K1–K11/K4; пишет только собственные виртуальные
  диагностические каналы.
- Existing `room_local_runtime.js`: независимые 8 комнат, уставки WB,
  обычный гистерезис, `meta/error` отдельного WB-MSW. Нет
  избыточного контроля свежести/heartbeat датчиков.

## Команды и порядок

1. `heatDemand=true` комнаты → **OPEN** всех её NO-приводов
   (`false/0`). Остальные комнаты не становятся аварийными.
2. После наблюдения значения OPEN на **каждом** выходе требуемой
   комнаты и выдержки 180 с → возможно `K4=ON`. Это не доказательство
   расхода и **не заменяет** независимые защиты и локальный
   `HHM`-grant/гидравлическую проверку.
3. При переключении комнат сначала OPEN новой; пока новый путь
   не выдержал задержку, не CLOSE последний прежний открытый путь
   при работающем насосе.
4. Когда **все** комнаты явно `heatDemand=false`, сначала
   `K4=OFF`; закрытие последней NO-зоны только после наблюдения
   отключённого насоса.
5. `heatDemand=null` одной комнаты → **HOLD** её приводов;
   не превращать null в OFF и не отключать K4, пока остаётся запрос
   тепла других комнат. Явная ошибка её WB-MSW даёт `false`
   только для этой комнаты, согласно принятой простой политике.
6. Независимая настоящая защита оборудования передаёт
   `protectionActive=true`: writer предлагает `K4=OFF` и
   не открывает/закрывает зоны. Это **не** ошибка комнатного датчика.
7. При перезапуске объекта/смене boot epoch открытие приводов
   квалифицируется заново. Все команды являются попытками записи,
   не утверждением физического результата.

## Что реализовано, а что НЕ реализовано

**Действительно реализовано и протестировано:**
- команды NO/K4 из конкретной карты Исети;
- порядок отключения насоса/закрытия последнего пути;
- изоляция комнат и отсутствие глобального HA heartbeat;
- разрешённый/запрещённый режимы физического writer;
- теневое моделирование на копии WB API.

**Не реализовано / отдельная натурная приёмка:**
- действительно работающий live `wb-rules` исполнительный entrypoint
  и объектная привязка `HHM` к независимому interlock / арбитру;
  нельзя подменить этот вход литералом `false` при physical режиме;
- verified single-writer handover от `23_heating_living_manager.js`,
  полная карта других файлов-владельцев, rollback и NST adoption;
- утверждённые восемь уставок/гистерезисов, durably сохранённые на WB;
- работа насосного выбега, теплоисточника, ГВС, OT и независимых защит
  всей Исети — **это более широкий переход HM2→HHM по Issue #204**;
- физический контроль движения приводов/протока не заявляется,
  таймер на 180 секунд берётся из as-built.

**Активировать `room_zones.commissioned=true` сейчас запрещено.**
Создание кода PHYSICAL writer ≠ перенос физического владения.
Текущий контроллер сохраняет HM2 без изменений.

## Offline regression

```sh
node Systems/HHM/tests/iset-room-output-owner.js
node Systems/HHM/tests/iset-wb-shadow-bridge.js
```

Тесты проверяют stop-before-close, old-path handover,
readback/open wait, pump start, one failed room vs another healthy,
map whitelist, отсутствие разрешения в SHADOW и без commissioning,
отсутствие второго writer, диагностические каналы WB shadow.
Любой фактический live переход потребует отдельно согласованных
NST gate, протокола испытаний и точки отката.
