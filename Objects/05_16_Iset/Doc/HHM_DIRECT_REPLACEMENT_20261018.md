# Исеть — прямая замена HM2 на автономный HHM, затем NST

**Решение пользователя от 18.10.2026:** не разрабатывать параллельный
запуск двух систем, специальный live handover, старые HA heartbeat
как разрешение отопления и сложную аттестацию WB-MSW. Есть
**плановая короткая остановка**, затем однократная замена HM2 на HHM.
Ввод NST — **после подготовки HHM**, Home Assistant — **после запуска
работающего автономного отопления**.

## Последовательность на объекте — когда комплект HHM завершён

1. Сделать внешнюю копию файлов /etc/wb-rules,
   /etc/wb-rules-modules, конфигураций датчиков/виртуальных устройств;
   сохранить список включённых правил, значения комнатных уставок,
   контрольные суммы и способ вернуть исходный HM2.
2. Остановить отопление на заранее выбранное короткое окно.
   Выключить старые активные HM2 20–27; не запускать одновременно
   новый и старый физические writers.
3. Установить одним подготовленным комплектом новые объектные
   WB-модули, правила, локальные уставки и виртуальные панели HHM.
   Отложенную настройку HA не делать условием старта.
4. Старые файлы HM2 удалять только после создания внешнего
   работоспособного архива и проверки установленного нового набора.
   Отдельные правила освещения, вентиляции, рециркуляции, сервиса,
   а также неразобранные наблюдатели НЕ удалять скопом.
5. Перед NST подготовить перечень всех файлов **не-HHM** и их хэши:
   ../HHM/nst_preserve_inventory.json — инвентаризация 13 файлов
   по **копии от 18.10.2026**, не официальный allowlist NST.
   Текущие live SHA перед регистрацией проверить ещё раз.
6. Установить NST, принять именно согласованный набор файлов.
   Не разрешать NST cleanup удалять неизвестные правила.
   Проверить статус и архив диагностики на **фактически установленном**
   контроллере. Заявление «NST поддерживает Исеть» требует изменения
   его текущего плагина: сейчас HHM allowlist ограничен Иволгой.
7. Запустить единственный HHM и проверить реальную циркуляцию,
   источник, ГВС, радиаторы и подмес ТП. Физические таймеры/пороги,
   защитные реакции и теплоотдачу фиксировать на объекте,
   а не только по виртуальным readback.
8. Дальше изменения кода — через reviewed HHM release/NST.
   Home Assistant/Sprut-интерфейсы подключить отдельно, уже при
   штатно работающем автономном WB.

**Не надо сложного live cutover.** Но новый HHM нельзя запускать
без работающего управления источником/котлом/ГВС/радиаторами/ТП,
причём без дублирующих авторов физических команд.

## Реально разработано в Draft PR #206

| Подсистема | Есть исходники / офлайн-тесты | Готово на WB |
|---|---|---|
| 8 комнат WB-MSW / K1–K11 | Простые термостаты, PersistentStorage binding, NO planner и виртуальные 120-с таймеры | Нет |
| Насос жилых радиаторов K4 | Упорядоченный старт после 120 с, диагностика | Нет |
| Цоколь K3 | Локальные 4 термометра, простой спрос с удержанием тепла при краткой потере измерений | Нет |
| ГВС K1 | Автономный запрос, условный приоритет, лимит времени, выбег, расчёт K1 | Нет |
| Источник OpenTherm 11 | Автономная уставка с диапазоном/скоростью и подтверждением команды | Нет |
| ТП K2, K12–K16, MAO4 131 | Гидравлический предпуск: NO 120 с, MAO4 1%, 40/45 °C. Адаптер общего `HHM3Mixing` с объектными параметрами Исети уже протестирован офлайн | **Нет: нет единого физического WB writer и натурной проверки шагового смесителя** |
| ПВУ K6 | Отдельный физический владелец сохранён, ПВУ в HM2 не введена | Не переносить слепо |
| Общий WB writer / правила / таймеры всех насосов | Отдельные чистые модели и теневая панель K4 | **Нет: не сформирован installable production package** |
| NST | Инвентаризация файлов и текущего ограничения NST | **Нет: не произведена object registration, archiving acceptance, install** |

Состояние `commissioned=false`, нет утверждённых восьми локальных
комнатных уставок. Не выдавать пакет PR #206 за готовый replacement.

## Откуда взяты параметры

- Фактический HM2 `HeatingConfig.js` из копии WB 18.10.2026:
  источник OT 11; K1 ГВС, K2 ТП, K3 цоколь, K4 жилой,
  K6 ПВУ, MAO4 131, WB-M1W2 65–67.
- ГВС: `target=52, hysteresis=3, trigger=45, timeout=7200,
  relief=900, overrun=180, policy=CONDITIONAL` — существующие
  as-built параметры, а не перенос Иволги.
- ТП: 40°C превентивное закрытие горячего порта, 45°C отдельный
  stop K2 **как ныне действующие границы** (Issue #194).
  Не считать алгоритм/гидравлику ТП прошедшими ПНР.
- NO жилых комнат K1–K11 и ТП K12–K16: для HHM новая
  согласованная выдержка 120 секунд вместо старых 180 секунд HM2.
- Работающий legacy HA mode ТП не годится для автономного HHM:
  режим и целевая подача должны определяться локально на WB.
- В `Systems/NST/nst/plugins.py` HHM policy пока жёстко
  принимает только `05_31_Ivolga_13`; `files` plugin допускает
  лишь собственные component namespaces. Инвентаризация сама по
  себе НЕ включает поддержку Исети в NST.

Этот документ — **короткая процедура замены и текущая фактическая
готовность**, а не отдельная система блокировок.

## Код автономных служб в PR #206 (18.10.2026)

Подготовленные объектные модули чистой логики:

- `isethhm_service_config.js` — фактические пути WB-M1W2 65–67, OT11,
  K1–K4/K6, MAO4 131, K12–K16, as-built ГВС/источника.
- `isethhm_dhw.js` — ГВС 52°C, гистерезис 3°C, условный приоритет,
  ограничение приоритета по наружной температуре, таймеры K1, выбег.
- `isethhm_demand.js` — локальный спрос цоколя (4 датчика) и комнат,
  арбитраж ГВС/отопления; при краткой потере ВСЕХ комнатных датчиков
  цоколя удерживается последняя подтверждённая температура/потребность.
- `isethhm_source.js` — расчет уставки OT 11, плавный рост/снижение
  по параметрам Исети, без Home Assistant. Фактическая запись и
  подтверждение разделены.
- `isethhm_coordinator.js` — единый автономный расчёт решений: жилые
  зоны, цоколь, ГВС и источник, без физических команд.
- `isethhm_floor_hydraulics.js` — K12–K16, K2, MAO4-1% предпуск,
  открытие NO 120 с, защита 40/45 °C; пока это расчет намерений.
- `isethhm_floor_mixing.js` — объектный адаптер проверенного общего
  `Systems/HHM/core/HHM3Mixing.js`, настройки из реального HM2 Исети.
  У него **инжектируемый** физический IO, но живой writer и ПНР ещё
  не выполнены; факт `IO accepted` ≠ механический результат клапана.

Следующая собственно программная задача: один WB entrypoint,
соединяющий эти модели и физические выходы K1–K4, K12–K16,
MAO4/OT11 (без дублирующих writers), плюс локальный интерфейс
уставок и таймеров для каждого насоса. Сейчас **не существует
утверждённой и готовой к установке production-сборки** HHM Исети.
