## Пользовательская карточка

Один Accessory «Подпитка отопления», комната «Котельная». Основная плитка — «Автоподпитка». Остальные значения открываются внутри карточки, как у котла Иволги; наличие цифры давления прямо на плитке beta пока не подтверждено.

| Элемент | WB control | Доступ |
|---|---|---|
| Давление отопления, Бар | pressure_bar | чтение, без повторной поправки |
| Автоподпитка | enabled | чтение/команда 0 или 1 только в полном варианте |
| Состояние | state_text | чтение |
| Аварийная блокировка | alarm | чтение: «Авария» / «Нет блокировки» |
| Причина аварии | fault | чтение |
| Причина запрета | block_reason | чтение |
| Датчик давления | sensor_alarm | чтение; при ошибке числу давления не доверять |
| Низкое давление | low_pressure_alarm | чтение |
| Авторежим WB | auto_mode | чтение; инженерное разрешение остаётся в WB |
| Сбросить аварию | reset_alarm | кандидат однократного действия, только после проверки |

Все MQTT пути начинаются с `/devices/lastochka_pressure_makeup/controls/`. Единственные допустимые пути записи — `enabled/on` и `reset_alarm/on`. Ни одного пути K5, изменения offset или физических команд в шаблонах нет.

Для автоподпитки нужны **enabled=true и auto_mode=true**. Инженер должен проверить autorежим в WB; пользовательский переключатель намеренно не обходит его и не пишет сразу в два controls. В DISCOVER оба false. В ReadOnly переключатель также только показывает состояние.

Давление не обнуляется при ошибке и не заменяется вычислением из другого источника. №414 может сохранять числовое давление при sensor_alarm: поэтому статус датчика обязателен. Сам MQTT-template не гарантирует свежесть кэша при остановке WB; до приёмки требуется проверка поведения потери связи. Принудительный C_Online=true отсутствует.

## Как устроен кандидат сброса

Самый близкий к кнопке вариант на уже известных типах — Switch/On с `data.SwitchOffTime=0.1`. На ON он должен отправлять `1`, при автоматическом OFF — `0`. Обработчик №414 реагирует только на истинное значение, поэтому целевой результат — один запрос сброса на нажатие. Нет topicGet, который мог бы повторно включить действие из retained-state. На link задан `retain:false`.

**Это параметры кандидата, не доказательство поведения данной beta.** DISCOVER не содержит поддержку/эффективность retain и SwitchOffTime, а документация общего механизма auto-off не доказывает отсутствие повторной публикации при восстановлении связи. Неизвестно и наличие штатного подтверждения нажатия. Нельзя выдавать авто-OFF за гарантию exactly-once, защиту от двойного нажатия или от восстановления состояния.

Кнопку держать внутри карточки, вне голосовых мостов и автоматизаций. Требуемый текст подтверждения: «Сбросить аварию и лимиты подпитки? При разрешённой автоматике подпитка может начаться сразу». Если штатное подтверждение/защита от повторного нажатия недоступны, командную часть не выпускать заказчику; временно использовать уже работающий сброс в WB. Общий Configurator ради кнопки не расширять.

После подтверждения механики у сервиса «Сбросить аварию» вручную отключить отдельную плитку (visible=false), сохранив доступ внутри карточки; проверить это на beta. YAML оформляет только общие сервисы ReadOnly/candidate и не включает непроверенную кнопку. Никаких bridge.alice даже со значением false: для этой beta оно UNKNOWN.

## Короткая установка — после отдельного разрешения

1. Сохранить резервную копию Sprut и настройки затрагиваемого устройства. Убедиться, какой MQTT-контроллер читает брокер WB. Не менять или перезапускать действующие контроллеры ради проверки вслепую. Если отдельного MQTT-контроллера нет, его создание/настройка — отдельное изменение, пока не выполненное.
2. Сначала получить перечисленные ниже read-only данные. Проверить, что matcher `/devices/(lastochka_pressure_makeup)/controls/pressure_bar/meta/type` действительно существует и не пересекается с уже установленным custom template. Автоматическая native-интеграция и MQTT — разные источники: старый `wb:lastochka_pressure_makeup` автоматически не заменится.
3. Для первого этапа через **Каталог → MQTT → импорт файла** загрузить только ReadOnly. Не пользоваться старым способом копирования на флешку. Не удалять существующие шаблоны/устройства и не запускать широкое автосоздание всех устройств брокера без просмотра списка.
4. Проверить новое единственное MQTT Accessory и fresh DISCOVER. По соглашению matcher ожидается serial `lastochka_pressure_makeup`, но это ещё не подтверждено beta. Если serial другой — изменить в объектовом YAML только на фактический однозначный serial. Не использовать native `wb:...` и не переносить runtime aId/sId из старого экспорта.
5. Открыть свежий DISCOVER и YAML в Configurator, выполнить DRY RUN. Проверить все действия: только новый Accessory, имя/комната/видимость/статусы. До создания нового Accessory текущий offline DRY RUN закономерно блокируется отсутствующим serial; это не ошибка инструмента.
6. APPLY оформления — только после отдельного разрешения. Сверить давление с WB одновременно; новые state_text/fault/block_reason должны быть read-only и обновляться. Пустые/старые данные не принимать за норму.
7. Полный candidate подключать только после теста Probe и решения вопросов доступности, подтверждения сброса и старого K5. Нельзя просто импортировать второй вариант рядом с ReadOnly и рассчитывать на безопасную замену: сначала уточнить механизм обновления конкретного Accessory в beta, сохранить возможность отката.
8. После успешной проверки отдельно согласовать скрытие старого native Accessory и отзыв прямого управления K5 из Sprut. **Скрыть K5 недостаточно**: его On.write сейчас true. Нужна подтверждённая настройка read-only/отключение только этой связи; не трогать остальной MR6CU или действующие устройства. Эта задача пока не выполнена.

## Probe: короткая проверка команд без физики

Пока только подготовлен, **не выполнялся**. После отдельного согласования использовать отдельный тестовый брокер/стенд Sprut той же beta; тестовая ветка `lastochka_pressure_makeup_probe` не должна иметь ни одного подписчика, связывающего её с №414 или физическими выходами. Не устанавливать копию управляющего скрипта.

1. Опубликовать искусственные state/meta сообщения в тестовую ветку, импортировать PROBE. Это единственный файл с командной частью, разрешённый для проверки до приёмки; его matcher исключает рабочее виртуальное устройство.
2. С пассивным наблюдением MQTT нажать сброс один раз. Ожидаются один `1`, затем один `0`, оба без retain; UI возвращается в OFF. Новому подписчику не должно доставляться сохранённое `1` в command topic.
3. Повторить одиночное нажатие: снова ровно один `1`. Проверить быстрый двойной клик/подтверждение: случайные дубли должны быть исключены штатным UX; иначе не выпускать кнопку заказчику.
4. Проверить reconnect и restart только тестового Sprut, в том числе сразу после ON. Без нажатия не должно появляться ни одного нового `1`. Никаких команд из state/meta, перезагрузки интерфейса или синхронизации.
5. Проверить чтение значений, readonly, пустые/нечисловые давления, sensor_alarm и остановку тестового источника: устаревшая цифра не должна выглядеть достоверной. Если beta не предоставляет корректную индикацию недоступности — остановить внедрение до уточнения штатной availability-привязки, не маскировать online.

Проверка настоящего reset_alarm — отдельный полевой шаг с оператором. Чтобы не запустить цикл, предварительно оператор проверяет запрет подпитки и отсутствие активного цикла; само изменение разрешений также требует его согласования. Даже reset при активном цикле вызывает stopCycle и может отправить OFF: нельзя считать его пассивной диагностикой. Не проверять высокое давление, датчик или клапан искусственными записями в рабочие каналы.
