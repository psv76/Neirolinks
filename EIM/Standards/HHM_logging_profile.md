# HHM — профиль журналирования и диагностики

Дата: 29.09.2026.

Этот документ дополняет `WB_logging_standard.md` правилами для Heating Manager / HHM3.

Он не заменяет общий стандарт.

Связанные задачи: #69, #80, #81, #90, #94.

---

## 1. Цель

Для отопления оператор должен быстро понимать:

- есть ли запрос тепла;
- почему контур начал/не начал/прекратил нагрев;
- какая значимая команда была отправлена;
- есть ли ошибка выхода, датчика или источника;
- работает ли система в резерве;
- восстановилось ли штатное состояние.

Полное доказательство причин «почему холодно» выполняется по operator journal + текущему состоянию + MQTT history + diagnostic bundle.

---

## 2. Что показывать в текущем состоянии

Для каждого контура — только необходимые оператору поля:

- понятное состояние;
- наличие запроса;
- команда насосу;
- доступный readback реле отдельно от команды;
- расчётная команда смесителя, если применимо;
- Switch/readback и saved Level, если это нужно для понимания WB-MAO4;
- температуры подачи/обратки, если они существуют;
- активная ошибка/защита;
- «До запуска насоса»;
- «До остановки насоса».

Для источника:

- выбранный потребитель;
- запрошенная температура;
- отправленная уставка, если она отличается;
- состояние OT/источника;
- доступная температура источника;
- активная ошибка/ограничение.

Countdown обновляется в VD и не журналируется каждый цикл.

---

## 3. Обязательные операторские события HHM

### Контур

Писать при изменении:

- появился готовый запрос и начат нагрев;
- последний запрос снят и нагрев прекращается;
- начато ожидание открытия зоны;
- ожидание завершено/отменено/прервано;
- начат выбег насоса;
- выбег завершён/отменён/прерван;
- команда насосу изменилась ВКЛ ↔ ВЫКЛ;
- значимая команда закрыть/разрешить горячий порт;
- ошибка записи выхода;
- обязательный readback не подтверждён после timeout/retry;
- ошибка выхода восстановилась;
- подтверждённая защита/перегрев и её снятие;
- переход в резерв и возврат.

### Датчики

Писать:

- датчик стал непригоден;
- причина пригодности изменилась существенно;
- датчик восстановился.

Не писать стабильный OK каждый цикл.

### Источник

Писать:

- OT/источник стал недоступен;
- датчик источника потерян/восстановлен;
- подтверждён перегрев источника;
- ошибка записи уставки;
- функция восстановилась;
- существенное изменение режима source ON/OFF, если оно действительно управляется и доказуемо.

Кратковременные внутренние состояния подтверждения выхода, которые возникают на каждом обычном регулировочном шаге и не меняют технологический режим, относятся к technical trace, а не operator journal.

---

## 4. Что не должно попадать в operator journal HHM

Не журналировать как обычные INFO:

- каждый шаг регулирования клапана;
- последовательность `WAIT_OUTPUT_READBACK → HEAT_COMMANDED` при каждом нормальном изменении Level;
- полный набор readback Level/Switch/pump в каждой строке;
- `saved_level` в каждой строке;
- `seq` каждого readback;
- повторяющиеся «положение штока не измеряется / вращение насоса не измеряется / расход не измеряется»;
- каждую смену transient source-state, вызванную коротким подтверждением штатного output write;
- каждую итерацию NORMAL при неизменном технологическом смысле;
- изменение countdown.

Эти данные относятся к machine-readable trace и diagnostic bundle.

---

## 5. Technical trace HHM

Для глубокого разбора HHM может отдельно публиковать machine-readable trace.

Trace может содержать:

- state-machine state;
- расчёт клапана;
- write attempts;
- readback value/seq/time;
- saved Level;
- output readiness;
- requested pump;
- source request;
- причины transient states.

Trace:

- не выводится в `journalctl -u wb-rules` как обычный операторский INFO;
- не влияет на алгоритм;
- может быть собран NST #90;
- не заменяет MQTT history;
- имеет отдельный признак/топик либо явно machine-only contract.

## 6. WB-MAO4

Для Иволги и других объектов с тем же подтверждённым контрактом:

- `Switch=OFF` — электрическая команда отключить горячий порт;
- `Dimming Level` может сохранять прежнее значение;
- `Level=72%, Switch=OFF` не означает фактическое открытие 72%;
- readback Switch не подтверждает движение штока;
- физическое положение и расход считаются неизвестными без независимых датчиков.

### Операторский журнал

При закрытии достаточно значимого сообщения:

```text
[отопление][HHM3][502]; КОМАНДА=Закрыть горячий порт; причина=Снят запрос тепла; канал=A05/Channel 2 Switch; значение=ВЫКЛ
```

При ошибке:

```text
[отопление][HHM3][502]; ОШИБКА=Закрытие смесителя не подтверждено; ожидается=ВЫКЛ; прочитано=ВКЛ
```

Raw Level, seq, saved Level и подробности retry остаются в trace.

---

## 7. Таймеры

### Ожидание открытия зоны

Journal:

```text
СОСТОЯНИЕ=Начато ожидание открытия зоны; длительность_с=180
СОСТОЯНИЕ=Ожидание открытия зоны завершено
```

или:

```text
СОСТОЯНИЕ=Ожидание открытия зоны отменено; причина=Запрос снят
```

### Выбег

Journal:

```text
СОСТОЯНИЕ=Начат выбег насоса; длительность_с=120
СОСТОЯНИЕ=Выбег насоса завершён
```

или отмена/прерывание.

Остаток времени — только VD.

---

## 8. Sensor Health

Событие потери должно содержать только необходимое:

```text
[отопление][HHM3][датчик пола 504]; ОШИБКА=Датчик температуры непригоден; причина=Sensor OK сообщает неисправность; действие=Перейти в предусмотренный резерв
```

Восстановление:

```text
[отопление][HHM3][датчик пола 504]; СОСТОЯНИЕ=Датчик температуры восстановлен
```

Подробные `phase/reason/cause/error/value/seq` допустимы в trace/diagnostic bundle, если нужны расследованию.

Недоступное значение не подменять нулём.

---

## 9. NO_RESPONSE

Недостаточный температурный отклик — WARNING, пока не доказана конкретная авария.

Нельзя из `NO_RESPONSE` автоматически утверждать:

- нет расхода;
- насос физически не вращается;
- клапан заклинил;
- котёл не горит.

Если предупреждение исчезло — должна быть понятна нормализация, но нельзя создавать циклическое WARNING/INFO при каждом кратковременном колебании внутреннего state.

---

## 10. «Почему в доме холодно?»

Диагностический путь HHM:

```text
есть запрос?
→ зона готова?
→ контур разрешил нагрев?
→ команда насосу/смесителю отправлена?
→ readback выхода согласован?
→ источник получил запрос?
→ источник доступен?
→ температура подачи меняется?
→ помещение реагирует?
```

Operator journal должен показать значимые разрывы этой цепочки.

Временную динамику и точные доказательства брать из diagnostic bundle и MQTT history, а не пытаться повторить их в каждой строке журнала.

---

## 11. Иволга: требуемая коррекция текущего HHM 3.3

По #69 и полевому журналу 29.09.2026 необходимо:

1. обычные `OUTPUT_TRANSITION` при каждом регулировочном шаге перенести из operator journal в technical trace;
2. убрать повторяющийся хвост:
   `положение_штока=Не измеряется; вращение_насоса=Не измеряется; расход=Не измеряется`;
3. не создавать WARNING/INFO oscillation только из-за штатного pending ON/OFF при сохранённом READY-пути;
4. краткие `REQUESTS_UNAVAILABLE ↔ ACTIVE`, возникающие на обычной фазе подтверждения нового output command, не должны засорять operator journal; если недоступность сохраняется, она должна стать видимым предупреждением;
5. сохранить operator events таймеров, safety, sensor lost/recovery, write/readback faults и реальных изменений команды насосу;
6. regression должен отдельно проверять operator journal и machine trace.
