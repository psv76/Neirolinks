# Стандарт развития, версионирования и накопления инженерного опыта

## 1. Назначение

Имена ПО и обязательный двухкомпонентный формат версий `X.Y` задаёт [стандарт именования и нумерации версий](Software_naming_and_versioning_standard.md). Формат `X.Y.Z` для новых версий ПО NEIROLINKS запрещён.

Этот стандарт определяет, как в репозитории NEIROLINKS ведётся разработка систем и объектов, как фиксируются принятые решения, как формируются Releases и как новый инженер, ChatGPT, Codex или NST определяет актуальное состояние.

Главная цель — не допускать ситуации, когда актуальная версия существует только в чате, в памяти участника или в случайной рабочей ветке.

Ключевой принцип:

> main — основная читаемая инженерная база. Рабочая ветка — временное пространство незавершённой работы. Release — неизменяемая опубликованная версия. Objects — актуальное известное состояние реальных объектов.

---

## 2. Каноническая структура main

~~~text
main
│
├── Objects
│   └── каждый объект = его актуальное состояние
│
├── Systems
│   ├── HHM
│   ├── NST
│   ├── NLP
│   └── Sprut Configurator
│
├── Templates
│   ├── Saturn
│   ├── Sprut
│   └── Wiren Board
│
└── EIM
    ├── Standards
    ├── AI
    └── документация
~~~

### Objects

Хранит факты конкретных объектов:

- фактически используемые объектовые скрипты;
- конфигурации;
- карты каналов;
- описание контроллеров;
- Sprut/YAML и другие объектовые данные;
- подтверждённые версии установленных общих систем;
- бэкапы и эксплуатационную документацию.

Если файл в Objects заявлен как актуальный runtime-файл, он должен соответствовать фактически установленному файлу на объекте. Если соответствие live не проверено, это должно быть явно указано.

Разработка будущего состояния объекта в рабочей ветке не делает его текущим состоянием Objects в main до принятия и, когда требуется, фактического внедрения и проверки.

### Systems

Хранит общие системы NEIROLINKS, не принадлежащие одному объекту:

- HHM;
- NST;
- NLP;
- Sprut Configurator.

В Systems/<system>/ находится текущее принятое состояние исходников, архитектуры, тестов и документации системы.

Старые версии системы не раскладываются по отдельным папкам 3.4, 3.5, 3.6 только ради хранения истории. История хранится Git и Releases.

### Templates

Хранит повторно используемые шаблоны:

- Saturn;
- Sprut;
- Wiren Board.

Шаблон не является доказательством состояния конкретного объекта.

### EIM

Хранит общую методику Engineering Integration Method:

- стандарты;
- AI-инструкции;
- процесс разработки;
- общую инженерную документацию.

## 3. Четыре разных состояния, которые нельзя смешивать

| Состояние | Где смотреть | Смысл |
|---|---|---|
| Текущая принятая разработка | main/Systems/<system>/ | Текущее интегрированное состояние системы |
| Незавершённая разработка | рабочая ветка + PR | Кандидат на изменение, ещё не источник истины |
| Последний approved Release | GitHub Releases/tag | Версия, разрешённая для штатной установки |
| Фактически установленное на объекте | main/Objects/<object>/ + live/deployment evidence | Что реально работает на конкретном объекте |

Эти версии могут различаться.

Пример:

~~~text
HHM development in main: 3.6
latest approved Release: 3.5
Иволга live:             3.5
~~~

или:

~~~text
HHM development in main: 3.6
latest approved Release: 3.5
Иволга live:             3.4
~~~

Само различие не является ошибкой. Ошибка — не понимать, какое из этих состояний рассматривается.

## 4. Обязательный жизненный цикл изменения

### Шаг 1. Обсуждение

Обсуждение может начаться в ChatGPT, Codex, на объекте или в GitHub Issue.

Обсуждение само по себе не является принятым инженерным решением.

Если решение влияет на архитектуру, структуру репозитория, алгоритм, объектовую конфигурацию, release process или эксплуатационные правила, оно должно закончиться сохраняемым артефактом в GitHub.

### Шаг 2. Зафиксировать задачу

Для нетривиальной разработки используется существующий GitHub Issue либо создаётся новый.

Issue фиксирует минимум:

- цель;
- scope;
- источники фактов;
- ограничения;
- критерий готовности.

Мелкая документальная правка может выполняться без отдельной Issue, если смысл изменения полностью понятен из PR.

### Шаг 3. Создать рабочую ветку от актуального main

По умолчанию любая новая работа начинается от последнего main.

Рекомендуемое именование:

~~~text
system/<system>/<issue>-<topic>
object/<object>/<issue>-<topic>
template/<platform>/<issue>-<topic>
eim/<issue>-<topic>
hotfix/<scope>/<issue>-<topic>
~~~

Примеры:

~~~text
system/hhm/106-postrun
system/nst/93-ivolga-pilot
object/05-31-ivolga/80-circuit-502
eim/repository-lifecycle
~~~

Имя ветки помогает навигации, но не определяет актуальность. Актуальность определяется состоянием main, PR, Release и объектными фактами.

### Шаг 4. Разработка и проверки

Работа выполняется в ветке.

Ветка может содержать код, тесты, документацию, migration и object-specific изменения в рамках задачи.

Коммиты должны отражать законченные смысловые изменения.

Если работа зависит от другого незамерженного PR, такая зависимость должна быть явно указана. Длинная цепочка stacked branches не должна становиться постоянным хранилищем актуальной системы.

### Шаг 5. Pull Request в main

Готовая работа оформляется PR с base main.

PR должен показывать:

- что изменяется;
- какие проверки реально выполнены;
- что не проверено;
- влияет ли изменение на объект/live;
- требуется ли Release.

Зависимый PR, временно созданный поверх другой рабочей ветки, перед окончательным принятием должен быть приведён к понятной цепочке относительно main. Нельзя оставлять новую принятую версию доступной только через многоуровневый стек веток.

### Шаг 6. Merge в main

После проверки PR сливается в main.

С этого момента изменение считается частью текущей принятой инженерной базы.

Рабочая ветка больше не является источником истины и может быть удалена после завершения работы.

### Шаг 7. Подготовка Release

Если результат должен стать устанавливаемой версией системы, Release создаётся только после того, как все его исходники, manifests и release metadata находятся в main.

Последовательность:

~~~text
рабочая ветка
      ↓
PR
      ↓
merge в main
      ↓
release-ready commit в main
      ↓
tag на конкретный commit
      ↓
GitHub Release
~~~

Release не должен ссылаться просто на меняющуюся ветку main. Его tag фиксирует конкретный commit, который входит в историю main.

Если для Release требуется отдельная правка manifest/version metadata, она сначала проходит обычный PR и merge в main, и только затем ставится tag.

### Шаг 8. Старые Releases

Старые Releases сохраняются.

Пример:

~~~text
HHM 3.4
HHM 3.5
HHM 3.6
~~~

После публикации 3.6 версии 3.4 и 3.5 не удаляются только потому, что стали старыми. Они нужны для аудита, расследований, воспроизводимости, rollback и понимания истории объектов.

Опубликованный tag/Release нельзя переносить на другие байты под тем же номером. Ошибочный Release помечается как устаревший или заменяется новой версией; история не переписывается без отдельного аварийного решения.

### Шаг 9. Внедрение на объект

Публикация Release не означает автоматического обновления объекта.

~~~text
approved Release
      ↓
deployment / NST sync / ручная установка
      ↓
проверка live
      ↓
обновление фактов Objects/<object>/
~~~

Если объект ещё работает на предыдущей версии, Objects/<object>/ не должен притворяться, что новая версия уже установлена.

## 5. Что должен считать источником истины ИИ

Перед разработкой ChatGPT или Codex должен определить слой задачи.

### Общая система

Смотреть:

~~~text
main/Systems/<system>/
~~~

и связанные approved Releases.

Рабочая ветка используется только если задача явно продолжает конкретный незавершённый PR.

### Конкретный объект

Смотреть:

~~~text
main/Objects/<object>/
~~~

и при необходимости подтверждать live-состояние контроллером, backup, deployment manifest, журналом или диагностическим пакетом.

### Общий шаблон

Смотреть:

~~~text
main/Templates/<platform>/
~~~

### Методика и правила

Смотреть:

~~~text
main/EIM/
~~~

Нельзя считать более новую по дате рабочую ветку автоматически более актуальной. Нельзя выбирать последнюю версию по имени ветки.

---

## 6. Что должен смотреть NST

NST не использует рабочие ветки как источник production deployment.

Целевая цепочка:

~~~text
main/Objects/<object>/controllers/<serial>.json
        ↓
controller registry
        ↓
approved Releases общих компонентов
        ↓
CI формирует immutable deployment manifest
        ↓
точные version + commit + SHA256
        ↓
NST check / sync
~~~

Правила:

1. Физический контроллер определяется по hardware identity/serial.
2. Назначение контроллера берётся из object-local controller profile в принятом состоянии репозитория.
3. Общие компоненты разрешаются только через approved Releases.
4. Deployment manifest фиксирует конкретную версию, commit и SHA256.
5. NST не устанавливает произвольный HEAD рабочей ветки и не выбирает версию по имени ветки.
6. nst check может показать доступную approved версию; nst sync выполняется только явно.
7. Факт установленной версии подтверждается локальным state/live evidence, а не наличием новой версии в GitHub.

## 7. Накопление инженерного опыта

После работы на объекте результат должен быть классифицирован.

### Факт конкретного объекта

Остаётся в:

~~~text
Objects/<object>/
~~~

Примеры: физический канал, адрес устройства, назначение реле, особенность гидравлики, установленная версия, объектовая уставка.

### Общий механизм системы

Переносится в:

~~~text
Systems/<system>/
~~~

Примеры: общий алгоритм HHM, transaction engine NST, общая логика Sprut Configurator.

### Повторно используемый шаблон

Переносится в:

~~~text
Templates/<platform>/
~~~

### Общее правило или метод

Фиксируется в:

~~~text
EIM/
~~~

Таким образом работа на объекте должна при необходимости давать два результата:

~~~text
актуализированный объект
+
выделенный переносимый опыт
~~~

Переносимый опыт нельзя извлекать вместе с чужими физическими каналами и объектными параметрами.

## 8. Правило артефакта

Инженерная договорённость не считается надёжно сохранённой, если она существует только:

- в чате;
- в памяти участника;
- в незамерженной ветке без понятного статуса;
- в устном обсуждении.

После принятия существенного решения должен остаться один или несколько артефактов:

- изменение в main;
- стандарт;
- README;
- Issue с зафиксированным решением;
- merged PR;
- manifest;
- tag/Release;
- объектовый документ.

Если принятое решение изменяет постоянное правило работы, итоговый артефакт должен быть доступен из main.

---

## 9. Что не делать

Не использовать как постоянную модель:

~~~text
ветка A
  ↓
ветка B
  ↓
ветка C
  ↓
ветка D
~~~

где только последний участник разговора знает, какая ветка правильная.

Не хранить старые версии систем отдельными рабочими каталогами в main, если Git/Release уже обеспечивает историю.

Не публиковать production Release из commit, который не входит в принятую историю main.

Не обновлять Objects до будущего состояния только потому, что новая версия разработана или опубликована.

Не считать Issue, PR или chat-history заменой актуальной документации.

## 10. Краткая памятка

~~~text
Обсудили
   ↓
Issue / зафиксированный scope
   ↓
ветка от main
   ↓
разработка + тесты
   ↓
PR → main
   ↓
merge
   ↓
при необходимости Release из конкретного commit main
   ↓
явное внедрение
   ↓
live-проверка
   ↓
актуализация Objects
   ↓
выделение общего опыта в Systems / Templates / EIM
~~~

Если эта цепочка выполнена, новый человек или ИИ не должен восстанавливать актуальное состояние по истории чатов и случайным веткам.
