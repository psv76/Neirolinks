# Система логирования и диагностических панелей WB-rules

Дата фиксации: 13.09.2026  
Связанная задача: #44

## 1. Назначение

Этот стандарт описывает, как скрипты `wb-rules` должны давать инженеру на объекте понятную картину работы системы.

Стандарт нужен не только для расследования аварий после события, но и для текущей диагностики:

```text
что система делает сейчас;
почему она это делает;
какой слой разрешил или заблокировал работу;
какая команда рассчитана;
какая команда реально отправлена в физический канал;
есть ли подтверждённый технологический отклик.
```

Для Heating Manager 2.0 дальше используется сокращение `HM2`.

---

## 2. Три источника диагностики

Диагностика WB-rules состоит из трёх разных источников. Они не заменяют друг друга.

| Источник | Что показывает | Когда использовать |
|---|---|---|
| Виртуальные каналы состояния | Текущее состояние прямо сейчас | Открыть WebUI и понять, почему система работает или не работает |
| Системный журнал `wb-rules` | События и причины переходов во времени | Разобрать, что произошло раньше и почему |
| MQTT-история физических каналов | Фактические изменения реле, насосов, клапанов, диммеров, уставок | Проверить, что физическая команда действительно была отправлена |

Пример:

```text
виртуальный канал показывает: pump_cmd=1;
журнал показывает: почему насос должен включиться;
MQTT-история физического канала показывает: было ли реально записано ON в реле насоса.
```

Нельзя считать виртуальный расчёт доказательством физического действия.

---

## 3. Виртуальные каналы как диагностическая панель

Виртуальное устройство скрипта — это не только интерфейс управления. Для HM2 это основная диагностическая панель.

Она должна отвечать на вопросы:

```text
есть ли запрос тепла;
валиден ли контур;
готов ли физический путь;
какая команда рассчитана;
разрешена ли физическая запись;
что выбрал арбитр;
что делает источник;
есть ли авария или блокировка;
какой watchdog сейчас активен.
```

Часто меняющиеся расчётные значения лучше держать в виртуальных каналах, а не писать в журнал на каждом цикле.

Примеры таких значений:

```text
текущая температура;
расчётная команда насоса;
процент клапана;
текущий выбранный потребитель;
текущий статус watchdog;
оставшееся время задержки;
возраст запроса;
текущая причина блокировки.
```

## 4. Базовые каналы HM2

Новые HM2-скрипты должны иметь минимальный набор диагностических каналов по смыслу роли скрипта.

### 4.1. Общее состояние

| Канал | Смысл |
|---|---|
| `state` | Основное состояние: `INACTIVE`, `ACTIVE`, `UNKNOWN`, `FAULT`, другое точное состояние скрипта |
| `valid` | Может ли результат скрипта использоваться другими слоями |
| `status` | Человеческое объяснение текущего состояния |

`valid=1` не означает, что есть запрос тепла. Это означает, что результат скрипта пригоден к чтению.

### 4.2. Запрос тепла

| Канал | Смысл |
|---|---|
| `heat_demand` | Есть ли запрос тепла от этого потребителя |
| `requested_supply_c` | Запрошенная температура подачи контура |
| `requested_source_temperature` | Запрошенная температура источника |
| `request_reason` | Почему сформирован или не сформирован запрос |
| `request_timestamp` | Время расчёта запроса |
| `request_ttl_s` | Сколько секунд запрос считается свежим |

### 4.3. Готовность физического пути

| Канал | Смысл |
|---|---|
| `active_zone_count` | Количество активных логических зон |
| `physical_active_output_count` | Количество активных физических выходов зон |
| `zone_inputs_valid` | Доступны ли состояния зональных выходов |
| `path_ready` | Выдержана ли задержка открытия сервоприводов / готов ли путь теплоносителя |

`path_ready=1` не доказывает проток. Это только разрешение продолжать логику после выдержки задержки и проверки условий.

### 4.4. Команды и обратная связь

| Канал | Смысл |
|---|---|
| `pump_cmd` | Расчётная команда насоса |
| `pump_on` / `pump_physical_state` | Прочитанное состояние реле насоса, если доступно |
| `valve_position_cmd` | Расчётная команда положения клапана |
| `valve_position_physical` | Прочитанное значение выхода клапана, не положение штока |
| `valve_enable_physical` | Прочитанное состояние питания клапана |
| `physical_readback_valid` | Доступен ли readback физических выходов |

Readback реле или аналогового выхода не равен доказательству протока, движения штока или фактического нагрева.

### 4.5. Арбитраж HM2

| Канал | Смысл |
|---|---|
| `selected_consumer` | Выбранный потребитель тепла |
| `selected_consumer_title` | Читаемое имя выбранного потребителя |
| `selected_requested_temperature` | Выбранная температура источника |
| `selected_reason` | Почему выбран этот потребитель |
| `no_demand_contract` | Нет валидного запроса тепла |
| `active_candidate_count` | Сколько кандидатов пригодны для выбора |
| `rejected_candidate_count` | Сколько кандидатов отвергнуто |
| `candidates_json` | Диагностический снимок всех кандидатов |
| `grant_XXX_state` | Состояние grant для конкретного потребителя |
| `grant_XXX_reason` | Причина grant/reject для конкретного потребителя |

### 4.6. Источник тепла

| Канал | Смысл |
|---|---|
| `source_state` | Состояние источника тепла |
| `physical_write_grant` | Разрешена ли физическая запись в источник прямо сейчас |
| `write_block_reason` | Почему физическая запись запрещена |
| `requested_heating_setpoint` | Уставка, запрошенная арбитром |
| `limited_heating_setpoint` | Уставка после ограничений источника |
| `written_heating_setpoint` | Последняя реально записанная уставка |
| `last_written_ts` | Время последней записи |
| `source_temperature_c` | Температура источника |
| `boiler_connection` | Состояние связи с котлом / интерфейсом |
| `boiler_fault` | Авария котла по доступным признакам |
| `boiler_flame` | Флаг пламени, если доступен |
| `boiler_modulation` | Модуляция горелки, если доступна |

### 4.7. Тепловой отклик и аварии

| Канал | Смысл |
|---|---|
| `response_status` / `response_state` | Состояние watchdog отклика потребителя |
| `response_elapsed_s` | Сколько секунд идёт проверка отклика |
| `response_rise_c` | Измеренный рост температуры |
| `source_response_status` | Отклик источника тепла |
| `source_response_elapsed_s` | Сколько секунд источник проверяется на отклик |
| `fault_latched` | Защёлкнутая авария потребителя |
| `fault_text` | Причина аварии потребителя |
| `source_fault_latched` | Защёлкнутая авария источника |
| `source_interlock` | Источник заблокирован защитой |
| `fault_reason` | Причина аварии или блокировки источника |

## 5. Терминология состояний HM2

| Состояние | Смысл |
|---|---|
| `INACTIVE` | Нет активной работы или нет запроса |
| `ACTIVE` | Есть активный валидный запрос или активная работа |
| `NO_DEMAND` | Валидно подтверждено отсутствие запроса |
| `NOT_COMMISSIONED` | Подсистема ещё не введена в работу |
| `SHADOW_*` | Логика считает, но физическая запись запрещена |
| `SAFE_OUTPUTS` | Скрипт активно пишет безопасный физический ноль |
| `PHYSICAL_*` | Разрешена физическая работа в явно обозначенном режиме |
| `DEGRADED_PLANNED` | Известный долг ПНР или неполная функция, но не runtime-авария |
| `DEGRADED_RUNTIME` | Проблема во время работы, но часть системы может продолжать работу |
| `INTERLOCK` | Работа заблокирована защитным условием |
| `FAULT` | Авария, требующая действия или сброса |
| `FAULT_LATCHED` | Авария защёлкнута и не должна исчезать сама |
| `DECISION_REQUIRED` | Нельзя безопасно выбрать поведение без инженерного решения |

Важно не смешивать:

```text
невведённый в работу контур;
теневой расчёт;
безопасный физический ноль;
ручной режим ПНР;
штатную рабочую эксплуатацию;
runtime-аварию.
```

## 6. Формат строки системного журнала

Базовый формат:

```text
[система][скрипт][контекст]; СОБЫТИЕ=значение; параметр=значение; параметр=значение
```

Первый блок — инженерная система:

```text
[отопление]
[питание]
[вода]
[протечки]
[вентиляция]
[ворота]
[освещение]
[уведомления]
```

Второй блок — имя скрипта или логического узла:

```text
[620_thermostats]
[501_tp_dom_manager]
[HM2_source_manager]
```

Третий блок — контекст, понятный инженеру:

```text
[детская справа]
[501 ТП дом]
[503 Радиаторы дом]
[источник тепла]
```

Пример:

```text
[отопление][501_tp_dom_manager][501 ТП дом]; OUTPUT_MODE=PHYSICAL_MANUAL_COMMISSIONING; причина=ручной grant ПНР; насос=A03/K1; клапан=A05/Channel 1
```

## 7. Имена событий

Для новых HM2-скриптов использовать стабильные технические имена событий на английском в верхнем регистре. Это нужно, чтобы одинаково искать события через `grep`, `journalctl` и WebUI.

| Событие | Уровень | Когда писать |
|---|---|---|
| `SCRIPT` | `log.info()` | старт, инициализация, версия, безопасный сброс разрешений |
| `STATE` | `log.info()` | значимая смена состояния алгоритма |
| `DEMAND` | `log.info()` | появление или исчезновение запроса тепла |
| `GRANT` | `log.warning()` или `log.info()` | выдача, снятие или отказ разрешения |
| `OUTPUT_MODE` | `log.warning()` | смена режима физической записи: shadow/safe/physical |
| `COMMAND` | `log.info()` | попытка записи в физический канал или уставку |
| `RESULT` | `log.info()` | подтверждённый технологический результат |
| `WATCHDOG` | `log.warning()` или `log.error()` | watchdog ждёт, подтвердил отклик или остановил систему |
| `FAULT` | `log.error()` | авария или защёлкнутая авария |
| `RESET` | `log.info()` или `log.warning()` | ручной сброс аварии или отказ сброса |
| `INTERLOCK` | `log.warning()` или `log.error()` | защитная блокировка |

Для старых и простых WB-скриптов допустимы русские типы:

```text
СКРИПТ
СОСТОЯНИЕ
НАСТРОЙКА
КОМАНДА
РЕЗУЛЬТАТ
ОШИБКА
АВАРИЯ
WATCHDOG
```

В одном новом HM2-скрипте не смешивать русские и английские имена событий без отдельной причины.

Текст события и параметры могут быть на русском языке.

---

## 8. Уровни журнала

| Уровень | Что означает |
|---|---|
| `log.info()` | Нормальная работа, старт, запрос, результат, запись команды |
| `log.warning()` | Нештатное или опасное для автоматического режима состояние, но безопасно обработанное |
| `log.error()` | Авария, watchdog-остановка, защёлка, невозможность безопасной работы |

`warning` для `OUTPUT_MODE=PHYSICAL_*` допустим: это помогает быстро увидеть моменты физического воздействия при ПНР.

## 9. Команда, readback и технологический результат

`COMMAND` / `КОМАНДА` означает попытку записи.

Не писать как факт:

```text
клапан открылся;
насос работает;
контур греется;
котёл нагрел.
```

если это не подтверждено независимым признаком.

Писать:

```text
COMMAND=Включить насос; канал=A03/K1; значение=ON
COMMAND=Записать уставку источника; канал=wbe2-i-opentherm_XX/Heating Setpoint; значение=45
```

Readback реле подтверждает только состояние канала или записанное значение, но не доказывает:

```text
проток теплоносителя;
фактическое движение штока;
открытие коллектора;
работу насоса по гидравлике;
нагрев помещения.
```

Технологический результат писать отдельным событием `RESULT`, `WATCHDOG` или `FAULT`, если он подтверждён датчиком температуры, давления, расхода, концевиком, током или другим независимым признаком.

## 10. Что логировать событием, а что держать в виртуальном канале

Не писать лог на каждом периодическом расчёте без изменения состояния.

В виртуальных каналах держать:

```text
температуры;
текущие команды;
текущий режим;
процент клапана;
возраст запроса;
таймеры watchdog;
текущую причину блокировки;
текущий выбранный контур.
```

В журнал писать события:

```text
старт скрипта;
сброс live-разрешений при старте;
смена режима shadow / safe / physical;
появление запроса тепла;
исчезновение запроса тепла;
выбор другого потребителя арбитром;
разрешение или запрет физической записи;
попытка записи в физический канал;
попытка записи уставки источника;
подтверждённый технологический результат;
авария;
защёлка аварии;
ручной сброс;
отказ сброса;
срабатывание watchdog;
ошибка записи в физический канал;
потеря связи с важным устройством.
```

## 11. История MQTT и дублирование

Фактическое переключение исполнительного устройства смотреть по истории физического MQTT-канала.

Если физический канал уже пишет историю, не нужно без причины создавать отдельный `event_*` или виртуальный канал с тем же смыслом.

Виртуальный канал добавлять, если он нужен для одного из трёх случаев:

```text
оператору нужно видеть состояние сейчас;
другой скрипт должен читать это состояние;
историю события невозможно удобно восстановить только по физическому каналу.
```

---

## 12. Когда нужны `event_*` каналы

`event_*` каналы не являются обязательной частью каждого скрипта.

Они нужны для процессов, где важен снимок состояния в момент события:

```text
подпитка давления;
авария котла;
протечка;
критичный насос;
клапан с аварийной логикой;
питание;
комплексная ПНР-проверка.
```

Минимальный набор:

```text
event_counter
event_time_s
event_type
event_text
```

Профильные поля добавлять только по смыслу:

```text
event_pressure_bar
event_temperature_c
event_delta_c
event_channel
event_command
event_result
```

`event_*` не заменяют системный журнал и не заменяют MQTT-историю физических каналов.

## 13. Как инженеру понять, почему «ничего не работает»

Для HM2 смотреть сверху вниз.

### 13.1. Термостат / зона

```text
target_state
state
физический выход зоны
```

Если зона не просит тепло, дальше контур может быть выключен штатно.

### 13.2. Manager контура

```text
state
valid
heat_demand
active_zone_count
path_ready
pump_cmd
status
fault_latched
fault_text
```

Если `heat_demand=1`, но `path_ready=0`, чаще всего ещё не выдержана задержка открытия сервоприводов или нет валидного состояния зон.

Если `pump_cmd=1`, но физический насос выключен, смотреть `outputs_enabled`, `manual_commissioning_grant`, `grant_state`, `status`.

### 13.3. Арбитр

```text
state
valid
selected_consumer
selected_requested_temperature
no_demand_contract
selected_reason
candidates_json
```

Если контур активен, но арбитр его не выбрал, смотреть причину в `candidates_json` и `grant_XXX_reason`.

### 13.4. Источник

```text
source_state
physical_write_grant
write_block_reason
requested_heating_setpoint
limited_heating_setpoint
written_heating_setpoint
source_response_status
boiler_connection
boiler_fault
```

Если есть запрос, но котёл не получает уставку, первым делом смотреть `physical_write_grant` и `write_block_reason`.

### 13.5. Физика и технологический отклик

```text
MQTT-история насоса;
MQTT-история клапана;
MQTT-история уставки источника;
температура источника;
температура подачи контура;
температура обратки контура;
response_status.
```

## 14. Локальная функция логирования

Пример для HM2-скрипта:

```javascript
var SYSTEM_NAME = 'отопление';
var SCRIPT_NAME = '501_tp_dom_manager';
var CONTEXT_NAME = '501 ТП дом';

function formatParams(params) {
    var list = [];
    var k;

    if (!params) return '';

    for (k in params) {
        if (params.hasOwnProperty(k)) {
            if (params[k] !== undefined && params[k] !== null && params[k] !== '') {
                list.push(k + '=' + params[k]);
            }
        }
    }

    return list.length ? '; ' + list.join('; ') : '';
}

function writeLog(level, eventName, eventText, params) {
    var message = '[' + SYSTEM_NAME + '][' + SCRIPT_NAME + '][' + CONTEXT_NAME + ']; ' +
        eventName + '=' + eventText + formatParams(params);

    if (level === 'error') {
        log.error(message);
    } else if (level === 'warning') {
        log.warning(message);
    } else {
        log.info(message);
    }
}
```

Пример использования:

```javascript
writeLog('warning', 'OUTPUT_MODE', 'PHYSICAL_MANUAL_COMMISSIONING', {
    причина: 'ручной grant ПНР',
    насос: 'A03/K1',
    клапан: 'A05/Channel 1'
});
```

## 15. Совместимость со старыми скриптами

Этот стандарт не требует немедленно переписывать старые WB-скрипты.

Для новых HM2-скриптов обязательны:

```text
диагностическая панель через виртуальные каналы;
разделение расчётной команды и физической записи;
понятный status;
понятная причина блокировки;
единый формат событий журнала;
логирование смены режима физической записи;
логирование аварий, watchdog и сбросов.
```

Для старых скриптов рекомендуется постепенно приводить формат к этому стандарту при плановой доработке, а не отдельными массовыми правками без практической задачи.

## 16. Числовые коды событий

Числовые коды событий не являются обязательной частью текущего стандарта.

В WebUI расследование обычно удобнее вести по:

```text
системе;
скрипту;
контексту;
типу события;
физическому каналу;
тексту причины;
виртуальным диагностическим каналам.
```

Если конкретному критичному скрипту нужны числовые коды, таблицу кодов писать в начале этого скрипта или в документации конкретного объекта.

Не вводить глобальную таблицу кодов для всех скриптов без отдельного решения.
