# Стандарт именования ПО NEIROLINKS и нумерации версий

## 1. Область действия

Нормативный стандарт для новых имён и версий программного обеспечения NEIROLINKS. В вопросах именования и формата версий этот документ имеет приоритет над прежними примерами в README, migration-документах и инструкциях сборки.

Порядок разработки, PR, публикации Release и внедрения определяется [стандартом жизненного цикла](Development_lifecycle_standard.md).

## 2. Именование

Бренд в названиях продуктов и документации: **NEIROLINKS**. В файловых путях, где нужен бренд, используется полное имя `neirolinks`. Сокращение `neiro` не используется для нового именования ПО.

### NST

**NST = NEIROLINKS Service Tool.** Канонические имена и пути:

| Назначение | Имя или путь |
|---|---|
| Продукт | `NST` — `NEIROLINKS Service Tool` |
| Исходники в репозитории | `Systems/NST/` |
| Debian package | `nst` |
| Артефакт Debian | `nst_<X.Y>_all.deb` |
| CLI | `/usr/bin/nst` |
| Runtime | `/usr/lib/nst` |
| Package data | `/usr/share/nst` |
| Документация пакета | `/usr/share/doc/nst` |
| Persistent config новых установок | `/mnt/data/etc/neirolinks/nst` |
| Persistent state новых установок | `/mnt/data/var/lib/neirolinks/nst` |
| Persistent logs новых установок | `/mnt/data/var/log/neirolinks/nst` |

`<X.Y>` в имени артефакта заменяется фактической двухкомпонентной версией: например, `nst_2.0_all.deb`. Пример не назначает номер следующего выпуска.

Имена `neiro-nst`, `nst-package`, `package-nst`, `nst-apt` и `nl-st` не являются альтернативными именами нового пакета NST. В сообщениях пользователю используются `NST` для продукта и `nst` для пакета или команды.

### Legacy migration compatibility

`nli` (включая `/usr/bin/nli` и существующий внутренний Python package) и старые пути с `/neiro/nli` допускаются только для совместимости при миграции существующих установок:

- `/mnt/data/etc/neiro/nli`;
- `/mnt/data/var/lib/neiro/nli`;
- `/mnt/data/var/log/neiro/nli`.

Они не являются новым именованием NST и не должны создаваться как штатная структура чистой установки. Новая установка использует канонические пути `neirolinks/nst` и не должна требовать предварительной установки NLI.

Старые имена пакетов и runtime-пути допустимы в исторических материалах и механизмах распознавания/миграции прежних установок. Перенос существующих config, state, logs, backup, pending, audit и rollback-данных требует отдельной реализации и проверки миграции; принятие стандарта само по себе не перемещает и не удаляет данные.

## 3. Версия ПО: только X.Y

Версия ПО NEIROLINKS содержит ровно два числовых компонента, разделённых точкой: **`X.Y`**.

- **X** — номер глобальной версии. Увеличивается при существенном расширении функциональности или изменении архитектуры. При переходе к следующей глобальной версии Y начинается с `0`.
- **Y** — номер ревизии внутри глобальной версии. Последовательно увеличивается при исправлениях и незначительных изменениях: `1.0` → `1.1` → `1.2`.
- Формат **`X.Y.Z` запрещён** для новых версий ПО NEIROLINKS. Третий компонент для patch не добавляется.

Два компонента — не обязательно две одиночные цифры: `1.9` → `1.10` → `1.11` допустимо. Компоненты — неотрицательные целые числа без ведущих нулей; `1.10` не сокращается до `1.1`.

| Изменение | Пример |
|---|---|
| Исправление или незначительное изменение | `2.0` → `2.1` |
| Следующая незначительная правка | `2.9` → `2.10` |
| Существенное расширение функциональности или изменение архитектуры | `2.10` → `3.0` |
| Недопустимый формат новой версии | `2.0.1` |

Номер должен совпадать в метаданных версии ПО, поле Version пакета, имени артефакта, выводе CLI и описании соответствующего Release. Префикс продукта в имени tag/Release не является компонентом версии и не разрешает добавление третьего числа.

Этот формат относится к версиям собственного ПО NEIROLINKS. Он не переименовывает версии сторонних зависимостей и самостоятельные версии схем/протоколов.

## 4. Применение к существующей реализации

Уже опубликованные tags, Releases, артефакты и записи о фактически установленных версиях сохраняют исходные имена и номера для аудита и воспроизводимости. Исторические `NLI 0.1.9` и `neiro-nst 1.0.0` не являются образцами для новых выпусков; переписывать их как `NLI 0.1` или `NST 1.0` нельзя.

Введение стандарта — изменение документации. Приведение сборки, Python package, runtime, persistent paths и release metadata к стандарту выполняется отдельным изменением с проверками чистой установки и обновления существующего NLI/NST. До этих проверок соответствие реализации стандарту и готовность чистой установки не считаются подтверждёнными.

Стандарт не назначает следующий номер NST, не выпускает пакет и не разрешает автоматическое обновление live-контроллеров.
