## Why ordinary Temperature MQTT is not positive poll evidence

By default `max_unchanged_interval=-1`, so an unchanged temperature need not
be republished after each successful RS-485/Modbus poll. Setting a **positive**
`max_unchanged_interval` can publish an unchanged value after a subsequent
normal driver read; this is a candidate way to obtain local liveness evidence
**without adding high-priority Modbus requests**, but changing the global
setting may increase MQTT publications across all configured devices.
The distinct `max_publish_interval` option republishes cached values without
a new register read; it was introduced in wb-mqtt-serial **2.270.0** and is
**NOT present** in the installed 2.268.0. Future driver upgrades must not
conflate the two publication modes.
Retained `/devices/wb-msw-v4_*/controls/Temperature` and a fresh timestamp
added by an HHM loop do **not** prove a new successful physical poll.
A device `meta/error` event may be useful as a negative health signal, but
absence of a new error/clear event is not independently attested success.

## Corrected device/Load request contract

`HHMRoomSerialLoadEvidence.create(config, HHMRoomSensorEvidence)` is a pure
ES5 state machine with injected module dependency. No relative Node `require`
in production code, no MQTT subscription, publish, Modbus command or physical
output write. `request()` only returns an intended request descriptor.

The verified **configured target** is sensor 22, type `WB-MSW v.4`, slave 22
on `/dev/ttyRS485-2` at 9600/8N2. The documented explicit addressing form
for `wb-mqtt-serial/device/Load/<client-id>` is:

```json
{
  "slave_id": 22,
  "device_type": "WB-MSW v.4",
  "channels": ["Temperature"],
  "path": "/dev/ttyRS485-2",
  "baud_rate": 9600,
  "parity": "N",
  "data_bits": 8,
  "stop_bits": 2
}
```

The manufacturer's RPC README and schema **also document `device_id`** as an
alternative addressing method. Earlier notes that called `device_id`
unsupported were **incorrect**. The pure planner intentionally uses the
explicit `slave_id` + `device_type` + port form to anchor all fields in the
read-only Iset configuration; the exact payload and response for installed
`2.268.0-wb102` have not been field-tested.
The RPC is documented as a high-priority channel read and therefore adds
RS-485 load. No `device/Set`, `device/SetPoll`, `port/Load` or `LoadConfig`
messages are generated by this module.

Every `request(now, bootEpoch, allowProbe)` call requires `allowProbe===true`
from a future trusted, independently rate-budgeted transport. Missing or
false grant returns `PROBE_NOT_AUTHORIZED` and creates **no** request.
An explicitly configured `minProbeGapMs` prevents repeated requests to a
single sensor within the specified interval (`PROBE_RATE_LIMITED`), but is
**NOT a global RS-485 bus budget**. No live interval has been approved; the
500 ms fixture is intentionally synthetic and must never be applied on Iset.
Each granted candidate call uses a unique non-retained request/reply topic suffix.
`reply({nowMs,bootEpoch,topic,retained,payload})` checks matching outstanding
request and its timeout; exact topic, same boot epoch, non-retained delivery,
numeric `id`, `error:null`, and a finite in-range
`result.channels.Temperature` value. Only then can
`HHMRoomSensorEvidence` receive a newly sequenced `WB_LOCAL_MODBUS_POLL`
observation. The same numeric temperature can be new evidence if a genuine
new request has succeeded.

Timeouts, wrong channels, invalid responses, stale replies, duplicate
messages, old boot and clock rewind do not qualify a sensor. Unique reply
topics are not by themselves authorization: the future **trusted WB-local**
transport must own its client prefix, subscribe before publishing, verify
the broker source, provide actual boot identity and monotonic time, and
prevent spoofed/retained payloads from being treated as a successful poll.
The present standalone module does **not** implement that transport.

## Safer alternative requiring separate validation

Prefer to evaluate `max_unchanged_interval` over periodic `device/Load` reads:
if a verified positive setting makes each room Temperature publication follow
a successful normal poll, it does not add RS-485 traffic. The resulting MQTT
message still needs session/retain/error qualification. On the current driver,
`max_publish_interval` is absent, but this must be version-gated on upgrades.
Before changing the active `wb-mqtt-serial.conf`, estimate MQTT volume of
all affected channels, preserve configuration backup, and review any service
restart side effects on active heating. There is **no permission to make such
changes in this phase**.
