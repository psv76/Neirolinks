# NL Project 3.0 — проверка физической идентичности трасс (Issue #216)

**Статус:** техническое описание кандидата PR #222, не отдельное продуктовое решение. Принятые правила: Q01, Q02, Q03, Q06 в `NL_PROJECT_3_Q01_Q11_DECISIONS.md` / Issue #216. Source of truth до merge остаётся `main/Systems/NLP`.

## 1. Откуда берётся физическая идентичность

В legacy модели `cable_topology_endpoint.id` принадлежит одной кабельной линии. **Он не является межлинейным физическим идентификатором**.

После миграции `000000000014_shared_box_endpoint` две `CableLine` могут иметь собственные `cable_topology_endpoint`, ссылающиеся на **один `cable_point.id`**. Для `point_kind=EL_BOX` эта общая физическая точка и её `cable_point.id` являются канонической связью между линиями. `BOX.010` остаётся обозначением/ссылкой в DWG и UI, а не заменой UUID физического объекта.

Разрешённые типизированные владельцы для сопоставления:

| Запись в topology | Физическая граница Project | Условие достоверности |
|---|---|---|
| `TOPOLOGY_POINT` → `INTERNAL_SOURCE` | `BOARD / board.id` | У `CableLine` задан активный `board_id` |
| `TOPOLOGY_POINT` → `EL_BOX` | `EL_BOX / cable_point.id` | Существующая точка Project соответствующего вида |
| `TOPOLOGY_POINT` → одиночное физическое устройство | `FIELD_DEVICE / field_device.id` | Ровно один подтверждённый активный физический владелец; неоднозначные монтажные группы не склеивать |
| `FIELD_PORT` | `FIELD_DEVICE / field_port.field_device_id` | Порт существует, активен и принадлежит активному устройству |
| `INSTANCE_RESOURCE` | `INSTANCE_RESOURCE / instance_resource.id` | Активный ресурс активного экземпляра |
| `BUS` root | `INSTANCE_RESOURCE / bus.root_resource_id` | Ресурс активен |
| `BUS` endpoint | `FIELD_DEVICE` или `INSTANCE_RESOURCE` | Типизированный `bus_endpoint` принадлежит той же шине; владелец активен |

Все владельцы берутся из таблиц **того же `project_id`**. Границы `{A,B}` образуют неориентированную физическую пару; `A→B` и `B→A` равны, но совпадения текста/координат/ГОФРА/длины недостаточно.

Для `BUS` связи с `connection_kind=TRACK` не являются монтажным кабелем и в проверку труб не включаются.

## 2. Что теперь делает read-only API

`CableService.conduit_physical_audit(project_id)` вызывает `load_conduit_membership_audit()` и выполняет только SQL `SELECT`.

По каждому существующему `Conduit` диагностируются **оба** существующих списка назначений: `conduit_segment_assignment` и `bus_segment_conduit_assignment`. Они не сливаются в новую таблицу.

- `EMPTY` — назначенных кабельных сегментов нет;
- `PHYSICAL_MATCH` — все известные назначенные сегменты имеют одинаковые подтверждённые физические границы;
- `UNRESOLVED` — хотя бы одну физическую границу/действующий сегмент нельзя подтвердить;
- `BOUNDARY_CONFLICT` — среди назначенных сегментов обнаружены разные канонические физические пары.

**`PHYSICAL_MATCH` не означает:** подтверждения общей физической трубы на объекте, допустимости совместной прокладки по нормам, заполнения/диаметра трубы, автоматического разрешения изменения назначений или готовности корректного расчёта длины/спецификации.

При обнаружении `UNRESOLVED`/`BOUNDARY_CONFLICT` read-only аудит **ничего не исправляет**, не меняет DWG, `path_json`, существующие назначения и ручные override. Проверка может работать на отдельном `Connection`/внутри будущего `UnitOfWork` без commit.

## 3. Зависимости до включения операций «Трасс»

1. Привязать фактические свойства труб и подтверждённые правила технической совместимости к планировщику `physical_conduit.py`. Совместимость нельзя вывести из одинакового `GOFRA_ID` или электрической сети; в текущем PR для неё нет нового хранилища и нет фиктивной auto-approval.
2. Выполнять проверку и все изменения ordinary/BUS assignments **в одной транзакции**, с защитой от конкурентных изменений/повторного sync; операция batch — all-or-none.
3. Явное транзитное прохождение непрерывного кабеля через physical-only `EL_BOX` не должно превращать `EL_BOX` в электрический topology point или создавать дополнительные выводы. Представление последовательных труб на непрерывном кабеле остаётся отдельной технической задачей интеграции Q02/Q03.
4. Q05/Q08 (единый ноль и окончательная длина), единичный учёт общей ordinary/BUS трубы в спецификации и migration/live acceptance выполняются отдельными контролируемыми этапами.
5. Ни одно из перечисленных технических условий **не является повторным запросом согласовать Q01–Q09**.
