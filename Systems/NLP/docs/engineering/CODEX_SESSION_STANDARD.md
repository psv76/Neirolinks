# NL Project — стандарт коротких сессий Codex (v1.0)

**Статус:** норматив процесса разработки; применяется ко всем будущим задачам NLP после принятия документа. Не изменяет runtime, CAD-контракт, schema или catalog.

## Разделение ответственности

- **Инженер-координатор (ChatGPT):** читает действующие контракты, готовит минимальный scope, зависимости, границы задачи и тесты, проверяет CI/PR, фиксирует решение о приёмке и готовит следующий этап.
- **Codex:** выполняет одну заранее ограниченную задачу: изменения кода и тестов, локальная проверка, коммит/PR или обновление branch, checkpoint. Codex не выбирает архитектуру самостоятельно и не выполняет бесконтрольный аудит всего репозитория.
- **GitHub:** постоянная память и source of truth: Issue (план, критерии), файл задания, PR/branch/commit SHA (код и evidence), компактная контрольная точка.

## Обязательный контракт каждой сессии

Перед запуском доступны: репозиторий и точный base ref + base SHA; задача и ожидаемый результат; список разрешённых областей; запрещённые изменения; ссылки на действующие нормативы; команды проверок и acceptance criteria; путь к checkpoint.

**Одна сессия = одна заранее подготовленная инженерная задача.** Не объединять разные архитектурные решения ради заполнения окна лимита.

Сначала убедиться, что base SHA и текущий branch соответствуют заданию. При расхождении **остановиться и зафиксировать** расхождение, не переписывать чужие изменения и не делать молчаливый rebase.

## Технические правила

1. Использовать отдельную рабочую ветку. Не менять `main`, реальные SQLite/DWG, AutoCAD и установленное приложение без отдельного разрешённого gate.
2. Приоритет реализации: минимальный вертикальный срез + проверяемые тесты; не делать несогласованный рефакторинг.
3. Не отключать упавшие тесты, не менять expected values без объяснения несовместимого нормативного изменения. Отличать дефекты fixture от дефектов production.
4. При изменении schema head/catalog successor: не объявлять live PASS до backup → штатной миграции → разрешённого catalog successor → startup smoke на рабочей базе, на отдельно разрешённом этапе.
5. Сохранять принятые идентификаторы, ручные значения, актуальные количества и защитные fail-closed проверки, если ТЗ прямо не разрешает их менять.
6. В Issue и отчёте фиксировать только факты и evidence. Не заявлять Windows/AutoCAD/live acceptance по Linux CI.

## Checkpoint: обязателен даже при частичном результате

При завершении каждого исполнимого среза сохранять в PR/Issue краткую контрольную точку:

- `task_id`, `base_sha`, `branch`, `head_sha`, статус `PASSED | PARTIAL | BLOCKED`;
- изменённые пути, реализованный контракт, тестовые команды и точные результаты;
- невыполненные условия, известные ограничения, следующая **одна** конкретная операция;
- нерассмотренные риски/потребность в решении архитектора.

При риске обрыва лимита сначала сохранить безопасный коммит и checkpoint. Не обещать завершение в следующем сеансе без сохранённого состояния. При невозможности зафиксировать коммит отметить `NOT_PERSISTED`; не ссылаться на несохранённую работу как на выполненную.

## Восстановление после 5-часового интервала

Следующая сессия получает **не переписку**, а checkpoint + task brief + точный commit. Проверяет HEAD и короткий diff, запускает только необходимые узкие тесты и исполняет указанную операцию. При отсутствии checkpoint либо расхождении SHA — fail closed, запрос координатору.

## Приёмка и переход

Координатор независимо проверяет изменённый код, отрицательные случаи, CI и критерии задачи. `PARTIAL` или успешная компиляция не равны `PASSED`. Только после приёмки текущего среза готовится следующий. Release/merge/live acceptance — отдельные gate с отдельным разрешением.
