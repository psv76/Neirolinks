# Разделение NL Project 1.0 и NL Project 2.0

## Назначение

Документ определяет границу между действующей NL Project 1.0 и создаваемой NL Project 2.0.

## Независимость версий

NL Project 1.0 и NL Project 2.0 являются независимыми программами.

- текущий принятый исходный код и документация NL Project 2.0 находятся в `Systems/NLP/` репозитория NEIROLINKS;
- локальная рабочая копия NL Project 2.0 может размещаться в `D:\NLP_2`;
- локальная NL Project 1.0 в `D:\NLP` остаётся отдельной системой и не является источником runtime-данных или требований версии 2.0.

Работы по NL Project 2.0 не должны изменять файлы, базу данных, DWG, настройки, ресурсы, резервные копии или временные данные NL Project 1.0. Исторический каталог `D:\NLP_2_DOCS` после завершения переноса не является действующим источником истины: принятые постоянные правила должны находиться в `Systems/NLP/docs/`, а история изменений — в Git.

## Объекты и данные

Существующие объекты остаются в NL Project 1.0. Их база данных, AutoCAD-блоки, DWG и созданные связи не мигрируются в NL Project 2.0.

NL Project 2.0 используется для новых объектов. Для неё создаются:

- новая база данных;
- новые AutoCAD-блоки;
- новый контракт сканирования DWG;
- собственные настройки;
- собственные ресурсы;
- собственные резервные копии;
- собственные временные файлы.

NL Project 2.0 не должна обращаться к изменяемым данным NL Project 1.0.

## Сопровождение NL Project 1.0

NL Project 1.0 продолжает использоваться для наладки и сдачи существующих объектов.

Необходимые исправления первой версии выполняются отдельно от разработки 2.0 и выпускаются отдельно по действующему стандарту `EIM/Standards/Software_naming_and_versioning_standard.md`. Задачи 2.0 не должны автоматически переноситься в 1.0, а исправления 1.0 — в 2.0.

## Использование результатов NL Project 1.0

Отсутствие нового решения в документации 2.0 не означает автоматическое наследование технической реализации 1.0.

Перед повторным использованием функция или компонент NL Project 1.0 должен пройти read-only аудит и получить один из статусов:

- `REUSE` — переносится почти без изменения;
- `ADAPT` — используется после адаптации к новой архитектуре;
- `REWRITE` — реализуется заново;
- `DROP` — не требуется в 2.0;
- `LATER` — откладывается до следующего выпуска.

Предметное поведение NL Project 1.0, которое не отменено требованиями 2.0, должно быть учтено в аудите наследования. Схема старой SQLite, методы доступа к данным, специальные правила и обходные решения не переносятся автоматически.

## Граница этого документа

Документ не определяет:

- схему новой базы данных;
- архитектуру программных модулей;
- состав MVP;
- сроки реализации;
- конкретные компоненты 1.0 для повторного использования.

Эти решения принимаются и фиксируются отдельно.
