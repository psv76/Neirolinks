# Расчёт длины кабелей и защитные трубы NL Project 2.0

## Актуализация Repair 08

Корень ordinary line задаётся `CABLE_SOURCE` и представляется derived `ROOT_ENDPOINT`; для источника на полевом реле применяется concrete reference `<BUS_POINT_ID>/<PORT>`, например `902.003/K1` или `902.003/K2`. `EL_BOX` — обычная topology point с `BOX_ID=BOX.NNN`, например `BOX.010`; её связи выводятся из `CABLE_SOURCE` дочерних точек, а retired `OUT_*` не является target ATTDEF. DALI/RS-485 route facts хранятся как отдельные physical `BusSegment`; их conduit assignment учитывается ровно один раз и не смешивается с ordinary `CableSegment`.

## 1. Назначение

Документ определяет способы прокладки физических участков кабельных линий, автоматический и ручной расчёт длины, запас у щита, топологию `CableSegment`, модель защитных труб и назначение сегментов в трубы.

## 2. Способ прокладки и физический сегмент

`CableLine` остаётся базовой кабельной линией с одним `CABLE_ID=XYY`. Физическая трасса линии может состоять из одного или нескольких внутренних `CableSegment`.

`CableSegment` — один физический участок кабеля между двумя соседними topology nodes/endpoints. Пользовательский `CABLE_ID` отдельному сегменту не присваивается.

Для каждого сегмента должен быть определён один способ прокладки:

- `По полу`;
- `В стяжке`;
- `По потолку`;
- `В стене`;
- `В брусе`;
- `В кабель-канале`.

Для простой линии с одним участком свойства сегмента одновременно являются свойствами всей линии. Для последовательной или разветвлённой линии разные сегменты могут иметь разные `MOUNT_WAY` и разные назначения в защитные трубы.

`CABLE_TYPE` и `BOARD` в текущем контракте остаются едиными свойствами базовой линии. Разные `CABLE_TYPE` на сегментах одной базовой линии не вводятся без отдельного решения.

**Целевой контракт Q05:** высоты всех физических точек, потолка и основания для одного объекта/здания приводятся к **единому нулю здания**. Нельзя создавать индивидуальные room/floor offsets. Старые DWG могут хранить `MOUNT_HEIGHT` от чистого пола; такие значения **не переинтерпретировать молча** — нужен подтверждённый mapping/миграционный gate перед применением новых геометрических формул.

## 3. Формирование топологии сегментов

Топология сегментов определяется предметной моделью, а не порядком INSERT, Handle или близостью блоков на плане.

Для обычной ветвящейся линии:

- `EL_BOX` имеет `BOX_ID=BOX.NNN`, а исходящие связи определяются `CABLE_SOURCE` дочерних точек;
- ссылка на точку той же базовой линии создаёт один `CableSegment`;
- цикл, двойной родитель, отсутствующая цель и неоднозначный корень запрещены.

Для общей линии выключателей `2YY` с несколькими физическими выключателями порядок `2YY.01 → 2YY.02 → ...` задаётся числовым порядком `.ZZ` от щита.

Для шин используются отдельные правила [23_DATA_BUS_TOPOLOGY.md](23_DATA_BUS_TOPOLOGY.md).

Для простой линии без ветвления и с одной конечной точкой существует один сегмент между физическим источником линии и этой точкой.

Физическим источником первого сегмента может быть щит либо назначенный выходной ресурс полевого устройства. Запас кабеля у щита применяется только к линии, физически начинающейся в щите.

### 3.1. Дизайн #216 Q02 / #235: физический транзит через EL_BOX

Новый `CABLE_TRANSIT` у `EL_BOX_OUT_100x100` описывает **неразрезанный обычный кабель** (например `301`, `301-1;302`), а не отдельное электрическое ребро `CABLE_SOURCE`. Кабель может пройти `BOARD → BOX.010 → BOX.020 → устройство`: геометрическая модель складывает физические участки, используя реальные точки коробок, **не** начисляя `0,20 м` за расключение на транзитных точках. Каждый участок может требовать отдельного способа прокладки/Conduit; однако одно поле `CABLE_TRANSIT` не сообщает, какая `MOUNT_WAY`/`GOFRA_*` относится к каждому промежутку. До implementation approval неизвлекаемые факты не домысливаются. **Принято для первого этапа (#235):** рассчитывать транзитные физические участки **только при однозначной последовательности BOX вдоль конкретного пути кабеля**. Если у ordinary линии есть ветвление и принадлежность транзитных BOX ветви неразличима, **не выводить предположительную геометрию/длину/трубу** для спорных участков: статус **`Требует внимания`**, сохранение достоверной ранее существовавшей электрической топологии и назначений. Несвязанные однозначные участки продолжают считаться. Новый branch-specific синтаксис `CABLE_TRANSIT` в этом этапе не вводить.

Для `TRACK_230V`, `TRACK_48V`, `TRACK_DALI` реальные **внешние** кабели заканчиваются на точке вставки/подключения `TRACK_ID=TRACK.NNN` и рассчитываются как `CableSegment`/внешний `BusSegment`. Связи `TRACK.NNN → LIGHT_TRACK_*` являются внутренними derived `TRACK` и **не создают ни кабельных метров, ни дополнительных труб**. `LENGTH` трека (мм) относится к изделию/раскрою, отдельно от длины входящего кабеля и итоговой трубы. Два отдельных монтажных кабеля в одну подтверждённо общую Conduit не удваивают её количество в спецификации.

Новый контракт использует единую принятую систему строительных отметок Q05 и математику Q04/Q08/Q06 из #216. Остальная legacy-формула в этом документе не является разрешением перезаписать работу draft #218/#230/#231: интеграция архитектурного изменения #235 должна учитывать их зависимости и пройти отдельный review/migration gate.

## 4. Расчёт расстояния и высоты одного сегмента

Координаты `X/Y` и `MOUNT_HEIGHT` используются в миллиметрах по [20_AUTOCAD_BLOCK_CONTRACT.md](20_AUTOCAD_BLOCK_CONTRACT.md).

Горизонтальное расстояние рассчитывается параллельно осям:

```text
Lxy_mm = |X2 - X1| + |Y2 - Y1|
```

### 4.1. `По полу`

Используются отметки бетонного основания `B1/B2`:

```text
L_floor =
(
    Lxy_mm
    + |H1 - B1|
    + |B2 - B1|
    + |H2 - B2|
) / 1000
```

### 4.2. `В стяжке`

`В стяжке` — отдельный способ прокладки выше слоя тёплого пола, но ниже чистого пола, до заливки стяжки. Он не эквивалентен `По полу`: `По полу` относится к нижней разводке на бетонном основании до утеплителя и тёплого пола.

Геометрия участка `В стяжке` считается между фактическими отметками точек по той же ортогональной схеме, что и для `В стене`:

```text
L_screed = (Lxy_mm + |H2 - H1|) / 1000
```

Для `В стяжке` защитная труба обязательна; `GOFRA_TYPE` должен быть задан каноническим типом и размером.

### 4.3. `По потолку`

Для высоты чистового потолка `C = R * 1000`:

```text
L_ceiling =
(
    Lxy_mm
    + |C1 - H1|
    + |C2 - C1|
    + |C2 - H2|
) / 1000
```

### 4.4. `В стене`

Участок считается проходящим в плоскости стены между двумя заданными точками. Автоматическая длина:

```text
L_wall = (Lxy_mm + |H2 - H1|) / 1000
```

Если фактическая штроба/обход отличается от такой ортогональной трассы, отклонение учитывается дополнительной или полной ручной длиной.

### 4.5. `В брусе`

Участок внутри конструкции из бруса имеет геометрию по той же ортогональной схеме, что и `В стене`:

```text
G_timber = (Lxy_mm + |H2 - H1|) / 1000
```

**Принято Q04/Q08 в #216:** не начислять историческую фиксированную прибавку `+0,5 м` за каждый сегмент `В брусе`, ни ordinary, ни BUS. Монтажная нелинейность/обходы учитываются только едиными проектными процентами от исходной геометрии или явно заданной дополнительной длиной/полным ручным override. Правила обязательной трубы для `В брусе` сохраняются.

### 4.6. `В кабель-канале`

```text
L_cable_channel = Lxy_mm / 1000
```

Вертикальные подъёмы, спуски и обходы, не выраженные точками топологии, учитываются ручной корректировкой.

## 5. Автоматическая и итоговая длина линии (Q04/Q05/Q08, #216)

**`G(segment)`** — чистая геометрическая длина физического `CableSegment` в метрах, без процентов, выводов, округления и дополнительных запасов. Сегменты внутри одной линии идентифицируются по **реальным физическим границам**, не по равенству координат или `GOFRA_ID`. Каждый уникальный физический сегмент суммируется один раз.

```text
R(segment)   = G(segment) × (1 + P_nonlinearity + P_bypass)
G_line       = Σ G(уникальных физических CableSegment)
R_line       = Σ R(уникальных физических CableSegment)
O_total      = O_board + O_box + O_endpoint + L_additional
Cable_raw    = R_line + O_total
Cable_auto   = RoundUp(Cable_raw, q)
Cable_final  = manual_full (если задано), иначе Cable_auto
RoundUp(L,q) = q × ceil(L/q), где q>0
```

- **Проценты:** `P_nonlinearity` + `P_bypass` складываются; оба относятся только к исходной геометрии `G`, без последовательного начисления одного процента на другой и без процентов на `O_total`.
- **Щит:** `O_board` = число реально начинающихся в щите **физических кабелей** × норму щитового вывода. Одна `CableLine` с несколькими физическими root-кабелями не получает фиктивную единственную норму. Полевой источник — не щит.
- **Коробки:** `O_box` = число реально разделанных/скоммутированных кабельных концов в `EL_BOX` × норма за конец. **Неразрезанный транзит через `CABLE_TRANSIT` → 0**. Degree узла/наличие box как таковое не доказывает коммутацию.
- **Конечные устройства:** `O_endpoint` начисляется каждому реально оконцованному устройству/концу по норме, в том числе не установленному в подрозетник. Щит и коммутируемый конец коробки не получают дополнительную норму конечного устройства; individual override возможен.
- **Ручное и дополнительные значения:** `L_additional` начисляется один раз абсолютно, не умножается на проценты. `manual_full` полностью **заменяет** auto total без повторных прибавок или округления.
- **Округление:** только один раз для суммарной линии; не округлять `CableSegment` отдельно. `Decimal` и точные кратные `q` не должны добавлять лишний шаг.
- **`В брусе`:** удалена специальная `+0,5 м` за сегмент для ordinary и BUS, в том числе скрытая legacy настройка. Обязательность трубы остаётся.

Действующие object defaults для **новых проектов**:

| Настройка | По умолчанию |
| --- | ---: |
| Вывод из щита | `3,00 м / физический root-кабель` |
| Разделка/коммутация в коробке | `0,20 м / реально коммутированный конец` |
| Физическое оконцевание устройства | `0,30 м / конец` |
| `P_nonlinearity` | `5 %` |
| `P_bypass` | `10 %` |
| `q` | `1,00 м` |

Прежние подтверждённые пользовательские настройки сохраняются при миграции; смена подписей параметров не означает обнуления данных. Реальный live-расчёт должен быть проверен отдельно до объявления PASSED.

## 6. Модель защитной трубы

Кабельная линия, физический сегмент и защитная труба являются разными сущностями.

Назначение в трубу выполняется на уровне `CableSegment`, а не всей ветвящейся `CableLine`.

Один сегмент может быть назначен не более чем в одну трубу. Одна труба может содержать один или несколько совместимых сегментов одной или разных линий, если проектировщик явно принял такое решение.

Для типового случая «один физический кабельный участок — одна отдельная гофра» длина трубы без собственного запаса равна геометрической длине соответствующего сегмента. Вывод из щита, коммуникационные запасы, дополнительные абсолютные длины и индивидуальные ручные поправки кабеля **не входят** в длину трубы.

Сегменты являются топологическими рёбрами между существующими точками, а не свободно редактируемыми route sections. Произвольная полилинейная трасса и отдельный редактор route-section geometry в версии 2.0 не вводятся.

Кабельные каналы, лотки и стальные жёсткие трубы как отдельные несущие сущности отложены. Способ `В кабель-канале` остаётся допустимым, но экземпляр кабельного канала как `conduit` не создаётся.

## 7. Наличие трубы по способу прокладки

| `MOUNT_WAY` | `GOFRA_TYPE` | `GOFRA_ID` | `GOFRA_COLOR` | Результат |
|---|---|---|---|---|
| `По полу` | обязательно | может быть пуст до назначения Project | допускается пустым | защитная труба обязательна |
| `По потолку` | пусто | должно быть пусто | должно быть пусто | открытая прокладка, труба не создаётся |
| `По потолку` | заполнено | может быть пуст до назначения Project | допускается пустым | защитная труба существует |
| `В стене` | обязательно, если кабель должен быть в защитной трубе по проектному решению | может быть пуст до назначения Project | допускается пустым | создаётся/назначается труба при непустом `GOFRA_TYPE` |
| `В брусе` | обязательно; только `ППЛ20` или `ППЛ25` | может быть пуст до назначения Project | допускается пустым | защитная труба обязательна |
| `В кабель-канале` | должно быть пусто | должно быть пусто | должно быть пусто | труба не создаётся |

`В стене` является самостоятельным способом прокладки для сегмента. Вертикальный подход к точке у сегмента `По полу` или `По потолку` остаётся частью соответствующего сегмента и не требует отдельной искусственной вставки.

Для `BUS_MOUNT_WAY=В брусе` `BUS_GOFRA_TYPE` обязателен (`ППЛ20` или `ППЛ25`), а `BUS_GOFRA_ID` может оставаться пустым до назначения Project. Специальной прибавки `+0,5 м` к кабелю BUS нет.

## 8. Тип, цвет и обозначение трубы

`GOFRA_TYPE` и `BUS_GOFRA_TYPE` содержат русское проектное значение типа вместе с каталожным/номинальным размером, под которым выбран тип изделия, например `ПНД25`, `ПВХ20`, `Металлорукав25`, `ППЛ20`, `ППЛ25`, `МПТ16`. Число не должно автоматически трактоваться как внутренний или наружный физический диаметр.

Для машинного суффикса применяются централизованные соответствия:

| Русское значение типа | Латинский код |
|---|---|
| `ПНД` | `PND` |
| `ПВХ` | `PVH` |
| `Металлорукав` | `MR` |
| `ППЛ` | `PP` |
| `МПТ` | `MPT` |

`GOFRA_ID` является видимым проектным обозначением конкретной трубы и имеет формат `NNN.<LATIN_GOFRА_TYPE>`, например `001.PND25`, `003.PVH20`, `006.MR26`. Числовая часть является редактируемым номером трубы. Суффикс генерируется из текущего `GOFRA_TYPE` и отдельно не редактируется.

Русское проектное обозначение полипропилена — `ППЛ`; technical/material code остаётся `PP`. Для `ППЛ20` и `ППЛ25` канонические suffix — `PP20` и `PP25`, соответственно. `PPL` не используется в material code или ID. Старые `ПП20` / `ПП25` не являются каноническими значениями нового ввода и отклоняются текущим validator.

Обычные поля `GOFRA_TYPE` / `GOFRA_ID` и bus-поля `BUS_GOFRA_TYPE` / `BUS_GOFRA_ID` используют один mapping и одинаковую проверку соответствия suffix типу. Примеры: `GOFRA_TYPE=ППЛ25` → `GOFRA_ID=001.PP25`; `BUS_GOFRA_TYPE=ППЛ20` → `BUS_GOFRA_ID=002.PP20`. Несовпадающий suffix блокирует принятие соответствующего поля, в том числе bus-поля.

`МПТ16` поддерживается contract/parser/validation без наличия паспорта или конкретного товара; ID имеет формат `NNN.MPT16`, например `GOFRA_ID=003.MPT16` или `BUS_GOFRA_ID=004.MPT16`. Это правило не утверждает наличие МПТ в equipment catalog и не разрешает выдумывать его товарные характеристики.

Поддержка `ПНД20/ПНД25 → PND20/PND25`, `ПВХ20 → PVH20` и `Металлорукав25 → MR25` сохраняется для обоих наборов полей.

Точный товар трубы выбирается отдельно через общий catalog/passport по совместимости материала, номинального размера и цвета. Для `ППЛ25` / `25` / `синий` утверждён товар DKC 11525 с `material_code=PP`; его артикул поступает в спецификацию из `product_definition`, а не из DWG и не из валидатора. Catalog composition этим изменением не расширяется. Русский prefix в историческом catalog payload не используется как allow-list validator: фактическая совместимость определяется material code, размером и цветом, а canonical DWG input — этим разделом.

Изменение типа или размера при сохранении номера должно изменить суффикс `GOFRA_ID`. Одинаковый непустой `GOFRA_ID` у разных физических сегментов означает назначение этих сегментов в одну физическую трубу. Все сегменты одной трубы должны быть согласованы по `GOFRA_TYPE`, `GOFRA_COLOR` и соответствию суффикса типу.

## 9. Первичный импорт и нумерация

Корректный непустой `GOFRA_ID`, заданный проектировщиком в DWG до первого импорта, должен быть сохранён. Project группирует входящие сегменты с одинаковым `GOFRA_ID` в один экземпляр трубы и не заменяет их назначение автоматической нумерацией.

Project присваивает номер только когда труба требуется или явно задана для сегмента по матрице раздела 7, а `GOFRA_ID` пуст. Следующий автоматический номер равен максимальному числовому префиксу существующих труб объекта плюс один. Пропуски автоматически не заполняются. Пакет новых сегментов обрабатывается в детерминированном порядке topology nodes/segments.

Проектировщик может вручную менять номер. Project не выполняет постоянную перенумерацию и не требует непрерывной последовательности.

## 10. Первоначальная и последующая длина трубы (Q03/Q06, #216)

**Одна физическая труба** может содержать совместимые ordinary `CableSegment` и `BusSegment`. У каждой `Conduit` есть собственная доказуемая геометрия `G_conduit`; объединение по равным длинам, координатам или номеру `GOFRA_ID` без доказательства физических границ **не допускается**.

```text
Conduit_raw   = G_conduit × (1 + P_nonlinearity + P_bypass)
Conduit_auto  = RoundUp(Conduit_raw, q)
Conduit_final = manual_override (если задано), иначе Conduit_auto
```

Физические границы совпадают для неориентированных интервалов `{A,B}` и `{B,A}`. Частичное совпадение трассы требует самостоятельной **реально подтверждённой** границы. Совпадающие coordinates/length/GOFRA_ID не делают один и тот же физический путь автоматически общим. В одной трубе не может быть несовместимых по принятому контракту сегментов.

`Conduit` учитывается **ровно один раз** в длине и спецификации, независимо от числа проложенных в ней ordinary/BUS кабелей. Ни выводы кабеля в щите/box/endpoint, ни дополнительная абсолютная длина кабеля, ни ручная полная длина кабеля в длину трубы не входят. Ручной override трубы сохраняет самостоятельность и не разрешает несовместимые назначения. При неизвестной геометрии `G_conduit` не подменять её случайной суммой, максимумом или длиной одного дочернего сегмента: показать «Требует внимания» до разрешения.

## 11. Объединение, перенос и происхождение

Проектировщик должен иметь возможность назначать сегменты в существующие трубы, переносить сегмент между трубами, изменять свойства и длину трубы, создавать пустую трубу и назначать сегменты в неё.

Автоматически созданная исходная труба удаляется только если после переноса стала пустой. Явно созданная пользователем пустая труба сохраняется до явного удаления.

Решение о совместной прокладке нескольких кабельных сегментов и выборе размера трубы принимает проектировщик.

## 12. DWG и представления Project

`MOUNT_WAY`, `GOFRA_TYPE`, `GOFRA_COLOR`, `GOFRA_ID` синхронизируются как свойства входящего сегмента конкретной topology point/insertion. Для простой одноточечной линии это эквивалентно прежнему line-wide представлению.

`BUS_MOUNT_WAY` использует тот же набор способов прокладки для физического `BusSegment`. Для `BUS_MOUNT_WAY=В брусе` сохраняются ортогональная геометрия и обязательность защитной трубы `ППЛ20`/`ППЛ25`. Исторический кабельный запас `+0,5 м` не применяется ни к BUS, ни к ordinary.

`CABLE_TYPE` и `BOARD` остаются line-wide facts.

Кабельный журнал показывает базовую линию и итоговую длину. Для ветвящейся линии Project должен уметь раскрыть составляющие сегменты и их длины без присвоения сегментам пользовательских `CABLE_ID`.

Принятое представление Q10 «Трассы» — **вариант B**: одна широкая таблица с inline раскрытием `Conduit → CableSegment/BusSegment`, отдельными строками всех сегментов **«Без трубы»**, быстрым фильтром «Требует трубы» и атомарным batch assignment. У сегмента колонка длины показывает **чистую геометрию `G`**, у трубы — **итоговую `Conduit_final`**. В «Линиях» показывается `CableLine_final`. Топологические источники от выбора строки UI не изменяются.

В журнале разбивка по способам прокладки суммирует уникальные физические сегменты. Длины сегментов остаются точной геометрией без объектовых запасов. Подключение в щите, реально коммутированные концы коробок, все конечные оконцевания, процентные запасы, дополнительная длина и полная ручная длина относятся к итогу линии и не распределяются произвольно по отдельным сегментам/способам. Специальной добавки `В брусе` нет.

После принятого изменения DWG-геометрии пересчитываются входящие и исходящие
сегменты затронутой точки, включая реальные BOARD-источники. После канонизации
помещения пересчёт использует только принятые Project facts и существующие
назначения труб: невыбранные изменения DWG не принимаются. Неоднозначная или
частично отсутствующая геометрия общей точки оставляет расчёт неполным.

Явный выбор номера назначает выбранный сегмент в совместимую существующую трубу
либо создаёт пользовательскую трубу. Перенос удаляет опустевшую автоматическую
трубу, но сохраняет пользовательскую. Подтверждённая пользователем длина трубы
не заменяется геометрическим пересчётом.

## 13. Массовое редактирование

Для выбранной группы физических сегментов или труб должно поддерживаться массовое изменение типа/номинального размера трубы в рамках правил controlled bulk operations.

Массовое редактирование не должно создавать конфликтующих свойств у одного экземпляра трубы.
