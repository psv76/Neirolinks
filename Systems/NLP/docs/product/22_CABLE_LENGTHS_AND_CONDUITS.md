# Расчёт длины кабелей и защитные трубы NL Project 2.0

## Актуализация Repair 08

Корень ordinary line задаётся `CABLE_SOURCE` и представляется derived `ROOT_ENDPOINT`; для источника на полевом реле применяется concrete reference `<BUS_POINT_ID>/<PORT>`, например `902.003/K1` или `902.003/K2`. `EL_BOX` — обычная topology point с `BOX_ID=BOX.NNN`, например `BOX.010`; её связи выводятся из `CABLE_SOURCE` дочерних точек, а retired `OUT_*` не является target ATTDEF. DALI/RS-485 route facts хранятся как отдельные physical `BusSegment`; их conduit assignment учитывается ровно один раз и не смешивается с ordinary `CableSegment`.

## 1. Назначение

Документ определяет способы прокладки физических участков кабельных линий, автоматический и ручной расчёт длины, запас у щита, топологию `CableSegment`, модель защитных труб и назначение сегментов в трубы.

## 2. Способ прокладки и физический сегмент

`CableLine` остаётся базовой кабельной линией с одним `CABLE_ID=XYY`. Физическая трасса линии может состоять из одного или нескольких внутренних `CableSegment`.

`CableSegment` — один физический участок кабеля между двумя соседними topology nodes/endpoints. Пользовательский `CABLE_ID` отдельному сегменту не присваивается.

Для каждого сегмента должен быть определён один способ прокладки:

- `По полу`;
- `По потолку`;
- `В стене`;
- `В кабель-канале`.

Для простой линии с одним участком свойства сегмента одновременно являются свойствами всей линии. Для последовательной или разветвлённой линии разные сегменты могут иметь разные `MOUNT_WAY` и разные назначения в защитные трубы.

`CABLE_TYPE` и `BOARD` в текущем контракте остаются едиными свойствами базовой линии. Разные `CABLE_TYPE` на сегментах одной базовой линии не вводятся без отдельного решения.

Высота каждой физической точки задаётся `MOUNT_HEIGHT` от чистого пола.

## 3. Формирование топологии сегментов

Топология сегментов определяется предметной моделью, а не порядком INSERT, Handle или близостью блоков на плане.

Для обычной ветвящейся линии:

- `EL_BOX` имеет `BOX_ID=BOX.NNN`, а исходящие связи определяются `CABLE_SOURCE` дочерних точек;
- ссылка на точку той же базовой линии создаёт один `CableSegment`;
- цикл, двойной родитель, отсутствующая цель и неоднозначный корень запрещены.

Для общей линии выключателей `2YY` с несколькими физическими выключателями порядок `2YY.01 → 2YY.02 → ...` задаётся числовым порядком `.ZZ` от щита.

Для шин используются отдельные правила [23_DATA_BUS_TOPOLOGY.md](23_DATA_BUS_TOPOLOGY.md).

Для простой линии без ветвления и с одной конечной точкой существует один сегмент между физическим источником линии и этой точкой.

Физическим источником первого сегмента может быть щит либо назначенный выходной ресурс полевого устройства. Запас кабеля у щита применяется только к линии, физически начинающейся в щите.

## 4. Расчёт расстояния и высоты одного сегмента

Координаты `X/Y` и `MOUNT_HEIGHT` используются в миллиметрах по [20_AUTOCAD_BLOCK_CONTRACT.md](20_AUTOCAD_BLOCK_CONTRACT.md).

Горизонтальное расстояние рассчитывается параллельно осям:

```text
Lxy_mm = |X2 - X1| + |Y2 - Y1|
```

### 4.1. `По полу`

Используются отметки бетонного основания `B1/B2`:

```text
L_floor =
(
    Lxy_mm
    + |H1 - B1|
    + |B2 - B1|
    + |H2 - B2|
) / 1000
```

### 4.2. `По потолку`

Для высоты чистового потолка `C = R * 1000`:

```text
L_ceiling =
(
    Lxy_mm
    + |C1 - H1|
    + |C2 - C1|
    + |C2 - H2|
) / 1000
```

### 4.3. `В стене`

Участок считается проходящим в плоскости стены между двумя заданными точками. Автоматическая длина:

```text
L_wall = (Lxy_mm + |H2 - H1|) / 1000
```

Если фактическая штроба/обход отличается от такой ортогональной трассы, отклонение учитывается дополнительной или полной ручной длиной.

### 4.4. `В кабель-канале`

```text
L_cable_channel = Lxy_mm / 1000
```

Вертикальные подъёмы, спуски и обходы, не выраженные точками топологии, учитываются ручной корректировкой.

## 5. Автоматическая и итоговая длина линии

Автоматическая длина базовой линии равна сумме длин всех уникальных расчётных сегментов её топологии:

```text
L_auto = Σ L(segment_i)
```

Один сегмент не должен учитываться повторно из-за нескольких представлений или ссылок.

Для кабельной линии поддерживаются:

1. дополнительная длина;
2. полная ручная длина.

Итог:

```text
L_final = L_manual_full
```

если задана полная ручная длина, иначе:

```text
L_final = L_auto + L_additional + L_board_reserve
```

`L_board_reserve` добавляется только если физический источник базовой линии находится в щите. Для линии, начинающейся на полевом устройстве, этот запас не добавляется.

Ручная полная длина заменяет автоматический расчёт всей базовой линии, но не изменяет топологию и не должна неявно менять длины защитных труб.

## 6. Модель защитной трубы

Кабельная линия, физический сегмент и защитная труба являются разными сущностями.

Назначение в трубу выполняется на уровне `CableSegment`, а не всей ветвящейся `CableLine`.

Один сегмент может быть назначен не более чем в одну трубу. Одна труба может содержать один или несколько совместимых сегментов одной или разных линий, если проектировщик явно принял такое решение.

Для типового случая «один физический кабельный участок — одна отдельная гофра» геометрическая длина трубы без собственного запаса равна автоматической длине соответствующего сегмента. Кабельный запас у щита и иные кабельные запасы не увеличивают длину трубы автоматически.

Сегменты являются топологическими рёбрами между существующими точками, а не свободно редактируемыми route sections. Произвольная полилинейная трасса и отдельный редактор route-section geometry в версии 2.0 не вводятся.

Кабельные каналы, лотки и стальные жёсткие трубы как отдельные несущие сущности отложены. Способ `В кабель-канале` остаётся допустимым, но экземпляр кабельного канала как `conduit` не создаётся.

## 7. Наличие трубы по способу прокладки

| `MOUNT_WAY` | `GOFRA_TYPE` | `GOFRA_ID` | `GOFRA_COLOR` | Результат |
|---|---|---|---|---|
| `По полу` | обязательно | может быть пуст до назначения Project | допускается пустым | защитная труба обязательна |
| `По потолку` | пусто | должно быть пусто | должно быть пусто | открытая прокладка, труба не создаётся |
| `По потолку` | заполнено | может быть пуст до назначения Project | допускается пустым | защитная труба существует |
| `В стене` | обязательно, если кабель должен быть в защитной трубе по проектному решению | может быть пуст до назначения Project | допускается пустым | создаётся/назначается труба при непустом `GOFRA_TYPE` |
| `В кабель-канале` | должно быть пусто | должно быть пусто | должно быть пусто | труба не создаётся |

`В стене` является самостоятельным способом прокладки для сегмента. Вертикальный подход к точке у сегмента `По полу` или `По потолку` остаётся частью соответствующего сегмента и не требует отдельной искусственной вставки.

## 8. Тип, цвет и обозначение трубы

`GOFRA_TYPE` и `BUS_GOFRA_TYPE` содержат русское проектное значение типа вместе с каталожным/номинальным размером, под которым выбран тип изделия, например `ПНД25`, `ПВХ20`, `Металлорукав25`, `ППЛ20`, `ППЛ25`, `МПТ16`. Число не должно автоматически трактоваться как внутренний или наружный физический диаметр.

Для машинного суффикса применяются централизованные соответствия:

| Русское значение типа | Латинский код |
|---|---|
| `ПНД` | `PND` |
| `ПВХ` | `PVH` |
| `Металлорукав` | `MR` |
| `ППЛ` | `PP` |
| `МПТ` | `MPT` |

`GOFRA_ID` является видимым проектным обозначением конкретной трубы и имеет формат `NNN.<LATIN_GOFRА_TYPE>`, например `001.PND25`, `003.PVH20`, `006.MR26`. Числовая часть является редактируемым номером трубы. Суффикс генерируется из текущего `GOFRA_TYPE` и отдельно не редактируется.

Русское проектное обозначение полипропилена — `ППЛ`; technical/material code остаётся `PP`. Для `ППЛ20` и `ППЛ25` канонические suffix — `PP20` и `PP25`, соответственно. `PPL` не используется в material code или ID. Старые `ПП20` / `ПП25` не являются каноническими значениями нового ввода и отклоняются текущим validator.

Обычные поля `GOFRA_TYPE` / `GOFRA_ID` и bus-поля `BUS_GOFRA_TYPE` / `BUS_GOFRA_ID` используют один mapping и одинаковую проверку соответствия suffix типу. Примеры: `GOFRA_TYPE=ППЛ25` → `GOFRA_ID=001.PP25`; `BUS_GOFRA_TYPE=ППЛ20` → `BUS_GOFRA_ID=002.PP20`. Несовпадающий suffix блокирует принятие соответствующего поля, в том числе bus-поля.

`МПТ16` поддерживается contract/parser/validation без наличия паспорта или конкретного товара; ID имеет формат `NNN.MPT16`, например `GOFRA_ID=003.MPT16` или `BUS_GOFRA_ID=004.MPT16`. Это правило не утверждает наличие МПТ в equipment catalog и не разрешает выдумывать его товарные характеристики.

Поддержка `ПНД20/ПНД25 → PND20/PND25`, `ПВХ20 → PVH20` и `Металлорукав25 → MR25` сохраняется для обоих наборов полей.

Точный товар трубы выбирается отдельно через общий catalog/passport по совместимости материала, номинального размера и цвета. Для `ППЛ25` / `25` / `синий` утверждён товар DKC 11525 с `material_code=PP`; его артикул поступает в спецификацию из `product_definition`, а не из DWG и не из валидатора. Catalog composition этим изменением не расширяется. Русский prefix в историческом catalog payload не используется как allow-list validator: фактическая совместимость определяется material code, размером и цветом, а canonical DWG input — этим разделом.

Изменение типа или размера при сохранении номера должно изменить суффикс `GOFRA_ID`. Одинаковый непустой `GOFRA_ID` у разных физических сегментов означает назначение этих сегментов в одну физическую трубу. Все сегменты одной трубы должны быть согласованы по `GOFRA_TYPE`, `GOFRA_COLOR` и соответствию суффикса типу.

## 9. Первичный импорт и нумерация

Корректный непустой `GOFRA_ID`, заданный проектировщиком в DWG до первого импорта, должен быть сохранён. Project группирует входящие сегменты с одинаковым `GOFRA_ID` в один экземпляр трубы и не заменяет их назначение автоматической нумерацией.

Project присваивает номер только когда труба требуется или явно задана для сегмента по матрице раздела 7, а `GOFRA_ID` пуст. Следующий автоматический номер равен максимальному числовому префиксу существующих труб объекта плюс один. Пропуски автоматически не заполняются. Пакет новых сегментов обрабатывается в детерминированном порядке topology nodes/segments.

Проектировщик может вручную менять номер. Project не выполняет постоянную перенумерацию и не требует непрерывной последовательности.

## 10. Первоначальная и последующая длина трубы

Для автоматически созданной отдельной трубы одного сегмента первоначальная длина равна автоматической геометрической длине этого сегмента без кабельного запаса у щита.

Если один заранее заданный `GOFRA_ID` относится к нескольким сегментам, Project не должен молча выбирать сумму/максимум/один из сегментов, если по topology facts нельзя доказать длину конкретной физической трубы. Такая длина остаётся незаданной до явного подтверждения проектировщиком.

После явного подтверждения длина трубы становится самостоятельным хранимым свойством и не меняется неявно при изменении кабельной длины.

## 11. Объединение, перенос и происхождение

Проектировщик должен иметь возможность назначать сегменты в существующие трубы, переносить сегмент между трубами, изменять свойства и длину трубы, создавать пустую трубу и назначать сегменты в неё.

Автоматически созданная исходная труба удаляется только если после переноса стала пустой. Явно созданная пользователем пустая труба сохраняется до явного удаления.

Решение о совместной прокладке нескольких кабельных сегментов и выборе размера трубы принимает проектировщик.

## 12. DWG и представления Project

`MOUNT_WAY`, `GOFRA_TYPE`, `GOFRA_COLOR`, `GOFRA_ID` синхронизируются как свойства входящего сегмента конкретной topology point/insertion. Для простой одноточечной линии это эквивалентно прежнему line-wide представлению.

`CABLE_TYPE` и `BOARD` остаются line-wide facts.

Кабельный журнал показывает базовую линию и итоговую длину. Для ветвящейся линии Project должен уметь раскрыть составляющие сегменты и их длины без присвоения сегментам пользовательских `CABLE_ID`.

Представление `Кабельные трассы` использует иерархию `труба → физические сегменты → базовые кабельные линии`. На уровне сегмента показываются его начало/конец, способ прокладки и рассчитанная длина; на уровне линии — `CABLE_ID`, назначение и тип кабеля.

## 13. Массовое редактирование

Для выбранной группы физических сегментов или труб должно поддерживаться массовое изменение типа/номинального размера трубы в рамках правил controlled bulk operations.

Массовое редактирование не должно создавать конфликтующих свойств у одного экземпляра трубы.
