# Контролируемые массовые операции NL Project 2.0

## 1. Назначение

Документ определяет обязательное предметное поведение массовых инженерных операций NL Project 2.0.

Массовая операция переносит одно уже принятое инженером решение на заранее выбранную однородную группу. Она не выбирает инженерное решение вместо пользователя и не создаёт второй источник данных вне Project model.

Правила совместимости конкретных аппаратов, ресурсов, LED-линий, шин и цепей остаются в соответствующих product documents и паспортах оборудования. Настоящий документ определяет только общий контракт планирования и применения массовой операции.

## 2. Обязательный объём 2.0

Controlled bulk automation входит в обязательный объём NL Project 2.0 минимум для действий:

- назначить защиту;
- назначить питание;
- назначить выход или канал;
- назначить вход.

Одиночное и массовое выполнение одного предметного действия должны использовать одинаковые правила совместимости, занятости, проверки и итоговые Project facts.

## 3. Однородный выбор

Массовое действие разрешено только для selection, к которому применимо одно и то же выбранное инженером решение.

Перед preview система должна проверить для каждой выбранной сущности:

- применимость действия;
- достаточность исходных данных;
- совместимость выбранного паспорта, товара или типа ресурса;
- возможность детерминированного назначения;
- отсутствие нерешённого конфликта, блокирующего это действие.

Если selection неоднороден, действие не выполняется. Система должна перечислить несовместимые строки и причину, после чего пользователь изменяет selection. Скрыто делить выбор на инженерные подгруппы запрещено.

Автоматически расширять selection через `select similar` или иной скрытый поиск запрещено.

## 4. Кандидаты и приоритеты

Для выбранного действия система сначала рассматривает существующие ресурсы, которые одновременно:

- физически совместимы;
- удовлетворяют действующим инженерным правилам;
- применимы к текущему действию;
- свободны с учётом exclusivity/capacity;
- не имеют пользовательского состояния `РЕЗЕРВ` по [10_EQUIPMENT_MODEL.md](10_EQUIPMENT_MODEL.md).

Занятый или зарезервированный ресурс не участвует в автоматическом распределении. Он может быть показан отдельно с понятной причиной недоступности.

Last-used preference может изменять только порядок уже допустимых кандидатов. Его правила определены разделом 10 настоящего документа.

## 5. Недостающее оборудование

Если существующих допустимых ресурсов недостаточно, preview должен рассчитать число недостающих экземпляров выбранного инженером паспорта и товара.

Недостающие экземпляры создаются только при подтверждении всей массовой операции. До подтверждения Project model не изменяется.

Создание экземпляра использует правила `EquipmentPassport → Product → ProjectInstance`, копирования, обозначений и materialization из [10_EQUIPMENT_MODEL.md](10_EQUIPMENT_MODEL.md). Массовая операция не имеет права подменить выбранный паспорт или товар другим вариантом.

## 6. Нумерация новых экземпляров

Пользователь задаёт стартовое обозначение или стартовый номер для создаваемой последовательности.

Система должна:

- назначать обозначения только новым экземплярам;
- не перенумеровывать существующие экземпляры;
- не заполнять старые свободные номера молча;
- до применения показать весь создаваемый диапазон;
- выявить каждое совпадение с существующим или другим новым обозначением;
- запретить применение до устранения конфликтов.

Изменение стартового значения пересчитывает preview, но не изменяет Project до подтверждения.

## 7. Детерминированное распределение

После фиксации selection, выбранного инженерного решения, существующих допустимых ресурсов и новых обозначений распределение должно быть детерминированным.

Одинаковые входные данные и одинаковое состояние Project должны давать одинаковый план `выбранная сущность → экземпляр → ресурс`. Технический порядок не должен зависеть от текущей сортировки таблицы, случайного UUID или времени выполнения.

## 8. Preview

До подтверждения пользователь должен видеть полный план:

```text
выбранная линия или сущность
→ существующий или новый экземпляр
→ user-facing label конкретного ресурса
→ создаваемые связи/назначения
→ предупреждения и конфликты
```

Preview должен отдельно показывать:

- использованные существующие экземпляры;
- новые экземпляры и их обозначения;
- ресурсы с доказанными labels;
- пропущенные строки и причины;
- все изменения Project facts;
- итоговое число создаваемых экземпляров, связей и назначений.

Internal IDs и ordinals допускаются в инженерных подробностях, но не заменяют рабочие обозначения и labels.

## 9. Подтверждение, атомарность и результат

Массовая операция применяется только после явного подтверждения preview.

Весь подтверждённый план является одной атомарной Project operation:

- все создаваемые экземпляры, ресурсы, связи, назначения и reservation changes фиксируются целиком;
- ошибка любого элемента отменяет весь Project commit;
- cancel и неуспешная предвалидация не изменяют Project;
- частично применённый результат не считается успешным;
- после commit все зависимые read models и проверки обновляются из одной Project model.

Operation journal должен сохранить тип действия, selection, выбранное инженерное решение, созданные экземпляры, назначения, результат и correlation ID без stack trace в пользовательском представлении.

## 10. Last-used preference

Last-used preference входит в NL Project 2.0 и хранится глобально для пользователя/приложения между объектами.

Preference:

- запоминает последний подтверждённо использованный вариант для данного типа предметного действия;
- ранжирует только уже допустимых кандидатов;
- не создаёт назначение автоматически;
- не изменяет compatibility result;
- не преодолевает занятость, `РЕЗЕРВ`, отсутствие данных или неприменимость;
- не становится Project fact и не переносится в проектный файл как инженерное решение.

Приоритет отбора всегда следующий:

1. физическая совместимость;
2. инженерные правила;
3. занятость и capacity;
4. пользовательский `РЕЗЕРВ`;
5. применимость текущему действию;
6. last-used preference среди оставшихся кандидатов.

Если сохранённый вариант больше не допустим или отсутствует в установленном каталоге, он не показывается как основной кандидат.

## 11. Запреты

Массовая операция не должна:

- скрыто выбирать тип защиты, паспорт, товар, напряжение, схему или иной инженерный вариант;
- использовать занятый или зарезервированный ресурс;
- переносить связи или занятость копируемого экземпляра;
- изменять существующие обозначения;
- применять только успешную часть плана;
- скрывать конфликт либо заменять неизвестное значение нулём;
- показывать технический ordinal вместо доказанного label.
