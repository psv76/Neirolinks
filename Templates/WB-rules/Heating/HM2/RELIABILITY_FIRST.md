# HM2 — приоритет сохранения отопления (решение #51 / #52)

Статус: согласованный принцип для новых реализаций; объектный выпуск Исети требует отдельной проверки перед установкой. Этот текст **заменяет противоречащие предписания** `SOURCE_AND_RESPONSE_CONTRACT.md`, прежде всего §§ 2, 6, 11–13, где отсутствие температурного отклика само по себе трактуется как опасная авария, `fault_latched=true`, invalid demand и отключение. Действительные аварии котла, перегрев, давление, безопасный гидравлический путь и единственный writer **не отменяются**. Общий контракт следует исправить при следующей полной редакции, не внедрять обе политики одновременно.

1. При устранимом сбое датчика, связи или диагностического контроля сохранять работу независимых исправных отопительных контуров. После восстановления входа — автоматический возврат, без ручного подтверждения уведомления. OFF не универсальное безопасное состояние дома зимой.
2. `NO_RESPONSE` при заданном ΔT/времени — **предупреждение**. Температурный тренд сам по себе не измеряет проток и не доказывает опасность работы насоса. Не создавать по нему latched fault и не запрещать арбитраж; временная нехватка нагрева требует диагностики и информирования.
3. При потере отдельного комнатного датчика не лишать тепла прочие комнаты; при потере наружного датчика после достоверного чтения допустимо удерживать последнюю корректную наружную температуру для погодной кривой. При холодном старте или потере всех датчиков резервные уставки должны быть подтверждены на объекте, не выдуманы.
4. Смесительный контур: на недостоверной подаче прекратить расчёт PID по ложному значению. Вариант удержания последней команды клапана допустим лишь при подтверждении предела температуры теплоносителя и существующей защиты. Иначе оставить локальную ранее проверенную защиту; не гасить остальные контуры.
5. Разделять состояние реальной безопасности и диагностику эффективности. Настоящее опасное состояние должно отключать только затронутое оборудование, если иное не требуется самой физической схемой.
6. Не множить virtual devices, MQTT-флаги, защёлки и состояния ради отображения нюансов. Для инженера важны рабочая команда, реальная причина остановки, источник управления и журнал смены состояния. Один физический канал — один writer.

**Объектные параметры** (адреса, насосы, 26 °C паркета, таймеры, наружная кривая, лимиты котла) остаются исключительно в объектном конфиге и не переносятся между Исетью и Иволгой. Тесты на модели не равны проверке реальной гидравлики. Ввод на объекте — только после резервной копии, проверки фактических выходов и отдельного разрешения инженера.
