# Карта зональных термостатов — 05 31 Иволга 13

Статус: **рабочая инженерная карта, 2026-09-07**.

Этот документ фиксирует, **какой тип термостата нужен каждой зоне, какие датчики он использует и каким физическим исполнительным каналом управляет**. Документ не является исполняемым кодом.

Основные источники истины:

- `PHYSICAL_CHANNEL_MAP.md` — фактические датчики и исполнительные каналы объекта;
- `Templates/Sprut/Heating/README.md` — принятые типы `simple / combo / climate`;
- `Templates/Sprut/Heating/NL_simple_thermostat.json` и `NL_combo_thermostat.json` — MQTT-контракт со Sprut.hub.

---

## 1. Где живёт логика

**Wiren Board — владелец логики зонального отопления.**

Wiren Board:

- читает физические датчики;
- хранит уставки;
- считает гистерезис и состояние зоны;
- формирует команду нагрева;
- управляет физическим сервоприводом/клапаном;
- логирует решения и ошибки;
- формирует виртуальное MQTT-устройство `NL_*_thermostat_XXX`.

**Sprut.hub — пользовательский интерфейс.**

Sprut.hub:

- показывает температуру и состояние;
- позволяет менять уставку;
- позволяет включать/выключать термостат;
- для `combo` показывает температуру пола и дополнительные уставки пола.

Критичная отопительная логика в сценарии Sprut.hub не переносится.

## 2. Типы термостатов

| Тип | Когда применяется | Датчики | Команда нагрева |
|---|---|---|---|
| `NL_simple_thermostat` | Один температурный датчик и одна команда нагрева | один датчик: воздух **или** пол | один исполнительный выход |
| `NL_combo_thermostat` | Отопление тёплым/горячим полом, есть воздух + пол | воздух + пол | один итоговый сигнал нагрева зоны |
| `NL_climate_thermostat` | Есть отопление и охлаждение | воздух + пол + климатические данные | нагрев + охлаждение |

На Иволге `climate` на текущем этапе **не требуется**.

### 2.1. Логика COMBO

`NL_combo_thermostat` — каскадный термостат:

```text
температура воздуха
        ↓
сравнение с уставкой помещения
        ↓
выбор цели температуры пола
        ↓
температура пола
        ↓
открыть / закрыть сервопривод зоны
```

Принцип:

```text
если воздух ниже уставки:
    цель пола = "Пол при нагреве"

если воздух в норме:
    цель пола = "Пол при поддержании"

сервопривод регулируется уже по температуре пола
относительно выбранной цели
```

MQTT-устройство WB:

```text
NL_combo_thermostat_XXX
```

Основные controls:

```text
air_temperature
floor_temperature
target_temperature
target_state
current_state
floor_min_temperature
floor_max_temperature
```

Штатные значения шаблона Sprut для дополнительных настроек пола сейчас: `25 °C` «Пол при поддержании» и `29 °C` «Пол при нагреве». Это **значения шаблона, а не утверждённые уставки Иволги**.

### 2.2. Логика SIMPLE

`NL_simple_thermostat`:

```text
один датчик температуры
        ↓
сравнение с уставкой + гистерезис
        ↓
один сигнал нагрева
```

Датчиком может быть как воздух, так и пол. Поэтому SIMPLE подходит, например, для радиатора с датчиком воздуха или для зоны пола, где отдельного датчика пола нет и принято регулировать по воздуху.

MQTT-устройство WB:

```text
NL_simple_thermostat_XXX
```

Основные controls:

```text
temperature
target_temperature
target_state
current_state
```

## 4. Что уже можно создавать без догадок

### COMBO

```text
601 Мастер спальня
604 Гостевая спальня          [временно по текущему WebUI]
605 Кабинет                   [временно по текущему WebUI]
606 Прихожая
609 Ванная
612 Гостиная
613 Кухня
614 Мастер ванная
```

`607` технически имеет полный набор `воздух + пол + выход`, но сначала нужно снять неоднозначность названия/физической зоны.

### SIMPLE

```text
603 Мастер гардероб           [подтвердить регулирование по воздуху]
608 Гардероб прихожей         [подтвердить канал]
610 Постирочная               [по воздуху]
615 Кладовка                  [по воздуху]
620 Радиатор прихожая         [по воздуху]
621 Радиатор гостевой         [временно по текущему WebUI]
```

### Не создавать до уточнения

```text
602 Мастер тамбур
611 Коридор
```

## 5. Две зоны с двумя отопительными приборами

### Прихожая

Есть:

- `606` — горячий пол: COMBO `воздух + пол`;
- `620` — радиатор: SIMPLE по тому же датчику воздуха `902.05_MSW_THM/Temperature`.

### Гостевая спальня

Есть:

- `604` — тёплый пол: COMBO `воздух + пол`;
- `621` — радиатор: SIMPLE по тому же датчику воздуха `902.10_MSW_TH/Temperature`.

На текущем этапе это следует считать **двумя отдельными исполнительными контурами в одной комнате**. Перед production-кодом нужно отдельно решить, должны ли их пользовательские уставки быть независимыми или синхронизированными. Не объединять оба выхода в один COMBO автоматически: текущая логика COMBO формирует итоговую команду по температуре пола, поэтому прямое включение радиатора в тот же `valveTopics` изменит смысл регулирования радиатора.

## 6. Правило нумерации виртуальных устройств

Номер термостата наследуется от проектного номера исполнительного канала:

```text
601 -> NL_combo_thermostat_601
603 -> NL_simple_thermostat_603
609 -> NL_combo_thermostat_609
620 -> NL_simple_thermostat_620
```

Для неопределённых зон виртуальное устройство не создавать до подтверждения физической привязки.

---

## 7. Следующий шаг

Перед написанием production-скрипта закрыть четыре вопроса:

1. какой датчик относится к `602 Мастер тамбур`;
2. какой датчик относится к `611 Коридор`;
3. подтвердить, что `607 A13/K2` — это именно санузел прихожей;
4. подтвердить физически `604/605/621` после истории перестановки гостевой спальни и кабинета.

После этого формируется WB-скрипт с `NL_combo_thermostat_*` и `NL_simple_thermostat_*`, затем проверяются Sprut-шаблоны и только после DISCOVER термостаты добавляются в YAML Configurator.
