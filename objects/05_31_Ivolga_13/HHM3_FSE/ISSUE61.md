## Проверенный API и доказательство

Изучен исходный тег [v2.40.0](https://github.com/wirenboard/wb-rules/tree/v2.40.0),
commit `5eb62b848129a5736b9a816d7d2ffe594643451b`:

- [engine.go / newTrackHandler](https://github.com/wirenboard/wb-rules/blob/5eb62b848129a5736b9a816d7d2ffe594643451b/wbrules/engine.go#L1964):
  callback получает объект ровно с `topic` и `value`. MQTTMessage не передаётся JS целиком;
  `retained` и `qos` не экспортируются. Сериализованная модель — tests/wb240-callback.js.
- [DefineMqttTracker](https://github.com/wirenboard/wb-rules/blob/5eb62b848129a5736b9a816d7d2ffe594643451b/wbrules/engine.go#L1927):
  подписка создаётся для первого tracker темы, удаляется после удаления последнего.
  Перезагрузка скриптов/порядок создания trackers могут пересоздавать подписки.
- [rule.go / CellChangedRuleCondition.Check](https://github.com/wirenboard/wb-rules/blob/5eb62b848129a5736b9a816d7d2ffe594643451b/wbrules/rule.go#L134):
  внутренняя информация IsRetained существует, но не становится полем callback trackMqtt.
  whenChanged фильтрует часть начальных/повторных событий; это не универсальный канал ACK.

Два допустимых входных сценария после отправки OFF:

1. Запись не дошла до устройства, после переподписки пришёл старый retained Switch=0.
2. Запись дошла, после неё пришла новая публикация Switch=0.

Оба дают JS `{topic: "…/Switch", value: "0"}`. Можно выбрать одинаковое время доставки
и любое число повторов в обоих сценариях. Поэтому счётчик callback, локальное время,
sleep, «второе одинаковое сообщение» и чтение dev не различают эти сценарии.
Принятие второго как нового доказательства без дополнительного наблюдаемого признака
также принимает первый. Это невозможно исправить чистой заменой JS над этим API.
Аналогично для Level, насоса, температур и метаданных. Запись dev не является Modbus-ACK.

Это доказательство ограничения **штатного JS API**, а не утверждение о невозможности
внешнего MQTT-reader. Задание допускает его разработку; отсутствие готового,
проверенного дополнительного транспорта — оставшийся программный блокер, не новая
просьба о разрешении уже согласованной разработки и не только аппаратная ПНР.

## Изменения этой ревизии

- Runtime.io.compatible проверяет наличие поддерживаемой формы MQTT metadata и отсутствие
  обнаруженной неподдерживаемой формы. До первого доказательства API включение запрещено.
  На 2.40 флага нет никогда, поэтому квалификация не наступит даже от реального live-трафика.
- 500/620 при неизвестном/неподдерживаемом API не запрашивают насос ON, Level или зональный ON.
  Для ранее введённой системы остаются только попытки OFF; source writer удержан. До
  FIRST_COMMISSIONING физических writes по-прежнему нет. Ложного подтверждения OFF нет.
- Unsupported сохраняется в экземпляре sensor/receiver; последующий случайный boolean false
  не снимает его. seq больше не растёт после такой дисквалификации. Это не synthetic ACK.
- Снятие meta/error квалифицируется в обоих WB; неизвестный flag диагностируется и здесь.
- Профиль harness 2.40 удаляет retained/qos **для всех** callback: датчиков, записей,
  frame, bridge и error. Никакого скрытого флага от модели не передаётся.
- Алгоритмы температурных лимитов, карта, собственники, настройки, 562 max50,
  числовой NO_DEMAND=0 и source.noDemandMode='unconfirmed' сохранены. Нет новых служб.

Потеря свежести отдельного датчика при API с корректной metadata по-прежнему локальна;
общая блокировка включения относится к недоказанному API данного скрипта, а не к обычному
локальному отказу датчика. Реальный OFF при недоступном брокере/приводе гарантировать нельзя.

## Необходимый внешний транспорт: отдельный незакрытый AC

Предпочтительное направление — локальный read-only MQTT-reader на каждом WB, отдельный
чистый сеанс MQTT, с проверенным клиентом, экспортирующим фактический broker retain flag.
Например, официальный [mosquitto_sub](https://mosquitto.org/man/mosquitto_sub-1.html)
умеет JSON `%j` с retain. Это лишь исходный primitive: `%j` или `-R` сами по себе
не решают перезапуски, очереди, потерю данных и корреляцию readback с командой.

Простой republish payload + retained=false **не подходит**: retained оригинала теряется;
даже envelope с retain может быть повторно доставлен из кэша уже другого topic. Нужны:

1. Проверяемое происхождение: точные разрешённые исходные темы, исходный retain flag,
   идентификатор boot/connection, возрастающий cursor без пропусков; отдельная ошибка при
   переполнении/потере событий. Не копировать /devices и не создавать новых writers.
2. Доставка reader → JS, которая не принимает старый envelope после reconnect/restart.
   Если MQTT — challenge текущего получателя, изоляция публикации и защита от replay;
   если локальный IPC — права файлов/socket и явные гарантии атомарности/очереди.
3. Барьер относительно конкретной записи: сообщение, наблюдённое reader ДО команды,
   но задержавшееся до JS ПОСЛЕ команды, не является свежим подтверждением. Проверяемая
   временная/каузальная привязка, а не увеличение счётчика по приходу envelope.
4. Полный порядок Switch событий: промежуточный OFF нельзя потерять при объединении
   нескольких сообщений в snapshot. Иначе ретаргетинг ошибочно сохраняет прежний ON.
5. Disconnect/reader restart/overflow/clock anomaly немедленно или в обоснованном bounded
   интервале снимают квалификацию; после восстановления никакого reuse старого ON/ACK.
   Истечение TTL должно отсчитываться от исходного наблюдения, не повторной выдачи кэша.
6. Отдельный полный пакет: исполняемый файл, закреплённые зависимости/версии и лицензии,
   конфиг каждого WB, service unit/пользователь, exact read-only ACL, health/логирование,
   процедура установки и rollback без изменения других служб/ACL/политики outputs.
   Никакие listener, пароль, права или установленный mosquitto-clients не предполагаются.
7. Изолированные тесты настоящего MQTT-клиента с брокером плюс VM точного API 2.40:
   retained, порядок, queues, restart, разрыв соединения, часы, repeated OFF без ACK,
   первый Level+ON, ретаргетинг Level без повторного ON, все пять контуров и оба WB.
   До прохождения этих AC нельзя снижать MIN_VERSION и объявлять SOFTWARE_READY.

Такой reader/bridge **не добавлен**. Не поставлены фиктивные systemd unit, зависимости
или инструкции его запуска. INSTALL/KEEP/DELETE для текущих файлов сохранены под
общей блокировкой. Следующий конкретный программный результат — этот пакет и доказательство
AC 1–7; аппаратной проверкой нельзя заменить его разработку. Разрешение на разработку
в scope #61 уже есть; на установку/изменение живых WB его нет.
