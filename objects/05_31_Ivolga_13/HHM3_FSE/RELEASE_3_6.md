# HHM 3.6 — выбег всех насосов и доработка operator journal

Основание: #69, #81 и live-проверка HHM 3.5 на Иволге 29.09.2026.

## Подтверждённые факты live 3.5

- 501 выключал насос без 120-секундного выбега; это соответствует конфигу 3.5 `pumpPostrunMs=0` и не является ошибкой восприятия оператора.
- 502 выполнял 120-секундный выбег.
- 504 выполнял 120-секундный выбег.
- неизменная команда Heating Setpoint=40 попала в operator journal повторно примерно через 30 секунд.
- команда/подтверждение перехода котла в «Ожидание» записывались коротко и однократно.
- оператор визуально наблюдал реальный переход «Ожидание → Зима ЦО + ГВС» после изменения уставок термостатов. В конкретном WebUI-export эта строка отсутствовала; это наблюдение подтверждает переход режима, но не доказывает наличие конкретной строки журнала.
- сам WebUI/System Journal export имеет отдельные дефекты: повтор блоков и управляющие байты.

## Выбег насосов

В 3.6 объектный контракт Иволги задаётся явно для всех пяти насосов:

| Контур | Насос | Выбег |
| --- | --- | ---: |
| 501 | A03/K1 | 120 с |
| 502 | A03/K2 | 120 с |
| 503 | A03/K3 | 120 с |
| 504 | A03/K4 | 120 с |
| 505 | A03/K5 | 120 с |

Для 501–503 зональные НЗ-приводы имеют проектное время полного хода 180 с, поэтому выбег 120 с завершается раньше расчётного полного закрытия последнего привода. Для 504/505 зонального привода на самом контуре нет; выбег остаётся конечным 120 с.

Direct-контуры теперь выполняют postrun и при `zoneActuatorOpenMs=0`, если `pumpPostrunMs>0`. Это необходимо для 505. Для 504 активный postrun теперь имеет операторское состояние `PUMP_POSTRUN` / «Выбег насоса», а не вводящее в заблуждение `NO_DEMAND` при фактически включённом насосе.

Аварийные/неопределённые состояния по-прежнему имеют приоритет: перегрев, output fault, небезопасный degraded state и отсутствие валидной группы не удерживают насос только ради выбега.

## Operator journal

### Heating Setpoint

Физическая reassert-запись той же уставки может выполняться технически, но она не является новым операторским событием.

Последнее операторски зафиксированное значение Heating Setpoint хранится в `PersistentStorage('hhm3_operator_log')`. Поэтому одинаковая техническая reassert-запись не создаёт новый `BOILER_SETPOINT_COMMAND`.

После reload/restart сохранённое значение также используется как исходное состояние dedup. При этом реальные промежуточные переходы запроса не скрываются: если в ходе повторной квалификации датчиков источник законно проходит, например, `35 → 45`, обе разные уставки остаются операторскими событиями. После стабилизации повторные записи неизменных 45 °C снова подавляются.

При изменении значения новая команда журналируется.

### Boiler Mode

Контракт 3.5 сохраняется:
- один `BOILER_MODE_COMMAND_STANDBY` до readback 0;
- один `BOILER_MODE_COMMAND_HEATING` до readback 1;
- подтверждение readback отдельной строкой;
- затем Heating Setpoint.

## Что не меняется

- алгоритм регулирования смесителей;
- Current Boiler Mode contract 0/1;
- порядок mode=1 → readback → Heating Setpoint;
- Sensor Health;
- thermal protection;
- MAO4 Switch/Level contract;
- единоличное ownership физических выходов;
- 180-секундная квалификация открытия зон 501–503;
- NLI transaction/rollback contract.

## Acceptance

1. 501–505 после последнего штатного demand удерживают насос ровно 120 с.
2. На 115-й секунде насос ещё ON; на 120-й — OFF.
3. Новый demand во время postrun отменяет останов без бессмысленного OFF/ON.
4. Перегрев/output fault прерывает postrun безопасно.
5. Неизменная reassert-запись Heating Setpoint не создаёт повтор operator event.
6. Изменившийся Heating Setpoint создаёт новый operator event.
7. После restart реальные изменения уставки журналируются, а последующие одинаковые reassert-записи снова подавляются.
8. 501–503 по-прежнему создают start/finish operator events 180-секундного ожидания открытия зоны.
9. Полный HHM3 CI и NLI CI — green.
