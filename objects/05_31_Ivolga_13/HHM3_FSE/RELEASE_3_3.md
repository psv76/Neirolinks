# HHM 3.3 — исправление полевой регрессии A05 readback

Основание: Issue #81, полевой тест boiler WB `wirenboard-ABF62SL` 28.09.2026.

## Наблюдение

После штатного обновления NLI 0.1.9 с HHM 3.1 на approved HHM 3.2 насос
смешивающего контура 502 во время устойчивого нагрева периодически получал
краткий OFF, затем снова ON. В журнале тот же механизм виден и для 501.

Полевой rollback `3.2 -> 3.1` прошёл штатно; после возврата 3.1 дёрганье
насоса прекратилось.

## Причина

В 3.2 новый контракт MAO4 требовал свежий `Dimming Level` и `Switch`
readback не только после новой команды, но и на каждом steady-state цикле.
Общий runtime readback использует sensor TTL 120 s. Если неизменившийся A05
не публиковал новое значение за этот срок, `io.readback()` возвращал
`value=null` при неизменившемся sequence. Это ошибочно запускало
`WAIT_OUTPUT_READBACK`, затем `ENABLE_UNCERTAIN` и безопасный OFF насоса.

Истечение TTL без нового sequence не является новым противоречащим readback.

## Исправление 3.3

- fresh Level/Switch остаётся обязательным после каждой новой команды открытия;
- после подтверждения steady HEAT отсутствие новых A05 событий не снимает READY;
- более свежий противоречащий Level/Switch запускает повторное согласованное подтверждение;
- подтверждённый OFF сохраняется без heartbeat, но свежий последующий ON запускает bounded OFF retry;
- существующие command timeout/retry и fail-safe OFF не ослаблены.

## Логирование

В полевом расследовании обнаружено, что часть HHM 3.2 нарушает принятый
стандарт #44/#69: M1W2 transition печатался как сырой JSON, а mixed-output
transition содержал технические `true/false`, JSON readback и недостаточно
понятную оператору структуру.

В 3.3:
- M1W2 LOST/RECOVERY выводятся русским текстом с кодом, причиной, температурой,
  Sensor OK, ошибками и действием системы;
- таймеры, решения, ошибки и выходные переходы получают отдельный понятный тип события;
- mixed-output transition показывает расчёт, команду насосу, попытки записи,
  readback Level/Switch/насоса, saved Level и границы доказанности без JSON-мусора;
- технические machine codes сохранены для grep/tests;
- стабильные состояния по-прежнему подавляются и не пишутся каждый цикл.

Полный observability-аудит #69 остаётся отдельной задачей; 3.3 закрывает
конкретные нарушения, обнаруженные при этом полевом дефекте.

## Regression

Добавлены/обновлены сценарии:
- steady HEAT переживает >120 s без нового A05 readback без команды OFF насосу;
- подтверждённый OFF переживает TTL без ложного повторного закрытия;
- свежий противоречащий readback по-прежнему требует нового подтверждения;
- transition logs не содержат raw JSON и имеют русскую операторскую интерпретацию;
- M1W2 health LOST/RECOVERY журналируются один раз на переход понятным текстом.

## Версия и публикация

Опубликованный `nli-approved-hhm-3.2` не изменяется: approved asset/manifest
остаётся неизменяемой историей. Следующий исправленный выпуск — **HHM 3.3**,
без третьей цифры версии, с новым immutable runtime commit R, новым manifest
commit M и новым unique approved tag. NLI остаётся 0.1.9.

NLI сравнивает версии численно и выбирает максимальную доступную approved
версию для совпадающих component/object/role. При одновременно опубликованных
3.2 и 3.3 должен быть выбран 3.3.

Сначала повторный boiler live test: устойчивый 502 должен отработать дольше
старого 120 s TTL без `ENABLE_UNCERTAIN` и без `A03/K2=false`. Беседка
обновляется только после этой проверки.
