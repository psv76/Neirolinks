# HHM3 Иволга — контролируемое обновление котельной

**Не является командой на установку.** Действующий контроллер уже введён в эксплуатацию, поэтому новый `start_heating` нажимать нельзя. Проводить замену только в согласованное окно после проверки состояния подпитки 507: `pressure_makeup` не активна, клапан A04/K1 закрыт, нет аварии давления. Перезапуск `wb-rules` влияет и на 507; его работа и текущая гидравлическая ситуация должны быть проверены до и после. Не менять MQTT, OT, беседку, Sprut, параметры насоса/клапана вручную ради этой замены.

## Предварительные условия

1. Сверить фактический SHA-256 текущих `500_HHM3_FSE.js`, `HHM3Outputs.js`, `HHM3Circuit.js`, сохранить их побайтовые копии с правами в отдельный каталог `/root/hhm3_rollback_YYYYMMDD_HHMM/`. Сохранить только копии файлов, не удалять каталоги или PersistentStorage. Если хотя бы один установленный файл отличается от ожидаемого состояния PR #60 / первоначального PR #63 — остановиться, сначала сравнить изменения.
2. На машине подготовки выполнить `node tests/run.js`, `node tests/persistent-storage-regressions.js`, `node tests/manifest.js --check` именно из каталога распакованного выпуска. Сверить `manifest.json`, размеры, оригинальные пути, `wb-rules` котельной (при последней проверке 2.46.5, подтвердить заново), состояние сети и доступность беседки. Исторический запрет из ISSUE61 касается 2.40, не версии 2.46.5.
3. Проверить работоспособность температурных датчиков и наличие независимого пути для безопасной работы насоса с закрытым горячим портом при защитной рециркуляции. Не предполагать его на основании одного MQTT switch. До этого защитные сценарии необходимо принимать под наблюдением инженера.

## Состав обновления — только котельная

| Файл из выпуска | Назначение |
|---|---|
| `modules/HHM3Outputs.js` | `/etc/wb-rules-modules/HHM3Outputs.js` |
| `modules/HHM3Circuit.js` | `/etc/wb-rules-modules/HHM3Circuit.js` |
| `boiler/wb-rules/500_HHM3_FSE.js` | `/etc/wb-rules/500_HHM3_FSE.js` |

Остальные файлы используются для полной воспроизводимой сборки и регрессий, **не копировать их на работающие контроллеры** как часть данного обновления. `620_thermostats.js`, `507_Pressure_makeup.js`, котёл/OT, `624_combo_besedka.js`, ACL, MQTT и настройки датчиков не менять. Обновлять файлы атомарно: подготовить временные копии в соответствующей файловой системе, сверить SHA-256 из манифеста, переименовать на место только в согласованное окно; запустить `wb-rules` штатно. До окна иметь немедленно доступные исходные файлы для отката.

## Проверка после согласованной установки

1. `wb-rules` активен, нет исключений, сохранились 18 пользовательских термостатов и 505 OFF (если его отдельно не включали). Проверить 507, A04/K1, давление и доступность WB. Не запускать повторно первичную ПНР.
2. В WebUI устройство HHM3 показывает краткие состояния 501–505 и котла; внутренние JSON не видны как элементы управления, но остаются в MQTT. Фактическое отображение `hidden` нужно проверить на установленной версии WebUI. Статус «команда принята» не трактовать как подтверждение движения механизма.
3. Перед любым включением согласовать безопасное окно, подтвердить наличие протока и возможность быстро остановить контур. На одном контуре проверить последовательность **обычный Level → явный Switch ON → насос ON**, фактический Switch, напряжение/ход клапана и изменение температуры подачи. Не включать одновременно три клапана на 100 %, не выводить из одного статуса HEAT_COMMANDED физический прогрев. Повтор неизменного MQTT readback не должен вызывать ложный цикл `OPEN_READBACK_TIMEOUT → OFF`. Проверить остальные 560/561/562 и штатные температурные защиты без опасного нагрева. При непредвиденном закрытии/нагреве/отказе — прекратить ПНР и вернуть исходные три файла.
4. Отдельно проверить 504 `FLOOR_SENSOR_INVALID`; при общем нулевом спросе режим выключения **только отопления** с сохранением ГВС остаётся неподтверждённым (`noDemandMode='unconfirmed'`). Подтверждённый выбор `ch_enable` либо `setpoint_zero` — отдельное изменение с собственной ПНР, не часть данного исправления.

## Откат

В контролируемое окно вернуть сохранённые исходные **ровно три файла** из каталога бэкапа на прежние пути, сверить их исходные SHA-256, штатно перезапустить `wb-rules`, проверить насосы/клапаны, котёл, 507 и пользовательские уставки. Не чистить PersistentStorage и не нажимать `start_heating`. Если подпитка активна, перед перезапуском нужно обеспечить её безопасное управление на объекте; не отключать вслепую общую службу.

**Приёмка производства:** успешные GitHub CI и тесты подтверждают программную сборку. Фактические насосы/подмесы/отключение CH, 504, отображение WebUI и реакция на реальные отказы требуют отдельного протокола объекта, которого данный выпуск не создаёт автоматически.

## Полевое обнаружение 22.09.2026 (после выпуска 45ac439)

Фактически зафиксировано: A05 Switch каналов 1–3 = 0 при Level 100/100/74–98; насосы K1–K4 = 1, источник ≈42 °C, подачи смешанных контуров ≈17–18 °C. Исходный алгоритм 45ac439 ошибочно предполагал авто-включение **обычного** Level. Исправление explicit Switch ON существует только как новый кандидат и требует полного CI, нового пинованного SHA и контролируемой ПНР на одном контуре. Выпуск 45ac439 **не считать физически принятым**. При отсутствии фактического протока обеспечить безопасный режим на объекте; не включать горячие порты при Level 100 % вслепую.
