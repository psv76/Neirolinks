## Архитектура и ownership

`620_thermostats.js` владеет только зональными выходами A08/A09/A13/A14 и формирует локальный frame v3 четырёх групп. 19 термостатов: 18 прежних домовых и новый 505. Воздушный 505 первоначально OFF, 20 °C, 15–28 °C, гистерезис 1 °C; насосом занимается только manager, без задержки приводов. ON/OFF и уставки сохраняются. Гостиная 010 и её датчик не переназначены.

`624_combo_besedka.js` на отдельном WB формирует wire v2 504: воздух выбирает цель пола; HEAT без OFF, пол максимум 30 °C. Физических writers нет. GazeboPanel остаётся прежним.

`500_HHM3_FSE.js` содержит пять managers, арбитр и source manager. Каждый manager владеет своим насосом и, где есть, смесителем. Арбитр только вычисляет MAX; порядок при равенстве 503, 502, 501, 504, 505. Source — единственный writer Heating Setpoint; Master CH enable используется исключительно при подтверждённом режиме ch_enable. 506, 507 и ГВС не входят в allowlist.

Один первоначальный ввод всего комплекта сохраняется в hhm3_operation.inService. После reboot/возврата питания и свежих данных повторного клика не требуется. Это не эксплуатационный grant каждого контура. До первоначального ввода отопительных физических writes нет; действующие неотопительные службы продолжают работу.

## Свежесть и восстановление

Датчик достоверен по свежей non-retained MQTT-публикации (120 с), при отсутствии meta/error и допустимом числовом значении. Пустые/null/boolean/NaN не подменяются нулём. Для frame нужны session/seq, TTL 30 с, ограничение рассинхронизации 2 с и подтверждение продвижения отправителя. retained не продлевает свежесть. Неизвестный retained у runtime явно диагностируется: необходим wb-rules >= 2.42.0. Заявки арбитра TTL 15 с. После разрыва или скачка часов повторяется квалификация свежести, но не требуется ручное разрешение.

При потере WB/LAN беседки 504 регулирует локальную подачу на 30 °C; штатно 35 °C, предел рабочей уставки 40 °C. Без 418 используется свежий пол с шагом 1 %/мин и пределом 50 % логического хода. Без обеих обратных связей задаётся закрытие горячего входа, рециркуляция сохраняется после совпадения readback выходов, NO_FEEDBACK_UNCOVERED явно сообщает непокрытый риск. Возврат датчиков восстанавливает штатный режим автоматически.

Домовой frame не является общим veto: при его потере manager использует сохранённый пользовательский ON и свежие состояния зональных реле, учитывая время открытия 180 с. Для 505 приводов нет. При потере воздушного датчика включённая зона сохраняет ограниченный запрос; при потере датчика пола соответствующая зона закрывается, исправные продолжают работу. Для 501/502 резерв без датчика подачи не разрешает открывать горячий вход (floorOnlyMaxPct=0); это локальное ограничение, не авария соседних контуров.

Защиты смешанных контуров используют сырые свежие температуры, запоминают перегрев через restart, закрывают горячий вход, затем при подтверждённом продолжающемся перегреве останавливают только свой насос. Для 504: подача 45/48/50 °C, пол 31/33 °C; охлаждение с гистерезисом, 120 с устойчивости и новая выборка, далее 60 с проверки циркуляции. В конфиге отдельно заданы стартовые пороги 501/502. NO_RESPONSE, холодный источник — предупреждения без бессрочной защёлки.

Источник теряет право новых writes при недостоверном 411/OT, но не выключает насосы соседей. Возврат свежих исправных данных автоматический. При перегреве 411 действуют аппаратные защиты котла; программный source не выдаёт новые нагревательные команды до охлаждения. Программный запрет записи сам по себе не отменяет прежнюю физическую уставку.

Достоверное отсутствие спроса всех потребителей даёт строго числовой 0. Недоступная заявка не считается доказанным отсутствием спроса. По умолчанию noDemandMode=unconfirmed: физическая команда OFF неизвестна, состояние NO_DEMAND_ACTION_UNCONFIRMED. Реализованы варианты setpoint_zero и ch_enable для выбора только после проверки на конкретном котле; скрытой уставки 42 °C нет. last_written/command_sent — команда программы, не подтверждение движения привода, протока или погасшей горелки.

## Единый контракт A05 MAO4

Главный источник — [задание 5749874727](https://github.com/psv76/Neirolinks/pull/60#issuecomment-5749874727). Владелец сообщил общую семантику всех каналов A05: OFF закрывает командный выход, сохраняя Level; ON восстанавливает сохранённый Level; ненулевой Level может AUTO-ON. Не требуется выяснять номер канала для программного контракта. Физическое испытание 20/ON → 20/OFF → 20/ON было на неназванном канале; оно не записывается как индивидуальная проверка остальных приводов или их герметичности.

20.09.2026 23:27 +05 на A05 Channel 1 / 560 владелец проверил без HHM3 и при K1 OFF: Level20 → 20/ON; только Level40 → 40/ON, но в non-retained MQTT за четыре секунды опубликован только Level40, без повторного Switch ON; завершающий только Switch OFF → 40/OFF. Это MQTT-факт одного канала, не испытание герметичности и не ПНР системы.

Для всех 560/561/562 используется один HHM3Outputs. Неоднозначные valveClosedLevel/valveClosedEnable удалены. Вместо них: valveActiveMinLevel=1, valveActiveMaxLevel=100 — шкала при включённом выходе; valveOffCommand=false — единственная команда закрытия. floorOnlyMaxPct=50 для 562 сохранён. Визуальное наблюдение 560 при 1%/ON не разрешает использовать ON как безопасное закрытие.

| Состояние | Действие и условие перехода |
|---|---|
| UNINITIALIZED | После загрузки сначала новый OFF, старые MQTT значения не подтверждают состояние. |
| CLOSING | Только Switch OFF; насос OFF; ожидание нового non-retained OFF после конкретной попытки записи. Level не записывается. |
| CLOSED | Командный OFF подтверждён. Сохранённый Level любой, в том числе неизвестный; 20/OFF — штатно. Защитная рециркуляция возможна по запросу политики после проверки насоса. |
| OPENING | Насос OFF; новый целочисленный Level. Из CLOSED обязательны новые Level и ON. Только при смене цели из подтверждённого OPEN допускается прежний свежий ON без повторной публикации при неизменном Switch; новый Level обязателен всегда. Отдельных Switch ON программа не пишет. |
| OPEN | Оба атрибута подтверждены; разрешена команда насосу и, после его readback, заявка арбитру. Изменение цели запускает новую квалификацию. |
| CLOSURE_UNCERTAIN | Ошибка OFF или timeout; насос OFF, заявка недействительна, повтор только OFF через 5 с. |

Обычное закрытие, запрет нагрева, термозащита, ошибка открытия, смена цели во время открытия, restart и скачок часов используют один путь beginClose: Switch OFF без Level до или после него. Ожидание readback ограничено 10 с. При ошибке Level (включая ошибку после фактического применения) немедленно пробуется OFF; ошибка его подтверждения переводит в CLOSURE_UNCERTAIN. После подтверждения и короткой задержки повторы автоматические, без ручных grants. При неопределённом состоянии насос не запускается. Ошибка самого насоса также исключает заявку; физическое исполнение не гарантируется программным присваиванием.

Переход 20/OFF к нагреву не использует ON, восстанавливающий старые 20. Отправляется новый вычисленный Level; при первом открытии нужны два новых совпавших сообщения. Только при ретаргетинге из OPEN новый Level подтверждается при сохранении прежнего достоверного ON без промежуточного OFF. Если положительный Level не дал подтверждённый ON или любой readback отсутствует, timeout приводит к OFF; скрытого запасного ON нет. Кэш/retained/прежний Level не подтверждают новую транзакцию; прежний ON используется исключительно при подтверждённом непрерывном OPEN и действующей свежести. Внешнее изменение открытого выхода снимает готовность и вызывает OFF. Изменение только сохранённого Level при достоверном OFF не требует его исправлять.

Диагностика разделяет saved_level (MQTT), requested_level (цель открытия либо null при OFF), requested_enable/closed_command, состояние транзакции, fault и ready. closed_readback_match означает только свежий подтверждённый Switch OFF без незавершённой ошибки, не сравнивает Level с 1/0 и не доказывает герметичность. Нормальный CLOSED не обязан иметь Level=0 или 1.

commands[] различает SENT (успешное завершение присваивания), CACHE_SKIP (записи не было) и ERROR (delivery_unknown: команда могла примениться до исключения). command_sent не является подтверждением положения. Журнал использует info для состояния/восстановления, warning для ошибок, error для перегрева/неопределённого закрытия. Внешние уведомления не добавлялись.

## Границы программных гарантий

Радиаторные 503/505 не имеют смесителей: fallbackC=35 — запрос источнику, а не гарантия температуры воды 35 °C, когда другие потребители запрашивают больше. Настройки 501/502, динамику приводов и тепловую инерцию нужно проверить при ПНР. При полном отказе WB/питания либо одновременно недоступных датчиках программой нельзя гарантировать незамерзание. Аппаратные защиты не заменяются программными.

Структурированные события v3 публикуются при переходах локально в /neiro/ivolga/hhm3/events (state/warning/alarm/recovery), плюс журнал и VD. Обработчик внешних уведомлений не нужен для отопления; доставка уведомлений не реализована.
