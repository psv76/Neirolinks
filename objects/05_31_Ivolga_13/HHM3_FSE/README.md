# HHM 3.0 FSE — 05 31 Иволга 13

Единый комплект для котельного WB и WB беседки по [Issue #59](https://github.com/psv76/Neirolinks/issues/59). Все пять контуров входят в одну сборку. Физической установки и испытаний на объекте при разработке не было.

- [Установка и ПНР](INSTALL.md): DELETE / KEEP / INSTALL, недостающие физические факты.
- [Результаты программных проверок](TEST_RESULTS.md).
- [Объектный конфиг](modules/HHM3Config.js): все адреса, термостаты, пороги, таймеры и способ NO_DEMAND.
- [Манифест](manifest.json): назначения и SHA-256 каждого файла комплекта; aggregate SHA-256 идентифицирует содержимое.
- Проверка: `node tests/run.js`, затем `node tests/manifest.js --check` из этой папки. Node 18+; внешних npm-зависимостей нет.

## Архитектура и ownership

`620_thermostats.js` владеет только зональными выходами A08/A09/A13/A14 и формирует локальный frame v3 четырёх групп. 19 термостатов: 18 прежних домовых и новый 505. Воздушный 505 первоначально OFF, 20 °C, 15–28 °C, гистерезис 1 °C; насосом занимается только manager, без задержки приводов. ON/OFF и уставки сохраняются. Гостиная 010 и её датчик не переназначены.

`624_combo_besedka.js` на отдельном WB формирует wire v2 504: воздух выбирает цель пола; HEAT без OFF, пол максимум 30 °C. Физических writers нет. GazeboPanel остаётся прежним.

`500_HHM3_FSE.js` содержит пять managers, арбитр и source manager. Каждый manager владеет своим насосом и, где есть, смесителем. Арбитр только вычисляет MAX; порядок при равенстве 503, 502, 501, 504, 505. Source — единственный writer Heating Setpoint; Master CH enable используется исключительно при подтверждённом режиме ch_enable. 506, 507 и ГВС не входят в allowlist.

Один первоначальный ввод всего комплекта сохраняется в hhm3_operation.inService. После reboot/возврата питания и свежих данных повторного клика не требуется. Это не эксплуатационный grant каждого контура. До первоначального ввода отопительных физических writes нет; действующие неотопительные службы продолжают работу.

## Свежесть и восстановление

Датчик достоверен по свежей non-retained MQTT-публикации (120 с), при отсутствии meta/error и допустимом числовом значении. Пустые/null/boolean/NaN не подменяются нулём. Для frame нужны session/seq, TTL 30 с, ограничение рассинхронизации 2 с и подтверждение продвижения отправителя. retained не продлевает свежесть. Неизвестный retained у runtime явно диагностируется: необходим wb-rules >= 2.42.0. Заявки арбитра TTL 15 с. После разрыва или скачка часов повторяется квалификация свежести, но не требуется ручное разрешение.

При потере WB/LAN беседки 504 регулирует локальную подачу на 30 °C; штатно 35 °C, предел рабочей уставки 40 °C. Без 418 используется свежий пол с шагом 1 %/мин и пределом 50 % логического хода. Без обеих обратных связей горячий вход закрывается, рециркуляция сохраняется, NO_FEEDBACK_UNCOVERED явно сообщает непокрытый риск. Возврат датчиков восстанавливает штатный режим автоматически.

Домовой frame не является общим veto: при его потере manager использует сохранённый пользовательский ON и свежие состояния зональных реле, учитывая время открытия 180 с. Для 505 приводов нет. При потере воздушного датчика включённая зона сохраняет ограниченный запрос; при потере датчика пола соответствующая зона закрывается, исправные продолжают работу. Для 501/502 резерв без датчика подачи не разрешает открывать горячий вход (floorOnlyMaxPct=0); это локальное ограничение, не авария соседних контуров.

Защиты смешанных контуров используют сырые свежие температуры, запоминают перегрев через restart, закрывают горячий вход, затем при подтверждённом продолжающемся перегреве останавливают только свой насос. Для 504: подача 45/48/50 °C, пол 31/33 °C; охлаждение с гистерезисом, 120 с устойчивости и новая выборка, далее 60 с проверки циркуляции. В конфиге отдельно заданы стартовые пороги 501/502. NO_RESPONSE, холодный источник — предупреждения без бессрочной защёлки.

Источник теряет право новых writes при недостоверном 411/OT, но не выключает насосы соседей. Возврат свежих исправных данных автоматический. При перегреве 411 действуют аппаратные защиты котла; программный source не выдаёт новые нагревательные команды до охлаждения. Программный запрет записи сам по себе не отменяет прежнюю физическую уставку.

Достоверное отсутствие спроса всех потребителей даёт строго числовой 0. Недоступная заявка не считается доказанным отсутствием спроса. По умолчанию noDemandMode=unconfirmed: физическая команда OFF неизвестна, состояние NO_DEMAND_ACTION_UNCONFIRMED. Реализованы варианты setpoint_zero и ch_enable для выбора только после проверки на конкретном котле; скрытой уставки 42 °C нет. last_written/command_sent — команда программы, не подтверждение движения привода, протока или погасшей горелки.

## Границы программных гарантий

Радиаторные 503/505 не имеют смесителей: fallbackC=35 — запрос источнику, а не гарантия температуры воды 35 °C, когда другие потребители запрашивают больше. Настройки 501/502, динамику приводов и тепловую инерцию нужно проверить при ПНР. При полном отказе WB/питания либо одновременно недоступных датчиках программой нельзя гарантировать незамерзание. Аппаратные защиты не заменяются программными.

Структурированные события v3 публикуются при переходах локально в /neiro/ivolga/hhm3/events (state/warning/alarm/recovery), плюс журнал и VD. Обработчик внешних уведомлений не нужен для отопления; доставка уведомлений не реализована.

## Происхождение

За основу взяты проверенные combo, wire v2 и температурная политика из PR #57 (remote head 5cffa6ec8c16ad7bf6769b18ef59abcdd6da25b5, локальное дерево исходного материала 2e127fd). HHM3Mixing основан на общем MixingController из репозитория. Удалены индивидуальные commissioning gates и блокирующая архитектура grants; общий runtime и интеграционная модель написаны для пяти контуров. Старый main служит только базой Git PR, его скрипты не являются установочным набором. Имена HM2/MixingController не являются runtime-зависимостями релиза.
