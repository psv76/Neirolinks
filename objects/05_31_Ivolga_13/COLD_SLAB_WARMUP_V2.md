## План и реализованное поведение

1. Отдельно распознать изменение подачи после начала физической работы.
2. Затем требовать подтверждённый рост от минимума, достигнутого до первого прогресса.
3. После прогресса повышать контрольную температуру; не опускать её при колебаниях.
4. Ограничить время без прогресса и общую длительность незавершённого прогрева.
5. Сохранить readback, sensor/mixing/hard-max защиты и безопасное снятие запроса.
6. В runner считать падение только диагностикой, проверять актуальный тепловой результат.
7. Оставить периодический расчёт 620, убрав его принудительный подробный лог.

503, арбитр, источник и общий MixingController не изменяются.

### Начальные пределы для ревью и контролируемого ПНР

Это инженерные начальные параметры этой версии, не подтверждённая настройка гидравлики.

| Параметр | Значение |
|---|---|
| Первичный гидравлический сдвиг | 1 C в любую сторону |
| Минимальный новый рост | 1 C, 3 подтверждения с интервалом не менее 30 с |
| Полезный источник | не ниже target + 3 C |
| Учитываемые выходы | насос ON, питание клапана ON, readback положения 5–100% |
| Первое ожидание роста | 300 с grace + 600 с при полезном источнике и выходах |
| Следующее ожидание роста | 600 с с последнего подтверждения |
| Клапан >=95%, без нового роста | 600 с суммарно при полезном источнике |
| Подтверждение отсутствия прогресса | ещё 120 с и минимум 3 разнесённые проверки |
| Общий предел незавершённого прогрева | 3600 с, включая ожидания; WARMUP_TIMEOUT |
| Достижение цели | supply >= target − 1 C, 3 подтверждения |

При достигнутой цели допустимо закрытие смесителя до 0–5%: это штатное
регулирование и не должно приводить к WARMUP_TIMEOUT. Насос, питание клапана
и корректный readback остаются обязательными. Порог открытия 5% требуется
для подтверждения роста во время прогрева, а не для AT_TARGET.

Времена полезного нагрева и большого открытия накапливаются.
Ожидание источника/выходов не обнуляет историю и общий предел.
Начальная минимальная подача фиксируется до первого подтверждённого роста;
последующие колебания вокруг той же температуры не создают новый прогресс.
Достижение цели завершает эпизод, подтверждённый новый спад начинает следующий.
Изменение уставки само по себе не сбрасывает бюджет.

NO_WARMUP_PROGRESS сначала виден в течение подтверждения, затем защёлкивается.
Защёлкнутая авария даёт FAULT_LATCHED, invalid request, heat_demand=0,
path_ready=0 и три безопасных выхода. Причина остаётся в fault_text и response_reason.
Явный reset_fault оставляет физические разрешения выключенными.

### Статусы и диагностика

START_GRACE — начальная выдержка; WAIT_HOT_SOURCE — ожидание горячего источника;
WAIT_OUTPUT_READBACK — ожидание выходов; HYDRAULIC_RESPONSE — первичный сдвиг;
COLD_SLAB_WARMUP — ожидание обязательного роста;
WARMUP_PROGRESS — подтверждённый рост после холодного падения;
RESPONSE_OK — подтверждённый рост без начального падения;
AT_TARGET — подтверждённая цель; NO_WARMUP_PROGRESS — подтверждение отсутствия роста;
FAULT_LATCHED — защёлкнутая авария. IDLE остаётся для выключенного контура.

Новые controls: warmup_elapsed_s, warmup_hot_elapsed_s,
warmup_baseline_supply_c, warmup_min_supply_c, warmup_checkpoint_c,
warmup_progress_count, hydraulic_response_seen, warmup_high_valve_s, response_reason.
Текущая подача, источник, клапан и изменение подачи доступны в существующих
supply_temp_c, source_temp_c, valve_position_physical, response_rise_c.
При аварии история прогрева сохраняется до явного сброса, но не через перезагрузку.
Журнал пишет переходы response_status, а не каждую периодическую проверку.

MQTT readback — состояние выхода, не положение штока и не доказательство протока.
Значения температур не имеют отдельного heartbeat в текущем контракте managers;
разнесённые проверки не доказывают свежесть каждого физического измерения.
Неподвижная подача при горячем источнике теперь ограничена таймером,
но физические датчики, направление клапана, насос и гидравлика требуют проверки на месте.

## Установка без запуска отопления

Архив должен содержать рассмотренную версию этой папки с
Wirenboard/wb-rules, tools/hm2_install_cold_slab_v2.sh и
tools/cold_slab_v2.sha256.json. Передать архив на WB отдельно.
Установщик проверяет контрольные суммы, снимает разрешения 501/502,
проверяет MQTT-ноль, сохраняет все три исходных live-файла с контрольными суммами
в уникальную папку /root/hm2/backups и печатает BACKUP_DIR.

Команда после передачи архива в /root/hm2/ivolga-cold-slab-v2.tar.gz:

```sh
mkdir -p /root/hm2/ivolga-cold-slab-v2
tar -xzf /root/hm2/ivolga-cold-slab-v2.tar.gz -C /root/hm2/ivolga-cold-slab-v2
sh /root/hm2/ivolga-cold-slab-v2/tools/hm2_install_cold_slab_v2.sh install /root/hm2/ivolga-cold-slab-v2
```

Установщик атомарно заменяет только 501, 502, 620. Общего restart wb-rules нет:
[wb-rules автоматически перезагружает изменённые файлы](https://github.com/wirenboard/wb-rules#автоматическая-перезагрузка-сценариев).
Исходные live-файлы сохраняются даже при частичной ошибке установки.
Затем повторно проверяются отключённые разрешения и MQTT-ноль.
Сброс fault_latched, запуск runner и включение контуров не выполняются.

Проверить журнал загрузки всех трёх файлов, отсутствие ошибок JS,
состояние 503/источника и новые controls. Активная служба сама по себе
не подтверждает успешную загрузку каждого сценария.

```sh
journalctl -u wb-rules --since '5 minutes ago' --no-pager
```

### Откат

Подставить точный BACKUP_DIR, напечатанный установщиком:

```sh
sh /root/hm2/ivolga-cold-slab-v2/tools/hm2_install_cold_slab_v2.sh rollback /root/hm2/backups/ИМЯ_РЕЗЕРВНОЙ_КОПИИ
```

Откат проверяет контрольные суммы резервной копии и возвращает исходные live-файлы,
также оставляя 501/502 выключенными. Он не восстанавливает разрешения на работу.
Если MQTT или wb-rules недоступны, установщик/откат прекращается до замены:
сначала восстановить возможность безопасно проверить выключенные выходы.
Старый live-patch в backup сохраняет свои ограничения; откат не разрешает его эксплуатацию.

## Отдельный ПНР — только после явного разрешения

Runner затрагивает все три контура, выключает тестовые термостаты и в конце
оставляет систему выключенной. Не запускать при работающем 503 без согласованного
окна испытаний. Установка runner не запускает.

Явный запуск после разрешения:

```sh
sh tools/hm2_integrated_commissioning_runner.sh --confirm-physical-test
```

Для 501/502 нужен измеренный рост минимум 1 C от наблюдённого минимума
и подтверждение manager либо измеренное AT_TARGET.
Требуется минимум три последовательных успешных опроса в конце теста,
одновременные pump/valve/source/arbiter условия, отсутствие fault/interlock,
свежий request_timestamp. Ранний успешный результат не перекрывает последующую потерю прогресса.
NO DATA/fault/interlock останавливают тест. Критерий 503 остаётся THERMAL.
Любое неизвестное RESPONSE_MODE не проходит.
Проверка safe-off входит в итог; после неуспеха следующий контур не запускается.
Пределы подачи/источника контролируют штатные managers; runner их не отменяет.
