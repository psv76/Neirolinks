# 05 31 Иволга 13 — HM2 ownership и фактическая гидравлика

Статус: **рабочая версия от 2026-09-11**.

Документ фиксирует не новую архитектуру, а объектную адаптацию уже принятой архитектуры Heating Manager 2.0 к фактической гидравлике и каналам Иволги.

## 1. Источники истины

Для отопления Иволги использовать в таком порядке:

1. `objects/05_31_Ivolga_13/HEATING_CHANNEL_MAP.md`
2. `objects/05_31_Ivolga_13/THERMOSTAT_MAP.md`
3. `objects/05_31_Ivolga_13/etc/wb-rules/620_thermostats.js`
4. `objects/05_31_Ivolga_13/etc/wb-rules/600_Heat_diagnostics.js`
5. `objects/05_31_Ivolga_13/etc/wb-rules/507_Pressure_makeup.js`
6. `Templates/WB-rules/Heating/HM2/MixingController/`
7. issue `#18` — общая разработка HM2
8. issue `#20` — объектная адаптация HM2 для Иволги

Старые карты и старые подписи сантехников не использовать как источник истины, если они противоречат актуальной карте каналов.

## 2. Не принимаем архитектуру заново

Для Иволги не проектируется новая схема HM2. Применяется уже принятый общий принцип:

```text
consumer → атомарный request → arbiter → source manager → единственный writer источника
```

Объектная особенность Иволги: зональные термостаты находятся в Wiren Board, а не во внешнем Home Assistant.

Следовательно, `620_thermostats.js` является нижним зональным слоем, а контурные managers должны читать его результат и публиковать HM2 consumer contracts.

## 6. Роль `620_thermostats.js` в HM2

`620_thermostats.js` не является полным Heating Manager 2.0.

Его роль:

```text
датчик помещения/пола → simple-термостат → команда сервоприводу зоны → состояние зоны для контурного manager
```

Для последующих managers он является источником состояния зон:

| Контур | Зоны / выходы |
|---|---|
| 501 ТП дом, паркет | `A08/K1`, `A08/K2`, `A08/K3`, `A08/K4` |
| 502 ГП дом, плитка | `A13/K1…K6`, `A14/K1…K3` |
| 503 Радиаторы дома | `A08/K5`, `A08/K6`, `A09/K1…K3` — пять зон; `A09/K4 OR A09/K5` — общая логическая зона 010 в manager 503 |

## 7. Роль `MixingController.js`

`MixingController.js` — не самостоятельный скрипт контура Иволги.

Это общий модуль регулирования положения смесительного клапана. Он не содержит:

- MQTT-адресов Иволги;
- насосов;
- зональных термостатов;
- погодной кривой конкретного объекта;
- HM2-арбитража;
- логики источника тепла.

Для Иволги нужны object managers, которые используют этот модуль.

Рабочие имена файлов пока считать предложением, а не исторически утверждённым фактом:

```text
560_mixing_tp_dom_manager.js
561_mixing_gp_dom_manager.js
562_mixing_gp_besedka_manager.js
```

## 8. Контракты будущих consumers

Каждый контурный manager должен публиковать атомарный HM2 request:

| Поле | Смысл |
|---|---|
| `state` | `ACTIVE / INACTIVE / UNKNOWN` |
| `valid` | достоверность обязательных входов |
| `heat_demand` | нужен ли теплоноситель контуру |
| `requested_source_temperature` | требуемая температура общей подачи |
| `request_reason` | причина запроса |
| `request_timestamp` | время расчёта |
| `request_ttl_s` | срок действия запроса |
| `path_ready` | готов ли физический путь после задержки сервоприводов |
| `pump_on` | команда/состояние насоса контура |
| `fault_latched` | защёлкнутая авария, запрещающая участие в арбитраже |
| `grant_state` | результат арбитража, пишет arbiter |
| `grant_reason` | причина результата арбитража |

Булев `true` без timestamp/TTL не считать полноценным запросом тепла.

## 10. Следующий рабочий шаг

### Шаг 1. Проверить усиленный safe-output contract 501

Manager `etc/wb-rules/501_tp_dom_manager.js` создан. Версия после исправления `sc()`
(commit `3d3118da7fbdce42148e28886f83055599de0d70`) прошла live shadow-тест
по сообщению Сергея: ACTIVE, valid=1, heat_demand=1, path_ready=1,
расчётный pump_on=1, подача 30 °C, запрос источнику 35 °C, источник около 59 °C,
подача около 22 °C, POST_MOVE_SETTLE; ошибок wb-rules нет.
Старое active_zone_count=2 соответствовало двум выходам одной зоны 601.
Этот результат относится к предыдущей версии; усиленная версия пока проверена локально.

**Статус: manager создан, проходит shadow/commissioning; физический запуск только
после проверки safe-output hardening на контроллере.**

Контракт новой версии:

- Любой запрет (включая outputs_enabled=false) активно отправляет насос OFF,
  положение клапана 0 %, питание клапана OFF. Повтор — на каждом расчёте
  (период ограничен 5–30 с). При исключении записи остальные выходы всё равно обрабатываются.
- Shadow теперь означает отсутствие положительных команд, но **нулевые физические команды отправляются**.
- На перезагрузке outputs_enabled и manual_commissioning_grant принудительно false.
- pump_cmd и valve_position_cmd — расчёт. pump_physical_state,
  valve_position_physical и valve_enable_physical — снимок MQTT перед записью;
  physical_readback_valid показывает наличие значений. Это readback модуля,
  не независимое подтверждение вращения насоса или положения штока.
- grant_state/grant_reason — readonly: NO_ARBITER по умолчанию. Адаптера арбитра ещё нет.
  Единственный предусмотренный сейчас GRANTED — явно включённый
  manual_commissioning_grant, отмеченный в WebUI и журнале.
- Реальный запуск требует всех локальных условий, outputs_enabled,
  manual_commissioning_grant и response_commissioned. Последний флаг означает
  подтверждение описанных ниже объектных параметров watchdog.
- Ручной freeze не обходит проверку hard max подачи в manager.
- active_zone_count: 601 (K1 OR K4), 602 (K2), 603 (K3).
  physical_active_output_count считает K1…K4 отдельно. Задержка готовности ведётся
  отдельно для каждой логической зоны; новый путь не наследует задержку закрывшегося.
- fault_latched обнуляет запрос температуры, valid и heat_demand;
  сброс возможен при валидных датчиках и подаче ниже hardMax−2 °C,
  снимает outputs_enabled и ручной grant, поэтому сам по себе не запускает контур.

Response watchdog (начальные параметры Иволги, требуют ПНР):

- 300 с grace, затем 600 с окно наблюдения;
- минимальный рост 413 — 1 °C; при достижении target−1 °C нагрев считается достаточным;
- наблюдение при readback насоса ON, питания клапана ON, положения ≥5 %
  и источнике не холоднее target+3 °C;
- после окна — минимум 120 с подтверждения и минимум 3 samples с интервалом ≥30 с;
- рост сбрасывает окно; контроль продолжается до достижения цели;
- при остановке, недостаточно горячем источнике, закрытом клапане или смене target
  окно переинициализируется; shadow не создаёт response fault;
- подтверждённое отсутствие роста: RESPONSE_TIMEOUT_413, защёлка и три нулевые команды;
- отсутствие readback включения насоса/питания клапана более 120 с:
  OUTPUT_READBACK_TIMEOUT. Свежесть/ошибки MQTT и физический теплоперенос
  необходимо проверить на ПНР; наличие числового readback не доказывает исправность связи.

Проверка на живом контроллере сначала при outputs_enabled=false:

1. Убедиться в отсутствии второго writer трёх выходов 501, установить обновлённый manager.
2. Проверить три нулевых выхода после загрузки; manual grant выключен, grant NO_ARBITER.
3. Открыть зону 601 через существующий термостат: logical count=1, physical count=2.
   После задержки pump_cmd может быть 1, физические значения должны оставаться 0.
4. Проверить снятие каждого локального разрешения, восстановление датчиков, рестарт,
   отсутствие ошибок и разделение cmd/readback. Не разрешать физический нагрев на этом этапе.
5. Для последующей ПНР отдельно подтвердить направление/нулевое положение клапана,
   датчики 411/413/414, параметры target/hard max/tuning и response. Только затем
   осознанно включать ручной grant и outputs_enabled под наблюдением.
6. С реальным управлением проверить безопасный stop каждого gate, реакцию подачи,
   watchdog и сброс fault. Не имитировать перегрев подменой живого датчика при нагреве;
   fault-сценарии сначала проверять на изолированном стенде.

### Шаг 2. 502 создан: проверить только shadow/gate (#27)

`etc/wb-rules/502_gp_dom_manager.js` адаптирован из актуального hardened 501
на GitHub main после merge PR #32 (`cb66a24362560d39d6422e9d0c63b9af051ff5b2`).
Виртуальное устройство: `hm2_502_gp_dom`, заголовок: **HM2 502 ГП дом / плитка**.
Физический ПНР 502, live-проверка и деплой на WB не выполнялись.
Production enable отсутствует; до отдельного ПНР разрешены только shadow/gate-проверки.

Каналы 502:

- насос — `A03/K2`;
- клапан 561 — `A05/Channel 2 Switch` и `A05/Channel 2 Dimming Level`;
- подача 415 / обратка 416 — `wb-m1w2_167/External Sensor 1` / `External Sensor 2`;
- источник 411 — `wb-m1w2_170/External Sensor 1`;
- зональные выходы `A13/K1…K6`, `A14/K1…K3` только читаются;
  **620 остаётся единственным writer зон A13/A14; A14/K4 не используется**.
- 502 не пишет OpenTherm. Запрос температуры источника — только собственный virtual control.

По `HEATING_CHANNEL_MAP.md`, `THERMOSTAT_MAP.md` и актуальному `620_thermostats.js`
термостаты 606–614 имеют по одному выходу. Допущение модели 502: каждый из девяти
указанных выходов — отдельная логическая зона; объединённых групп нескольких выходов
не подтверждено. Гостиная и коридор уже объединены за одним выходом A13/K6 (611).
`active_zone_count` считает эти девять логических зон, `physical_active_output_count`
считает девять выходов отдельно; сейчас значения совпадают. Для каждого выхода
ведётся своя задержка, открытие новой зоны не наследует готовность закрывшейся.

**ПНР-параметры, не объектная истина:** подтверждённой уставки подачи 502 в актуальной
карте нет (зональные температуры пола/воздуха не являются температурой теплоносителя).
Поэтому 502 имеет собственные стартовые `target_supply_c=32 °C`, диапазон 20–35 °C,
`hardMaxC=40 °C` для подачи 415 и запрос источнику target+5 °C.
Это предварительный осторожный набор для shadow/будущего ПНР, а не перенос паркетных
ограничений как нормы для плитки. Направление/шкала клапана, весь tuning, hardMax,
диапазон датчиков, actuator delay 180 с и source margin 3 °C требуют ПНР.

Сохранён hardened safe-output contract: любой запрет активно отправляет насос OFF,
клапан 0 %, питание клапана OFF; исключение одной записи не отменяет попытки остальных.
На reload принудительно выключаются `outputs_enabled`, `manual_commissioning_grant`
и дополнительно `response_commissioned`. Без ручного grant или response_commissioned
реальный запуск невозможен. Ручной grant оставлен только для будущего очного ПНР,
адаптера arbiter нет, стартовый grant — `NO_ARBITER`.
Расчётные `pump_cmd` / `valve_position_cmd` отделены от MQTT-readback трёх выходов,
который снимается до записи. `physical_readback_valid` означает наличие readback,
но не подтверждает его свежесть, проток или положение штока.

Response watchdog наследует принцип hardened 501 и включается только при реальном
разрешении управления: grace 300 с, окно 600 с, рост подачи 415 не менее 1 °C либо
достижение target−1 °C; подтверждение отказа минимум 120 с и 3 samples с шагом 30 с.
Нужны readback насоса/питания клапана ON, положение ≥5 % и источник ≥target+3 °C.
Пороги предварительные, требуют ПНР; таймаут называется `RESPONSE_TIMEOUT_415`.
Shadow не создаёт response fault, watchdog в нём IDLE. Независимые защиты hardMax
и MixingController сохраняются и могут защёлкнуть температурную/сенсорную аварию
также в shadow; это не response watchdog и не свидетельство полевого дефекта.

Краткая последующая проверка человеком (результат пока не заявляется):

1. Сверить ownership; убедиться, что три выхода 502 удерживаются в нуле после старта.
2. При outputs/grant/response=0 включить enabled/commissioned/local_permit и открыть
   тестовую зону через 620. После её actuator delay проверить counts, path_ready,
   pump_cmd и нулевой физический readback. У каждой из девяти зон проверить demand.
3. При response=0 проверить outputs=1 с grant=0, затем grant=1; физические выходы
   остаются 0. Не включать response_commissioned на этом этапе.
4. Снять все шесть разрешений, проверить нули, закрыть тестовую зону штатным
   термостатом, сохранить журнал. Runner #26 предназначен для 501, не для 502.
5. Перезапуск, ошибки датчиков, gate-stop и watchdog сначала проверить на изолированном
   стенде. Физический ПНР 502 — отдельный шаг после проверки 411 и гидравлики.

504 остаётся будущей отдельной адаптацией после уточнения demand; в #27 он не меняется.

`wb-m1w2_170/External Sensor 1`; обратка 417: `wb-m1w2_121/External Sensor 1`.
503 не пишет OpenTherm; `requested_source_temperature` — диагностический запрос
в собственном виртуальном устройстве, не команда источнику.

**620 остаётся единственным writer зон A08/A09.** Счётчики manager 503:

| Логическая зона 503 | Читаемые выходы | Максимум физических выходов |
|---|---|---:|
| 005, прихожая | `A08/K5` | 1 |
| 006, гостевая спальня | `A08/K6` | 1 |
| 007, мастер санузел | `A09/K1` | 1 |
| 008, кабинет | `A09/K2` | 1 |
| 009, мастер спальня | `A09/K3` | 1 |
| 010, гостиная | `A09/K4 OR A09/K5` | 2 |

`active_zone_count` максимум 6, `physical_active_output_count` максимум 7.
При двух активных выходах гостиной counts=1/2. Объединение в 010 выполнено
**по явному заданию #28 на уровне manager**: в текущих `620_thermostats.js`
и картах K4/K5 ещё соответствуют отдельным термостатам 010/011.
Это не утверждение об изменении 620 или синхронности двух физических приводов.
При активности любого из двух выходов гостиная считается одной активной зоной;
пока OR остаётся true, это та же логическая зона с тем же таймером.

У каждой из шести зон собственный `actuator_delay_s` (default 180 с, диапазон 0–900).
Новая логическая зона не наследует готовность закрывшейся. Неизвестное/некорректное
состояние любого из семи выходов делает `zone_inputs_valid=false`, `valid=false`,
запрос тепла невалидным, насос выключенным. Для `valid` также нужны enabled,
commissioned, допустимые значения обоих датчиков 411/417 и отсутствие fault.
Диапазон достоверности температур −20…95 °C — техническая проверка значения,
**не безопасный тепловой предел радиаторов**; реальные ограничения требуют ПНР.
`heat_demand=true` только при valid и наличии зоны; pump_cmd дополнительно требует
path_ready и local_permit. Период расчёта 5–30 с (default 30), TTL запроса 90 с.

Подтверждённой уставки источника для 503 в актуальных картах нет. Собственный
`target_source_c=45 °C`, диапазон 35–60 °C — **предварительный ПНР-параметр**,
не объектная истина. При valid+demand `requested_source_temperature=target_source_c`,
иначе 0. Настройки 501/502 не определяют этот запрос.

Любой запрет, в том числе outputs_enabled=false, активно отправляет A03/K3=false
на каждом расчёте. При старте outputs_enabled, manual_commissioning_grant и
response_commissioned принудительно сбрасываются. NO_ARBITER по умолчанию;
ручной grant оставлен только для будущего очного ПНР. Реальный пуск требует всех
локальных условий и outputs/manual grant/response. Pump_cmd отделён от снимка
readback A03/K3 до записи; physical_readback_valid проверяет распознаваемое булево
значение, но не свежесть MQTT и не работу насоса. Отказ записи защёлкивает fault,
пытается выключить насос и обнуляет valid/demand/запрос; повторный расчёт повторяет stop.
Reset сначала снимает все три физических разрешения, требует валидных входов и
успешной отправки stop, сам по себе никогда не возобновляет нагрев.

Response watchdog — **предварительные параметры для отдельного ПНР**:

- только при реальном разрешении управления; в shadow IDLE, response fault не создаётся;
- readback насоса ON; отсутствие подтверждения ON 120 с → OUTPUT_READBACK_TIMEOUT;
- источник 411 не холоднее target−3 °C, иначе WAIT_HOT_SOURCE со сбросом окна;
- обратка 417 не ниже target−10 °C → RETURN_WARM, дальнейшего роста не требуется;
- для холодной обратки нужен перепад source−return ≥3 °C;
- grace 300 с + окно 600 с; ожидается рост обратки ≥1 °C, рост обновляет baseline;
- после окна — подтверждение отсутствия роста ≥120 с и ≥3 samples с шагом ≥30 с;
- подтверждённая стагнация → RESPONSE_TIMEOUT_417, fault, насос OFF;
- остановка, смена target, холодный источник, отсутствие readback сбрасывают окно.

RETURN_WARM / RESPONSE_OK не являются доказательством протока. Источник общий,
обратка может прогреваться по другим причинам; насос, гидравлику, арматуру, воздух
и температуру труб проверяет инженер. Не включать физический ПНР 503 до этой проверки
и подтверждения source target/watchdog. Подменять живые датчики для fault-тестов нельзя.

   valid/demand/path_ready/pump_cmd и нулевой readback насоса. Для гостиной проверить
   K4 отдельно, K5 отдельно, оба вместе: logical=1, physical=1/1/2.
3. При response=0 проверить outputs=1 без grant, затем manual grant=1: насос остаётся OFF.
4. Снять все шесть разрешений, проверить OFF, закрыть тестовые зоны через их фактические
   термостаты 620 (в том числе 010 и 011), сохранить журнал с префиксом 503_rad_dom_manager.
