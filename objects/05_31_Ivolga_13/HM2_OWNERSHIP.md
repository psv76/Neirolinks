# 05 31 Иволга 13 — HM2 ownership и фактическая гидравлика

Статус: **рабочая версия от 2026-09-11**.

Документ фиксирует не новую архитектуру, а объектную адаптацию уже принятой архитектуры Heating Manager 2.0 к фактической гидравлике и каналам Иволги.

## 1. Источники истины

Для отопления Иволги использовать в таком порядке:

1. `objects/05_31_Ivolga_13/HEATING_CHANNEL_MAP.md`
2. `objects/05_31_Ivolga_13/THERMOSTAT_MAP.md`
3. `objects/05_31_Ivolga_13/etc/wb-rules/620_thermostats.js`
4. `objects/05_31_Ivolga_13/etc/wb-rules/600_Heat_diagnostics.js`
5. `objects/05_31_Ivolga_13/etc/wb-rules/507_Pressure_makeup.js`
6. `Templates/WB-rules/Heating/HM2/MixingController/`
7. issue `#18` — общая разработка HM2
8. issue `#20` — объектная адаптация HM2 для Иволги

Старые карты и старые подписи сантехников не использовать как источник истины, если они противоречат актуальной карте каналов.

## 2. Не принимаем архитектуру заново

Для Иволги не проектируется новая схема HM2. Применяется уже принятый общий принцип:

```text
consumer → атомарный request → arbiter → source manager → единственный writer источника
```

Объектная особенность Иволги: зональные термостаты находятся в Wiren Board, а не во внешнем Home Assistant.

Следовательно, `620_thermostats.js` является нижним зональным слоем, а контурные managers должны читать его результат и публиковать HM2 consumer contracts.

## 6. Роль `620_thermostats.js` в HM2

`620_thermostats.js` не является полным Heating Manager 2.0.

Его роль:

```text
датчик помещения/пола → simple-термостат → команда сервоприводу зоны → состояние зоны для контурного manager
```

Для последующих managers он является источником состояния зон:

| Контур | Зоны / выходы |
|---|---|
| 501 ТП дом, паркет | `A08/K1`, `A08/K2`, `A08/K3`, `A08/K4` |
| 502 ГП дом, плитка | `A13/K1…K6`, `A14/K1…K3` |
| 503 Радиаторы дома | `A08/K5`, `A08/K6`, `A09/K1…K5` |

## 7. Роль `MixingController.js`

`MixingController.js` — не самостоятельный скрипт контура Иволги.

Это общий модуль регулирования положения смесительного клапана. Он не содержит:

- MQTT-адресов Иволги;
- насосов;
- зональных термостатов;
- погодной кривой конкретного объекта;
- HM2-арбитража;
- логики источника тепла.

Для Иволги нужны object managers, которые используют этот модуль.

Рабочие имена файлов пока считать предложением, а не исторически утверждённым фактом:

```text
560_mixing_tp_dom_manager.js
561_mixing_gp_dom_manager.js
562_mixing_gp_besedka_manager.js
```

## 8. Контракты будущих consumers

Каждый контурный manager должен публиковать атомарный HM2 request:

| Поле | Смысл |
|---|---|
| `state` | `ACTIVE / INACTIVE / UNKNOWN` |
| `valid` | достоверность обязательных входов |
| `heat_demand` | нужен ли теплоноситель контуру |
| `requested_source_temperature` | требуемая температура общей подачи |
| `request_reason` | причина запроса |
| `request_timestamp` | время расчёта |
| `request_ttl_s` | срок действия запроса |
| `path_ready` | готов ли физический путь после задержки сервоприводов |
| `pump_on` | команда/состояние насоса контура |
| `fault_latched` | защёлкнутая авария, запрещающая участие в арбитраже |
| `grant_state` | результат арбитража, пишет arbiter |
| `grant_reason` | причина результата арбитража |

Булев `true` без timestamp/TTL не считать полноценным запросом тепла.

## 10. Следующий рабочий шаг

### Шаг 1. Проверить усиленный safe-output contract 501

Manager `etc/wb-rules/501_tp_dom_manager.js` создан. Версия после исправления `sc()`
(commit `3d3118da7fbdce42148e28886f83055599de0d70`) прошла live shadow-тест
по сообщению Сергея: ACTIVE, valid=1, heat_demand=1, path_ready=1,
расчётный pump_on=1, подача 30 °C, запрос источнику 35 °C, источник около 59 °C,
подача около 22 °C, POST_MOVE_SETTLE; ошибок wb-rules нет.
Старое active_zone_count=2 соответствовало двум выходам одной зоны 601.
Этот результат относится к предыдущей версии; усиленная версия пока проверена локально.

**Статус: manager создан, проходит shadow/commissioning; физический запуск только
после проверки safe-output hardening на контроллере.**

Контракт новой версии:

- Любой запрет (включая outputs_enabled=false) активно отправляет насос OFF,
  положение клапана 0 %, питание клапана OFF. Повтор — на каждом расчёте
  (период ограничен 5–30 с). При исключении записи остальные выходы всё равно обрабатываются.
- Shadow теперь означает отсутствие положительных команд, но **нулевые физические команды отправляются**.
- На перезагрузке outputs_enabled и manual_commissioning_grant принудительно false.
- pump_cmd и valve_position_cmd — расчёт. pump_physical_state,
  valve_position_physical и valve_enable_physical — снимок MQTT перед записью;
  physical_readback_valid показывает наличие значений. Это readback модуля,
  не независимое подтверждение вращения насоса или положения штока.
- grant_state/grant_reason — readonly: NO_ARBITER по умолчанию. Адаптера арбитра ещё нет.
  Единственный предусмотренный сейчас GRANTED — явно включённый
  manual_commissioning_grant, отмеченный в WebUI и журнале.
- Реальный запуск требует всех локальных условий, outputs_enabled,
  manual_commissioning_grant и response_commissioned. Последний флаг означает
  подтверждение описанных ниже объектных параметров watchdog.
- Ручной freeze не обходит проверку hard max подачи в manager.
- active_zone_count: 601 (K1 OR K4), 602 (K2), 603 (K3).
  physical_active_output_count считает K1…K4 отдельно. Задержка готовности ведётся
  отдельно для каждой логической зоны; новый путь не наследует задержку закрывшегося.
- fault_latched обнуляет запрос температуры, valid и heat_demand;
  сброс возможен при валидных датчиках и подаче ниже hardMax−2 °C,
  снимает outputs_enabled и ручной grant, поэтому сам по себе не запускает контур.

Response watchdog (начальные параметры Иволги, требуют ПНР):

- 300 с grace, затем 600 с окно наблюдения;
- минимальный рост 413 — 1 °C; при достижении target−1 °C нагрев считается достаточным;
- наблюдение при readback насоса ON, питания клапана ON, положения ≥5 %
  и источнике не холоднее target+3 °C;
- после окна — минимум 120 с подтверждения и минимум 3 samples с интервалом ≥30 с;
- рост сбрасывает окно; контроль продолжается до достижения цели;
- при остановке, недостаточно горячем источнике, закрытом клапане или смене target
  окно переинициализируется; shadow не создаёт response fault;
- подтверждённое отсутствие роста: RESPONSE_TIMEOUT_413, защёлка и три нулевые команды;
- отсутствие readback включения насоса/питания клапана более 120 с:
  OUTPUT_READBACK_TIMEOUT. Свежесть/ошибки MQTT и физический теплоперенос
  необходимо проверить на ПНР; наличие числового readback не доказывает исправность связи.

Проверка на живом контроллере сначала при outputs_enabled=false:

1. Убедиться в отсутствии второго writer трёх выходов 501, установить обновлённый manager.
2. Проверить три нулевых выхода после загрузки; manual grant выключен, grant NO_ARBITER.
3. Открыть зону 601 через существующий термостат: logical count=1, physical count=2.
   После задержки pump_cmd может быть 1, физические значения должны оставаться 0.
4. Проверить снятие каждого локального разрешения, восстановление датчиков, рестарт,
   отсутствие ошибок и разделение cmd/readback. Не разрешать физический нагрев на этом этапе.
5. Для последующей ПНР отдельно подтвердить направление/нулевое положение клапана,
   датчики 411/413/414, параметры target/hard max/tuning и response. Только затем
   осознанно включать ручной grant и outputs_enabled под наблюдением.
6. С реальным управлением проверить безопасный stop каждого gate, реакцию подачи,
   watchdog и сброс fault. Не имитировать перегрев подменой живого датчика при нагреве;
   fault-сценарии сначала проверять на изолированном стенде.

## 11. Что не делать

- Не копировать объектные каналы Исети.
- Не писать новый самостоятельный PID/step-hold с нуля, если уже есть `MixingController.js`.
- Не делать `MixingController.js` владельцем насоса.
- Не давать арбитру право писать насосы или клапаны.
- Не включать `A14/K4`.
- Не считать `507_Pressure_makeup.js` экспериментальным: на Иволге он уже полево проверен.
