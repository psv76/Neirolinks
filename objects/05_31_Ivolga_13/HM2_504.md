# HM2 504 — реализация согласованного контракта v1.0

**READY_FOR_REVIEW / NOT_DEPLOYED / LIVE_NOT_VERIFIED**, 20.09.2026.
Главный источник: [согласованный контракт](https://github.com/psv76/Neirolinks/issues/56#issuecomment-5745537476).
Связанные #18, #20, #39, #40, #51, #58 прочитаны; при противоречии применяется контракт 504.
Разработка продолжается в PR #57 от ee460de1da1cd98159655b13be4e7afdb89b49b0.

## Что реализовано

Управляющая часть переписана: HM2504Control отвечает за режимы и термозащиту,
HM2504Config — за объектные параметры, 504_gp_besedka_manager — за MQTT и единственный
writer. Общий MixingController используется для штатного регулирования подачи без
изменения общего файла и без копирования чисел других объектов. Его callbacks
считают желаемое положение в памяти; итоговые команды выдаёт manager после raw-защит.
При отказе 418 отдельная ограниченная ступенчатая регулировка использует именно пол,
не передаёт температуру пола в MixingController как температуру воды.

Один pushbutton «Включить отопление» при первичной ПНР сохраняет
ivolga_504_operation.inService. До него нет физических записей, даже OFF.
Старые enabled/commissioned/outputs_enabled/physical_write_grant/reset_fault,
PROFILE=null, shadowMixer и бессрочная диагностическая защёлка удалены.
Старое ivolga_504_safety не изменяется и не используется новым управляющим кодом:
оно не являлось введённой системой; при переходе проверить его происхождение,
не стирать реальные аварии действующего оборудования.

После ввода reboot/rules restart не требуют кнопки: новые измерения → закрытый
горячий вход и проверка на циркуляции → регулирование. Сохраняются только ввод
и причины текущей термозащиты; расчётные положение, свежесть и таймеры не восстанавливаются.
Отдельного пользовательского OFF нет. target_state — readonly HEAT для совместимости
UI, старый ноль переосмыслен; NO_DEMAND прекращает избыточный нагрев только 504.
Шаблон Sprut ограничен VD 504, не предлагает OFF и не перезаписывает уставки init.

## Физические записи

| Writer | Разрешённые записи |
|---|---|
| 624_combo_besedka на WB беседки | Собственный VD и один non-retained frame |
| 504_gp_besedka_manager на котельном WB | Собственный VD; после первичной ПНР A03/K4 и A05/Channel 3 Level/Switch |
| Арбитр | Только hm2_request_arbiter |
| Источник | Прежний Heating Setpoint, существующий контракт #40; добавлена только whitelist 504 |

При открытии Level записывается до Switch ON независимо от старого readback.
Закрытие соответствует измеренным closedLevel/closedEnable, включая обратную шкалу.
При stop сначала насос OFF, затем закрытие; ошибка одной записи не отменяет остальные.
Ошибка выдачи команды обнуляет пригодность запроса, диагностируется, запись повторяется
автоматически без latch. MQTT/dev assignment не доказывает движение привода или проток.
path_ready означает принятую локальную команду циркуляции, а не измеренный расход.

## Режимы и восстановление

| Условие | Действие | Возврат |
|---|---|---|
| До первого ПНР | Никаких физических writes | Одна кнопка после проверки физики и конфигурации |
| Свежий combo demand | Цель подачи 35 °C, максимум рабочей цели 40; насос ON, MixingController | Штатное регулирование |
| Исправный combo NO_DEMAND | Горячий вход закрыт, выбег циркуляции 120 с, затем насос OFF | Новый demand запускает проверку циркуляции |
| Нет воздуха, есть пол | Combo поддерживает пол по hold (25 по умолчанию) | Автоматически по свежему воздуху |
| Нет свежего/валидного удалённого demand, есть 418 | Автономия 30 °C, местные температурные защиты | Две свежие публикации с интервалом и временной проверкой → combo |
| Нет 418, есть свежий пол | FLOOR_ONLY, ограниченное ступенчатое открытие, защиты 31/33 | Свежий 418 → штатный регулятор с нулевого расчётного положения |
| Нет 418 и пола | Горячий вход закрыт, насос рециркулирует, NO_FEEDBACK_UNCOVERED | Исправный 418 или пол + проверка циркуляции |
| Нет 411/419, OT invalid, холодный источник | Предупреждение, доступное регулирование/циркуляция продолжаются | Автоматически; 504 не пишет котлу |
| Нет роста температуры | NO_RESPONSE warning, без latch/OFF/снятия demand | Фактический рост или достижение цели |
| Ошибка выходной записи | Повтор команд и уведомление, запрос не считается готовым | Следующая успешная выдача |

При одновременной потере 418 и пола **теплоснабжение трассы не гарантировано**:
рециркуляция с закрытым горячим входом не заменяет подпитку теплом. Минимальная
аппаратная мера для проверки — независимое термостатическое ограничение смешанной
подачи/резервный датчик 418 с подтверждённой схемой. Альтернатива по 411/419 требует
измеренной связи этих температур с максимально возможной подачей при заданном
открытии 562; такой связи в GitHub нет, автоматическое открытие по ней не выдумано.
Полный отказ WB/электропитания требует независимой механики/питания, не JS.

## Термозащита и тайминги

| Измерение | Команда |
|---|---|
| 418 ≥45 | Закрыть горячий вход, насос ON |
| 418 ≥48, свежая проба после закрытия и выдержки | Насос OFF + событие |
| 418 ≥50 | Немедленный stop при обработке MQTT sample, без выдержки |
| Пол ≥31 | Закрыть горячий вход, насос ON |
| Пол ≥33, свежая проба после закрытия и выдержки | Насос OFF + событие |

Проверки raw выполняются до фильтра MixingController; самое жёсткое действие имеет
приоритет. Причины защиты и stop сохраняются при reload, но это не ручная защёлка.
Для возврата каждый датчик, вызвавший защиту, должен быть снова свежим и устойчиво
ниже своего порога закрытия минус hysteresis. Новая проба обязательна: старый sample,
пропавший датчик, скачок часов или длительный разрыв выполнения не доказывают охлаждение.
После остывания — насос ON, горячий вход закрыт, наблюдение на циркуляции, затем регулирование.
Повторный перегрев снова срабатывает, без обхода защиты кнопкой.

Числа контракта: 35/40/45/48/50, 30 автономии, 31/33 пола.
Остальные значения в HM2504Config — **предложенные стартовые инженерные настройки
для review/стенда/ПНР**: выдержка закрытия 10 с, остывание 120 с, hysteresis
3 °C подачи / 2 °C пола, проверка циркуляции 60 с, выбег 120 с, NO_RESPONSE 900 с/1 °C,
margin источника 5 °C, отдельный объектный tuning общего регулятора.
Это не результаты физических измерений. Цели пола 25/29 сохранены, максимум 30 <31.
Настройка, нарушающая порядок порогов/тайминги, отвергается до запуска.

## Точные незаполненные физические параметры

- valveClosedLevel, valveOpenLevel, valveClosedEnable: измерить направление/диапазон
  562 и команду удержания закрытого горячего входа, в том числе влияние Switch.
  Пока null, единственная кнопка первого ввода не может включить writer.
- floorOnlyMaxPct: измерить допустимую долю открытия при горячем источнике и
  инерции датчика стяжки. Пока null, этот конкретный режим сохраняет циркуляцию,
  закрывает горячий вход и сообщает FLOOR_CAP_UNMEASURED. Штатный режим с 418
  может быть проверен независимо после внесения шкалы.
- Доставка notification_json в действующий канал уведомлений: существующий адаптер
  на объекте не известен. Событие с объектом/причиной/временем и журнал реализованы,
  повтор одинакового события подавляется; доставка человеку не объявляется проверенной.
  Никаких выдуманных credentials и persistent очередей.

Все вычислительные ветки и writer реализованы и тестируются с **синтетической**
измеренной шкалой/ограничением; её числа не перенесены в эксплуатационную конфигурацию.

## MQTT и runtime

Сохранён wire protocol **v2**, отдельно от версии инженерного контракта v1.0.
Topic /neiro/ivolga/504/v2/frame, QoS 0, retain=false, exact outbound bridge/ACL.
session_id — persistent integer, не wall clock; seq/TTL/receiver-local age, допуск
будущего sent_ms 2 с. Повторная валидация: ≥5 с локально, продвижение sent_ms ≥1 с,
последний sent_ms ≥первое получение+3 с. Replay/duplicate не обновляют TTL;
наблюдаемый rollback/expiry инвалидирует cache. SETTINGS_INVALID продолжает heartbeat
с null tuple без defaults, manager использует автономный ограниченный режим при 418.
enabled=false/OFF старого sender более не является эксплуатационной командой;
sender/module/UI обновляются согласованно одним пакетом.

На обоих WB нужен **wb-rules >=2.42.0**, добавивший retained/qos:
[официальный changelog](https://github.com/wirenboard/wb-rules/blob/master/debian/changelog).
Missing/nonboolean retained — явная русская диагностика, не false. Соответствующий
канал не считается свежим до reload исправленного runtime; другие исправные каналы
могут обеспечить автономию/резерв. Sensors TTL 120 с требует проверки публикаций
неизменного значения. ACL/TLS обеспечивает происхождение; source не подпись.

## 504 → арбитр → источник и границы

Статический запрет выбора 504 удалён. Арбитр проверяет атомарный request, TTL ≤15 с,
state/valid/demand/path/fault; выбирает MAX, при равенстве **503 >502 >501 >504**.
Текст selected_reason для прежних победителей сохранён ради совместимости.
504 не ждёт grant источника для локальной циркуляции и не выключает соседей.
Source whitelist принимает 504; **это единственное изменение source manager**.

Существующий source код #40 сохраняет прежние commissioning gates, OT interlock,
непроверенный NO_DEMAND и возможность диагностического latch. Он не переписан
в рамках 504 и не объявляется надёжным production source. Тест показывает приём
запроса и запись уставки при синтетически заданных существующих разрешениях;
при OT loss новая запись не выполняется, 504 сохраняет местную работу.
После reboot источника полное автоматическое теплоснабжение ещё зависит от #40.
Физический CH/NO_DEMAND котла, независимость ГВС и единоличный OT writer требуют
полевой проверки. 504 не пишет CH enable, ГВС, 505/507/620 или outputs 501–503.
Не выкладывать старый source/main поверх live: только проверенный точечный diff.
