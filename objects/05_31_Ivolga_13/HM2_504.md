## Комбо-термостат и интерфейсы

Тест сравнивает алгоритм с настоящими `calculateComboDecision`, `updateAirMode`,
`calculateFloorCommand` из `objects/05_38_Plod_47/etc/wb-rules/600_thermostats.js`.
Воздух с гистерезисом ±0.3 °C выбирает цель пола. Пол включает demand при цель−1 °C,
выключает при достижении цели. Нормальный воздух не запрещает поддержание пола.
22/25/29 — начальные уставки интерфейса, **не подтверждённые safety limits 504**.

| Случай | Результат |
|---|---|
| Нет воздуха | DEGRADED, поддержание по исправному полу |
| Нет пола | invalid, demand OFF; намеренное отличие от reference, допускающего нагрев только по воздуху |
| Нет обоих | invalid, demand OFF |
| Неверные уставки / hold > heat | Блокировка, heartbeat SETTINGS_INVALID каждые 5 с, valid=false/demand=false |
| Нет булевого trackMqtt.retained | RUNTIME_UNSUPPORTED, русская диагностика, valid=false/demand=false |
| OFF | Валидное отсутствие запроса, без физической команды |

Уставки и target_state сохраняет штатное хранилище virtual controls
(`forceDefault=false`); расчётное состояние и sensor freshness сбрасываются.
Сохранённый HEAT не обходит новые измерения, две публикации и blocked manager.
Недостоверная температура в UI остаётся последним числом: смотреть `air_valid`,
`floor_valid` и состояние. Sprut-шаблон не показывает validity автоматически;
диагностику нужно отображать отдельно. При подключении Sprut проверить `init:true`
опций до изменения сохранённых уставок. Fluxa должна менять только локальные
уставки и target_state, а не demand/выходы/удалённые `/on`.

## Транспорт v2

Раз в 5 с отправляется один JSON в `/neiro/ivolga/504/v2/frame`, QoS 0, retain=false.
Bridge сохраняет имя, только `out`, без wildcard, `/devices` и metadata.
Поля: `v=2`, `source=ivolga-besedka-504`, `session_id`, `seq`, `sent_ms`, `ttl_ms=30000`,
`air`, `floor`, `target`, `hold`, `heat`, `enabled`, `valid`, `demand`, `mode`, `reason`.
Лишние поля и неверные типы отвергаются, недостоверные air/floor — null.
`source` — идентификатор протокола, **не криптографическая подпись**; происхождение
должны обеспечивать dedicated identity + ACL/TLS. Без их сверки APPLY запрещён.

session_id — сохраняемый целочисленный счётчик запусков, независимый от Date.now().
Старый v1 boot_ms не используется; повреждённый/исчерпанный счётчик запрещает запуск.
Нельзя очищать или откатывать storage для обхода проверки сессии. v1 отвергается:
модуль на обоих WB, sender, manager и exact-topic configs должны соответствовать v2.

Приёмник отвергает retained, регресс session/seq и дубликаты до проверки времени.
Дубликат не продлевает TTL. Допуск будущего sent_ms — 2000 мс; возраст ≥30000 мс
отвергается. После старта/отката локальных часов нижний барьер sent_ms равен
времени этого события минус 2000 мс. Локальный TTL получения строго 30 с.
После старта, новой сессии, outage или регресса времени sender нужна повторная
валидация: ≥5 с по часам receiver, продвижение sent_ms ≥1 с и последний sent_ms
не раньше первого локального получения +3 с. Это учитывает допуск ±2 с, но не
позволяет очереди в один момент или близкому к старту replay сразу подтвердить поток.

Наблюдаемый откат часов receiver немедленно сбрасывает freshness и валидацию,
сохраняя старшие session/seq. Наблюдаемое истечение TTL не отменяется возвратом часов.
После синхронизации времени свежий поток проходит валидацию автоматически без reboot.
Это fail-closed обработка наблюдаемых скачков wall clock, не аппаратные монотонные
часы и не защита от взломанного publisher. Синхронизация обоих WB обязательна.

При SETTINGS_INVALID heartbeat имеет mode=BLOCKED, valid=false, demand=false,
target/hold/heat/enabled=null: значения по умолчанию не подставляются. Приёмник
сохраняет свежесть и точную причину ошибки вместо ложного MQTT_STALE; исправление
уставок автоматически возвращает обычную диагностику.

Sensor freshness приходит из non-retained raw-topic `trackMqtt` и `/meta/error`:
retained не подтверждает свежесть; очистка ошибки требует следующего измерения.
Диагностический TTL 120 с требует сверки: фильтрация неизменных значений драйвером
может давать ложный stale. Чтение старого числа из dev не обновляет freshness.
Документация: [wb-rules](https://github.com/wirenboard/wb-rules#подписка-на-mqtt-топики-trackmqtt),
[Mosquitto](https://mosquitto.org/man/mosquitto-conf-5.html).
Не добавлять `bridge_outgoing_retain false`: он маскирует retain bit.
QoS 0 не накапливает очередь команд; очередной heartbeat содержит полный снимок.
Clean session, notifications=false и отсутствие inbound ограничивают трафик.

## Минимальный runtime

На обоих WB требуется **wb-rules >= 2.42.0**: параметры retained/qos добавлены
30.05.2026 в [официальном changelog](https://github.com/wirenboard/wb-rules/blob/master/debian/changelog).
До установки обязателен read-only version check из DEPLOY_504.md; неизвестная или
старая версия блокирует установку. Обновление WB автоматически не выполняется.
Отсутствующий/небулев retained никогда не преобразуется в false: callback фиксирует
RUNTIME_UNSUPPORTED до reload и выводит русскую причину в runtime_status/state/status.
Отсутствие callback означает ожидание проверки, а не подтверждённую совместимость;
булев callback подтверждает возможность API, но не заменяет проверку версии пакета.

## Менеджер и DECISION_REQUIRED

Всегда UNKNOWN, valid/demand/path=0, запросы температур=0. Публикация начинается
с invalid, request_json — атомарный снимок, request_timestamp — последний marker.
`remote_demand` только диагностический. Тренд 418 не доказывает теплоперенос.
Outage даёт `DEGRADED_POLICY_NOT_CONFIRMED`, связь автоматически возвращается к
blocked normal. Приоритет: сохранённая fault, локальный `RUNTIME_UNSUPPORTED`,
`LOCAL_SENSOR_INTERLOCK`, freshness связи, затем удалённые `SETTINGS_INVALID`,
`REMOTE_RUNTIME_UNSUPPORTED` или `REMOTE_SENSOR_INTERLOCK`.
Сохранённая latch `ivolga_504_safety/fault` не очищается
при reload; reset отклоняется без подтверждённых условий восстановления.
Каркас не создаёт thermal fault по выдуманным пределам и не останавливает чужой writer.

**Автономный нагрев, hard-max, COLD_SLAB/watchdog и физический writer не реализованы
как production-контур.** PROFILE=null, адаптер общего MixingController принимает
только явно заданный tuning; callbacks работают исключительно в памяти.
Все gates readonly и принудительно OFF. Изменение одного control не включает физику.

Минимальные решения перед дальнейшей реализацией:

1. Live ownership трёх выходов 504; текущий installed manager/аварии.
2. Направление/шкала 562, открытие Level → Switch ON; отдельно stop насос OFF →
   Level 0 → Switch OFF, последствия ошибок и реальная реакция.
3. Цель/hard max подачи, max источника, предел поверхности пола, hysteresis reset,
   полный tuning 504 без копирования чисел 501/502.
   Manager обязан независимо проверять сырую подачу до MixingController и manual:
   общий модуль проверяет hard-max после фильтра, а freeze обрабатывает раньше него.
4. Автономная политика outage: длительность, цель/предел подачи, независимые местные
   условия и бюджет нагрева, действие после бюджета, после reboot и явного OFF.
   Нельзя бесконечно держать последний demand или автоматически всегда останавливать.
5. Availability/pressure/flow. Канал давления 421 известен по карте, но пороги,
   safety contract и наличие признака протока 504 не подтверждены.
6. COLD_SLAB_WARMUP_V2: grace, рост от минимума, checkpoint без отката вниз,
   подтверждающие samples/интервал, hot/high-valve budgets, общий timeout, AT_TARGET,
   persist latch/reset. Пока response_status=NOT_COMMISSIONED, не «успешный watchdog».
7. Source whitelist и tie-break, отдельный review кода/тестов. #40 здесь не меняется.

Пакет нельзя превратить в production переключателем: после получения фактов нужен
следующий проверенный код физического допуска и автономной политики.

## Арбитр и проверки

Статический `ENABLE_504_SELECTION=false`: новый кандидат в candidates_json с
FEATURE_DISABLED/validation_reason, grant_504 REJECTED. Active/rejected counters
при OFF относятся к прежним трём участникам; четвёртый — только диагностика.
504 независимо проверяется по atomic JSON, fault/state/valid/demand/path, TTL ≤15 с,
future/stale timestamp, числовой температуре. Под синтетическим gate 504 стоит
последним при равенстве: предложение под gate, не утверждённая policy.
Live arbiter может отличаться; установка только после отдельного diff.

`node objects/05_31_Ivolga_13/Tools/test_hm2_504.js`: **37 групп PASS**, включая
250 сравнений с базовым arbiter и node --check четырёх runtime JS. Proxy запрещает
любые writes вне собственного VD. Проверены combo/reference/fallback, settings,
errors/TTL, оба reboot, MQTT outage/reconnect/retained/stale/future/duplicate,
gates, сохранённая latch, atomic TTL/fault/tie. Overheat/watchdog сценарий доказывает
только non-writing блокировку, не ещё отсутствующие thermal safety/watchdog.
14 добавленных групп проверяют независимость сессии от часов, повреждение счётчика,
skew/TTL, drift/NTP/replay/reboot, отсутствие воскресания sensor cache,
небулев retained и русскую диагностику обоих scripts, SETTINGS_INVALID и восстановление.
Это локальный Node harness, не независимый CI и не live-проверка wb-rules.

Mosquitto отсутствует в PATH: проверен whitelist текста, не parser, не два брокера,
не TLS/ACL. WB runtime, real flash latch, Sprut/Fluxa, теплоперенос, live ownership
не проверялись. SSH, deploy, physical writes, restart и merge не выполнялись.
