# Архитектура объектовых скриптов — 04 22 Даниловский

Статус: **предварительное проектирование, 2026-09-24**.

На этом этапе исполняемые JS-файлы **не создаются**. Документ определяет будущую структуру, ownership и список функций, которые должны быть реализованы после завершения карты каналов.

## 1. Цель

Существующие три правила с контроллера не развиваем. Они остаются источником сведений о каналах и старой ПНР.

Новая логика должна:

- реализовать актуальное `Задание на выключатели ДЗ11-102.docx`;
- использовать фактические MQTT-каналы из текущих конфигов;
- учитывать всё установленное оборудование, а не только освещение;
- не зависеть от RAM-счётчиков вида `pressCount`, которые сбиваются при перезапуске `wb-rules`;
- не создавать конкуренцию между локальными действиями WB-MR6C и JavaScript;
- оставлять аппаратные защитные функции специализированных модулей на самих модулях там, где это безопаснее (прежде всего WB-MWAC).

## 2. Базовые принципы

### 2.1. Каналы храним централизованно

Планируемый модуль:

```text
Wirenboard/wb-rules-modules/danilovsky/channels.js
```

В нём будут только:

- MQTT device/control names;
- группы света;
- входы кнопок;
- комнаты;
- параметры по умолчанию и подтверждённые настройки.

Ни один рабочий скрипт не должен размазывать строки вроде `wb-led_52/CCT2` по коду без необходимости.

### 2.2. Не используем `pressCount` как состояние света

Старый код переключает свет по локальным переменным `pressCount`. После рестарта `wb-rules`, ручного управления из WebUI или изменения состояния другим сценарием такой счётчик расходится с реальностью.

В новой реализации:

- простой toggle рассчитывается от фактического состояния группы;
- режимы `день/ночь/выкл` имеют отдельное явно хранимое состояние;
- `last mode` берётся из реального/виртуального состояния света, а не из номера нажатия с момента запуска процесса;
- при рестарте скрипт синхронизируется с текущими outputs и не включает свет самопроизвольно.

### 2.3. Локальные связи WB-MR6C сначала аудируем

Сейчас часть кнопок уже управляет реле внутри модулей без JavaScript.

Перед вводом нового скрипта по каждой функции выбирается один вариант:

1. **оставить local binding** как единственного владельца простого действия;
2. **перенести действие в JS** и удалить/нейтрализовать local binding;
3. **осознанно разделить** функцию: например, локальный toggle основного реле + JS добавляет LED-группу.

Случайное одновременное управление одним выходом локальной прошивкой и JS запрещено.

### 2.4. Специализированная защита остаётся аппаратной

WB-MWAC должен самостоятельно закрывать краны при протечке. JavaScript не должен быть единственным уровнем защиты от воды.

JS добавляет:

- именованные зоны;
- уведомления;
- диагностику;
- отображение;
- сервисные команды, если они понадобятся.

### 2.5. Не придумываем неизвестные каналы

WB-MR6CU 162, WB-MAP6S 27, часть WB-MWAC 151 и WB-MSW 56 пока требуют полевой идентификации. Архитектура предусматривает их, но команды на неподтверждённые физические outputs не проектируются как факт.

## 4. Общие модули

### `channels.js`

Единый registry:

- кнопка → MQTT input event;
- группа → switch/brightness/temperature/palette controls;
- вентиляторы;
- WB-MSW;
- WB-MWAC;
- WB-MAP6S;
- ONOKOM.

Неподтверждённые поля помечаются `TODO`, а не заполняются предположениями.

### `lighting.js`

Низкоуровневые операции:

- `setGroupOn/Off`;
- `toggleGroup`;
- `setBrightness`;
- `changeBrightness(stepPct)`;
- установка CCT-профиля;
- установка RGB-профиля;
- синхронное управление набором групп;
- режимы `day`, `night`, `off`;
- «включить дополнительную группу, но не выключать её вместе с основной»;
- восстановление последнего режима.

Параметры яркости/цветовой температуры режимов `day/night` должны быть вынесены в настройки, а не зашиты в обработчики кнопок.

### `state.js`

Виртуальные состояния, которые действительно нужны логике:

- `home_state = HOME/AWAY`;
- `living_scene = DAY/NIGHT/OFF`;
- `bedroom_scene = DAY/NIGHT`;
- inhibit автоматического повторного пуска вентилятора после ручного выключения;
- последние подтверждённые режимы LED-групп, если их невозможно надёжно восстановить по физическим controls.

Состояния должны переживать restart `wb-rules` либо корректно реконструироваться.

### `notify.js`

Один транспортный слой уведомлений.

На этапе проектирования транспорт не фиксируется: SMS/e-mail/другой механизм выбирается после проверки того, что реально настроено на контроллере.

Скрипты предметных подсистем не должны самостоятельно знать, как отправляется сообщение.

# 5. Исполняемые скрипты

## `00_system_start.js`

Назначение:

- создать объектовые virtual controls;
- проверить наличие необходимых controls;
- синхронизировать программные состояния с фактическими;
- не менять физические outputs при обычном старте;
- записать в журнал версию объектовой конфигурации.

Запрещено:

- при загрузке «на всякий случай» выключать/включать весь свет;
- задавать яркость просто потому, что `wb-rules` перезапустился.

---

## `01_system_health.js`

Покрывает **все установленные модули** на уровне доступности.

План:

- контроль пропадания важных Modbus/MQTT controls;
- состояние ONOKOM `AC connected`;
- ошибки/невалидные показания WB-MSW;
- состояние WB-MWAC;
- доступность WB-MAP6S;
- журналирование недоступного WB-MR6CU 162 до установления его назначения.

Уведомление отправляется по изменению состояния `OK -> fault` и `fault -> OK`, а не циклически каждую минуту.

---

## `10_power_monitor.js` — WB-MAP6S 27

Модуль в системе есть, поэтому энергомониторинг должен быть частью объекта.

После идентификации токовых трансформаторов скрипт должен:

- контролировать напряжение сети;
- фиксировать пропадание/восстановление питания;
- контролировать ток/мощность по подписанным каналам;
- при необходимости выдавать предупреждения о перегрузке;
- отдавать диагностические controls для WebUI.

До полевой идентификации шести каналов:

- не придумывать названия нагрузок;
- не задавать пороги по отдельным линиям;
- не выполнять автоматические отключения потребителей.

Автоматическое отключение нагрузок по WB-MAP6S в исходную архитектуру **не входит** без отдельного решения.

---

## `20_leak_monitor.js` — WB-MWAC v.2, адрес 151

### Аппаратный уровень

WB-MWAC остаётся владельцем:

- обнаружения протечки;
- немедленного закрытия подключённых кранов;
- встроенного аварийного состояния.

### JS-уровень

После идентификации S1…S6 и K1/K2:

- именованные уведомления `Протечка: <зона>`;
- уведомление о восстановлении/сбросе;
- контроль фактического состояния кранов;
- контроль ошибок/неисправности датчиков, если соответствующий control доступен;
- при наличии водосчётчиков — отображение расхода и счётчиков;
- при использовании режима «влажная уборка» — отдельный статус/таймер.

Критическое правило: **после аварии JS не открывает воду автоматически**. Возврат воды — только по утверждённой процедуре/команде пользователя.

- short: 308 + 333.2 + 333.1;

**Открытый вопрос:** в текущем WebUI группа 308 — обычный relay `wb-mr6c_206/K3`, у неё нет control цветовой температуры. Поэтому буквальное требование «синхронизировать 333.1/333.2 по цветности с люстрой 308» сейчас технически не подтверждается доступными каналами. До кода надо выяснить, есть ли у люстры отдельный интерфейс/канал CCT, отсутствующий в WebUI. ## `50_cooling_thermostats.js`

В системе четыре ONOKOM, значит должны быть четыре объектовых термостата охлаждения:

| Помещение | ONOKOM |
|---|---|
| Детская девочки | `ONOKOM-AIR-GR-1-MB-B_2` |
| Кухня-гостиная | `ONOKOM-AIR-GR-1-MB-B_3` |
| Спальня | `ONOKOM-AIR-GR-1-MB-B_4` |
| Детская мальчика | `ONOKOM-AIR-GR-1-MB-B_5` |

Для каждого виртуального термостата:

- `enabled`;
- текущая температура;
- целевая температура;
- состояние охлаждения;
- связь с кондиционером;
- опционально fan speed отдельным control.

Команды:

- `enabled=false` -> `Active=false`;
- `enabled=true` -> `Active=true`, режим охлаждения;
- изменение setpoint -> `Target temperature`;
- состояние/температура читаются обратно из ONOKOM.

Термостат **только на охлаждение**. Никакого отопления через кондиционеры в исходной архитектуре нет.

При `AC connected=false`:

- показать fault/unavailable;
- не спамить повторными командами;
- уведомить один раз через `notify.js`.

`Я ушёл` выключает все четыре; `Я пришёл` включает их с сохранёнными пользовательскими setpoints, без придумывания новой температуры.

Для ONOKOM адреса 3 до реализации надо подтвердить полный набор MQTT controls: WebUI сейчас отображает только `Active`.

# 7. Порядок внедрения

Новые правила не следует писать и включать «всё сразу».

### Этап A — инвентаризация без команд

- закрыть неизвестные input mappings;
- определить WB-MR6CU 162;
- определить WB-MWAC;
- определить MAP6S;
- проверить MSW56/57 и ONOKOM3;
- снять backup `/etc/wb-rules`, `wb-mqtt-serial.conf`, WebUI.

### Этап B — безопасные сервисные функции

1. `01_system_health.js`;
2. `10_power_monitor.js`;
3. `20_leak_monitor.js` только как наблюдение/уведомления, без изменения аппаратной защиты;
4. `50_cooling_thermostats.js` сначала в shadow/read-only представлении, затем команды.

### Этап C — вентиляция и санузлы

- периодические вентиляторы;
- влажность;
- движение;
- расписание ночного света;
- ручные overrides.

### Этап D — освещение по комнатам

По одному файлу и одной комнате/группе сценариев, каждый раз:

1. определить local binding;
2. отключить конфликтующего legacy writer;
3. поставить новый script;
4. проверить single/long/double;
5. проверить управление из WebUI;
6. перезапустить `wb-rules` и убедиться, что состояния не «переворачиваются».

### Этап E — master scenes

`Я ушёл/Я пришёл` включать последними, когда все нижележащие группы и кондиционеры уже имеют подтверждённых owners.
