# Архитектура объектовых скриптов — 04 22 Даниловский

Статус: **предварительное проектирование, 2026-09-24**.

На этом этапе исполняемые JS-файлы **не создаются**. Документ определяет будущую структуру, ownership и список функций, которые должны быть реализованы после завершения карты каналов.

## 1. Цель

Существующие три правила с контроллера не развиваем. Они остаются источником сведений о каналах и старой ПНР.

Новая логика должна:

- реализовать актуальное `Задание на выключатели ДЗ11-102.docx`;
- использовать фактические MQTT-каналы из текущих конфигов;
- учитывать всё установленное оборудование, а не только освещение;
- не зависеть от RAM-счётчиков вида `pressCount`, которые сбиваются при перезапуске `wb-rules`;
- сохранять штатную резервную логику Wiren Board: основной свет должен работать через локальную mapping-матрицу модуля даже при отказе контроллера или `wb-rules`;
- JavaScript должен дополнять локальный биндинг расширенной логикой и не переключать повторно тот же основной выход;
- оставлять аппаратные защитные функции специализированных модулей на самих модулях там, где это безопаснее (прежде всего WB-MWAC).

## 2. Базовые принципы

### 2.1. Реальные каналы задаём в начале каждого скрипта

Общего файла `channels.js` не будет.

Каждый рабочий скрипт должен быть самодостаточным: открыл один файл — сразу видно, какие физические входы и выходы он использует.

В начале каждого скрипта делаем раздел с переменными реальных MQTT-каналов. Рядом обязательный русский комментарий с понятным назначением.

Пример:

```js
// ===== КАНАЛЫ СПАЛЬНИ =====

var BUTTON_210_SHORT = "wb-mr6c_156/Input 1 Single Press Counter"; // Кнопка 210, короткое нажатие
var LIGHT_312 = "wb-mr6c_156/K1";                                // Основной свет спальни
var LIGHT_311 = "wb-led_42/CCT1";                                // Подсветка потолка и мебели в спальне
var LIGHT_311_1 = "wb-led_23/CCT2";                              // Вертикальная подсветка спальни
var LIGHT_338 = "wb-mr6c_156/K4";                                // Настенный свет спальни
```

Правила:

- все переменные каналов объявляются в начале того скрипта, который ими пользуется;
- комментарии к каналам и логике — на русском;
- длинные MQTT-имена дальше по коду по возможности не повторяются;
- неподтверждённый канал не маскируется красивым именем: рядом явно пишется `ТРЕБУЕТ ПРОВЕРКИ`;
- общая карта объекта остаётся в `PHYSICAL_CHANNEL_MAP.md`, но для чтения рабочего скрипта переходить в неё не должно требоваться.

### 2.2. Не используем `pressCount` как состояние света

Старый код переключает свет по локальным переменным `pressCount`. После рестарта `wb-rules`, ручного управления из WebUI или изменения состояния другим сценарием такой счётчик расходится с реальностью.

В новой реализации:

- простой toggle рассчитывается от фактического состояния группы;
- режимы `день/ночь/выкл` имеют отдельное явно хранимое состояние;
- `last mode` берётся из реального/виртуального состояния света, а не из номера нажатия с момента запуска процесса;
- при рестарте скрипт синхронизируется с текущими outputs и не включает свет самопроизвольно.

### 2.3. Локальный биндинг — штатная резервная логика

На Даниловском прямые связи кнопок с основным светом в WB-MR6C сохраняются намеренно.

Требование заказчика:

> Пока контроллер и `wb-rules` работают — действует полная объектовая логика. Если контроллер или правила отказали, основной свет всё равно должен включаться и выключаться непосредственно самим модулем Wiren Board через mapping-матрицу.

Поэтому локальный биндинг **не считается конфликтом сам по себе**.

Типовая схема:

1. короткое нажатие кнопки локально переключает основной свет;
2. JavaScript получает событие того же нажатия;
3. JavaScript добавляет LED-подсветки, дополнительные группы, режимы, сценарии и другие функции;
4. JavaScript **не переключает второй раз тот основной выход, который уже переключил модуль**.

Пример для спальни:

```text
210 короткое
→ WB-MR6C 156 Input 1 локально переключает K1 = гр.312
→ скрипт по этому же нажатию управляет гр.311, 311.1 и дополнительной логикой гр.338
```

При ПНР для каждой кнопки фиксируем отдельно:

- какой физический вход срабатывает;
- какой выход модуль переключает локально;
- что дополнительно должен сделать JavaScript.

Локальный биндинг меняем или удаляем только если он сам противоречит ТЗ либо мешает штатной резервной работе.

### 2.4. Специализированная защита остаётся аппаратной

WB-MWAC должен самостоятельно закрывать краны при протечке. JavaScript не должен быть единственным уровнем защиты от воды.

JS добавляет:

- именованные зоны;
- уведомления;
- диагностику;
- отображение;
- сервисные команды, если они понадобятся.

### 2.5. Не придумываем неизвестные каналы

WB-MR6CU 162, WB-MAP6S 27, часть WB-MWAC 151 и WB-MSW 56 пока требуют полевой идентификации. Архитектура предусматривает их, но команды на неподтверждённые физические outputs не проектируются как факт.

Количество предметных скриптов сохраняем: разбиение по подсистемам и помещениям удобно для ПНР и обслуживания.

```text
objects/04_22_Danilovsky/

   └─ wb-rules/
```

Если позже действительно появится большой повторяющийся кусок кода, его можно вынести отдельно после появления практической необходимости, а не заранее.

## 4. Единый порядок внутри каждого скрипта

Каждый скрипт оформляем одинаково:

```js
// ============================================================================
// 1. НАЗНАЧЕНИЕ СКРИПТА
// Коротко: что именно делает этот файл и какие кнопки/устройства обслуживает.
// ============================================================================

// ============================================================================
// 2. ФИЗИЧЕСКИЕ КАНАЛЫ
// ============================================================================

var ... = "..."; // Русское понятное назначение
var ... = "..."; // Русское понятное назначение

// ============================================================================
// 3. НАСТРОЙКИ
// Пороги, времена, яркости, шаги регулировки.
// ============================================================================

// ============================================================================
// 4. ВСПОМОГАТЕЛЬНЫЕ ФУНКЦИИ ЭТОГО СКРИПТА
// Только то, что нужно именно этому файлу.
// ============================================================================

// ============================================================================
// 5. ПРАВИЛА
// Для каждого правила по-русски: какая кнопка/событие и что должно произойти.
// ============================================================================
```

Требования к читаемости:

- названия переменных могут быть короткими техническими, но комментарий рядом всегда объясняет назначение по-русски;
- перед каждым заметным куском логики пишем русский комментарий: какая кнопка, какое нажатие, какой результат;
- не прячем простую объектовую логику в общих библиотеках;
- если основной свет уже переключается локальной mapping-матрицей, в комментарии прямо пишем это и в JS повторно этот выход не трогаем;
- все числовые настройки, которые могут меняться на ПНР, собираем в начале файла в разделе «НАСТРОЙКИ».

# 5. Исполняемые скрипты

## `00_system_start.js`

Назначение:

- создать объектовые virtual controls;
- проверить наличие необходимых controls;
- синхронизировать программные состояния с фактическими;
- не менять физические outputs при обычном старте;
- записать в журнал версию объектовой конфигурации.

Запрещено:

- при загрузке «на всякий случай» выключать/включать весь свет;
- задавать яркость просто потому, что `wb-rules` перезапустился.

---

## `01_system_health.js`

Покрывает **все установленные модули** на уровне доступности.

План:

- контроль пропадания важных Modbus/MQTT controls;
- состояние ONOKOM `AC connected`;
- ошибки/невалидные показания WB-MSW;
- состояние WB-MWAC;
- доступность WB-MAP6S;
- журналирование недоступного WB-MR6CU 162 до установления его назначения.

Уведомление отправляется по изменению состояния `OK -> fault` и `fault -> OK`, а не циклически каждую минуту.

---

## `10_power_monitor.js` — WB-MAP6S 27

Модуль в системе есть, поэтому энергомониторинг должен быть частью объекта.

После идентификации токовых трансформаторов скрипт должен:

- контролировать напряжение сети;
- фиксировать пропадание/восстановление питания;
- контролировать ток/мощность по подписанным каналам;
- при необходимости выдавать предупреждения о перегрузке;
- отдавать диагностические controls для WebUI.

До полевой идентификации шести каналов:

- не придумывать названия нагрузок;
- не задавать пороги по отдельным линиям;
- не выполнять автоматические отключения потребителей.

Автоматическое отключение нагрузок по WB-MAP6S в исходную архитектуру **не входит** без отдельного решения.

---

## `20_leak_monitor.js` — WB-MWAC v.2, адрес 151

### Аппаратный уровень

WB-MWAC остаётся владельцем:

- обнаружения протечки;
- немедленного закрытия подключённых кранов;
- встроенного аварийного состояния.

### JS-уровень

После идентификации S1…S6 и K1/K2:

- именованные уведомления `Протечка: <зона>`;
- уведомление о восстановлении/сбросе;
- контроль фактического состояния кранов;
- контроль ошибок/неисправности датчиков, если соответствующий control доступен;
- при наличии водосчётчиков — отображение расхода и счётчиков;
- при использовании режима «влажная уборка» — отдельный статус/таймер.

Критическое правило: **после аварии JS не открывает воду автоматически**. Возврат воды — только по утверждённой процедуре/команде пользователя.

### Замечание к старому скрипту яркости

Старое правило ставит ночью 10%, а днём 50%. **10% подтверждено ТЗ; 50% в ТЗ не зафиксировано.** В новой версии дневную яркость нельзя жёстко задавать 50% без отдельного решения.

223 и 231:

- short: 308 + 333.2 + 333.1;

**Открытый вопрос:** в текущем WebUI группа 308 — обычный relay `wb-mr6c_206/K3`, у неё нет control цветовой температуры. Поэтому буквальное требование «синхронизировать 333.1/333.2 по цветности с люстрой 308» сейчас технически не подтверждается доступными каналами. До кода надо выяснить, есть ли у люстры отдельный интерфейс/канал CCT, отсутствующий в WebUI. Если нет — синхронизация должна трактоваться как общий программный режим DAY/NIGHT, а не чтение CCT из 308.

- выключить все четыре кондиционера;
- выключить кухонный вентилятор и остальные вентиляторы;
- установить `home_state=AWAY`.

Перед реализацией список «всего освещения» фиксируется прямо в начале `44_master_scenes.js` отдельными переменными с русскими комментариями.

### 236 long — `Я пришёл`

Срабатывает только если состояние `AWAY`.

ТЗ требует привязку к световому дню.

Светлое время:

- ON 333.4, 301.2, 333, 333.2, 3333, 311, 311.1;
- включить кондиционеры.

Тёмное время:

- ON 301, 302, 308, 333.1, 333.2, 333.4, 301.2, 333, 3333, 311, 311.1;
- включить кондиционеры;
- LED-группы включать в режиме DAY.

После выполнения: `home_state=HOME`.

Источник «светлого времени» должен быть один: астрономический календарь/расчёт восхода-заката. Конкретная реализация выбирается при написании скрипта; фиксированные часы вместо календаря без отдельного решения не использовать.

## `50_cooling_thermostats.js`

В системе четыре ONOKOM, значит должны быть четыре объектовых термостата охлаждения:

| Помещение | ONOKOM |
|---|---|
| Детская девочки | `ONOKOM-AIR-GR-1-MB-B_2` |
| Кухня-гостиная | `ONOKOM-AIR-GR-1-MB-B_3` |
| Спальня | `ONOKOM-AIR-GR-1-MB-B_4` |
| Детская мальчика | `ONOKOM-AIR-GR-1-MB-B_5` |

Для каждого виртуального термостата:

- `enabled`;
- текущая температура;
- целевая температура;
- состояние охлаждения;
- связь с кондиционером;
- опционально fan speed отдельным control.

Команды:

- `enabled=false` -> `Active=false`;
- `enabled=true` -> `Active=true`, режим охлаждения;
- изменение setpoint -> `Target temperature`;
- состояние/температура читаются обратно из ONOKOM.

Термостат **только на охлаждение**. Никакого отопления через кондиционеры в исходной архитектуре нет.

При `AC connected=false`:

- показать fault/unavailable;
- не спамить повторными командами;
- выдать однократное объектовое уведомление выбранным для объекта способом.

`Я ушёл` выключает все четыре; `Я пришёл` включает их с сохранёнными пользовательскими setpoints, без придумывания новой температуры.

Для ONOKOM адреса 3 до реализации надо подтвердить полный набор MQTT controls: WebUI сейчас отображает только `Active`.

# 7. Порядок внедрения

Новые правила не следует писать и включать «всё сразу».

### Этап A — инвентаризация без команд

- закрыть неизвестные input mappings;
- определить WB-MR6CU 162;
- определить WB-MWAC;
- определить MAP6S;
- проверить MSW56/57 и ONOKOM3;
- снять backup `/etc/wb-rules`, `wb-mqtt-serial.conf`, WebUI.

### Этап B — безопасные сервисные функции

1. `01_system_health.js`;
2. `10_power_monitor.js`;
3. `20_leak_monitor.js` только как наблюдение/уведомления, без изменения аппаратной защиты;
4. `50_cooling_thermostats.js` сначала в shadow/read-only представлении, затем команды.

### Этап C — вентиляция и санузлы

- периодические вентиляторы;
- влажность;
- движение;
- расписание ночного света;
- ручные overrides.

### Этап D — освещение по комнатам

По одному файлу и одной комнате/группе сценариев, каждый раз:

1. определить физический вход кнопки;
2. зафиксировать штатный локальный биндинг основного света;
3. определить, что именно должен добавлять JavaScript поверх локального биндинга;
4. отключить только старый JS, который заменяется новой логикой;
5. поставить новый скрипт;
6. проверить короткое/длинное/двойное нажатие;
7. проверить работу основного света при остановленном `wb-rules`;
8. проверить управление из WebUI;
9. перезапустить `wb-rules` и убедиться, что состояния не «переворачиваются».

### Этап E — master scenes

`Я ушёл/Я пришёл` включать последними, когда все нижележащие группы и кондиционеры уже имеют подтверждённых owners.

1. Неизвестные физические кнопки: 202, 205, 207, 209, 212, 221, 222, 223, 233, 234 и возможные параллельные входы.
2. Назначение WB-MR6CU 162.
3. Карта WB-MWAC 151.
4. Карта измерительных каналов WB-MAP6S 27.
5. Подтверждение WB-MSW 56 как датчика ванной.
6. Числовые параметры DAY/NIGHT для CCT-групп.
7. Пастельная RGB-палитра.
8. Однозначная трактовка кнопки 221.
9. Источник цветовой температуры для люстры 308 либо решение, что синхронизация выполняется по программному режиму.
10. Полные MQTT controls ONOKOM адреса 3.

Это не означает, что весь объект заблокирован. Скрипты будут внедряться по подсистемам после закрытия относящихся к ним пунктов.
