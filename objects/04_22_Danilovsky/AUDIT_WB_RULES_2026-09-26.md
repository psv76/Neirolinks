## 1. Основание и границы аудита

Проверены фактические файлы, снятые с работающего контроллера, против:

- `Задание на выключатели ДЗ11-102(1).docx` — функциональное задание;
- `PHYSICAL_CHANNEL_MAP.md` — подтверждённая карта исполнительных каналов и физических входов;
- `BUTTON_IMPLEMENTATION_MAP.md` — карта локальной аппаратной логики и программных дополнений;
- `WB_coding_standard.md` — правила разработки wb-rules для проекта;
- уже принятых объектовых решений по спальне и мастер-сценам.

В snapshot сохранено **30 файлов**:
- 26 активных;
- 4 файла `.disabled`;
- из активных: 23 файла содержат рабочую/диагностическую логику, `rules.js` — штатная заглушка, `alarms.conf` пустой.

Важно: snapshot содержит только `/etc/wb-rules`. Если бригада после 24.09 меняла mapping-матрицы модулей, такие изменения должны отдельно подтверждаться актуальным `wb-mqtt-serial.conf` или полевым тестом.

### Статусы

- **OK** — соответствует ТЗ с учётом подтверждённой локальной логики.
- **PARTIAL** — реализована только часть требования.
- **ERROR** — активная логика использует неверный вход/канал либо противоречит ТЗ.
- **MISSING** — требуемой функции сейчас нет.
- **BLOCKER** — корректная реализация требует решения человека или изменения физической схемы.
- **VERIFY** — для окончательного вывода нужна проверка текущей mapping-матрицы/полевой тест.

Приоритет:
- **P0** — может давать неправильное физическое действие или конфликт одновременно работающих правил;
- **P1** — обязательная функция отсутствует или реализована неполно;
- **P2** — сопровождение, журналирование, структура и чистка после ПНР.

## P0-02 — кнопка 205: ТЗ, физика и активные скрипты описывают разные группы

ТЗ для 205:
- short → `320.1 + 319`;
- long → +5% для `325.1 + 325.2 + 320.1`;
- double → цветовой цикл `325.1 + 325.2 + 320.1`.

Физическая кнопка 205 подключена к `wb-led_224/Input 1` и `wb-led_245/Input 1`; локальная логика этих модулей уже воздействует на группы **324** и **325.1**.

Активные JS дополнительно:
- short синхронизирует `325.2` с `325.1`;
- long изменяет яркость `325.1 + 325.2 + 324`;
- double меняет палитру `325.1 + 325.2 + 324`.

То есть реальное действие сейчас не совпадает с текстом ТЗ и при long/double накладывается на локальную логику WB-LED.

**Действие:** BLOCKER. До решения заказчика/проектировщика не переписывать по догадке.

## P0-03 — 221 long и «Я пришёл» работают от одного физического входа

- `221 длинное нажатие.js`;
- `44_master_scenes.js` с «Я пришёл».

Когда состояние квартиры AWAY, одно long-событие может запустить **оба сценария**. Это уже не только ограничение ТЗ, а активный конфликт двух правил.

Дополнительно `221 длинное нажатие.js` не делает полноценный toggle пары 301+302: через 300 мс он просто приравнивает состояние 301 к текущему состоянию 302.

**Действие:** отключить один из конкурирующих long-сценариев до принятия решения по 221/236.

# 6. Общие проблемы кода

## 6.1. Код раздроблен по отдельным нажатиям

Сейчас большинство функций оформлено файлами вида:
- `201 длинное нажатие.js`;
- `202 двукратное.js`;
- `231 длинное нажатие.js`.

Для эксплуатации объекта это хуже комнатной структуры: физические каналы, локальные функции и логика одной комнаты разбросаны по нескольким файлам.

**Целевая структура:** один понятный файл на комнату/подсистему, как уже сделано для спальни.

## 6.2. Нет инженерного журналирования

Большинство новых коротких скриптов вообще не пишет в системный журнал. Это нарушает проектный стандарт и затрудняет ПНР.

Нужен формат:
`[система][скрипт][контекст]; КОМАНДА=...; канал=...; значение=...`.

## 6.3. Общие имена правил

Во многих файлах повторяются имена:
- `relay_sync_input6_single`;
- `brightness_minus_5_0`;
- `rgb_color_cycle`.

В современных wb-rules файлы изолированы по контекстам, поэтому это не считаем самостоятельным P0, но в журнале/диагностике такие имена не объясняют, к какой комнате и кнопке относится правило.

## 6.4. Сценарии на RAM-счётчиках

`pressCount3` и `pressCount5` задают фазу сценария количеством событий, а не фактическим состоянием освещения. После перезапуска wb-rules или ручного изменения света цикл может расходиться с фактом.

## 6.5. Нет проверок значений в dim-скриптах

В dim-файлах выполняется арифметика непосредственно с `dev[channel]`. При недоступном/нечисловом control получится некорректное значение.

## 6.6. `299__input_detector.js` остаётся активным

Для ПНР это полезный диагностический инструмент. После завершения карты входов его лучше отключить или оставить выключаемым по умолчанию, чтобы не засорять журнал постоянным трекингом входов.

# 10. Итог

Текущий контроллер **не следует считать завершённым по ТЗ**.

При этом значительная часть базовых функций уже хорошо закрыта аппаратной локальной логикой: основные релейные включения, несколько short/long функций спальни, душевой, кухни и прихожей. Основная проблема текущего состояния — не отсутствие всего управления, а наложение трёх слоёв:

1. локальных mapping-матриц WB;
2. старых/новых маленьких JS-файлов бригады;
3. наших новых комнатных/мастер-скриптов.

До продолжения ПНР рабочей базой должен оставаться сохранённый snapshot. Исправления вносить по одному помещению, с одним программным владельцем каждого физического канала и с фиксацией результата в GitHub.
