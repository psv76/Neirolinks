# 05 16 Исеть — план перехода на Heating Manager 2.0

Дата: 05.09.2026  
Статус: ревизия v2 после формальной сверки с полным архитектурным аудитом, runtime-аудитом и проектом Heating Manager 2.0

## 1. Цель перехода

Перевести отопление объекта с набора частично пересекающихся скриптов и диагностических ВУ на целевую архитектуру:

```text
потребители тепла
        ↓
нормализованные запросы
        ↓
диспетчер запросов
        ↓
диспетчер источника
        ↓
единственный writer OpenTherm
```

При этом:

- не потерять уже хорошо работающий PID тёплого пола;
- сохранить безопасное поведение при отказах;
- убрать скрытые cross-writes и дублирование ответственности;
- сократить и упорядочить виртуальные устройства;
- спроектировать историю, Grafana и логирование одновременно с алгоритмами;
- выполнить замену на живом контроллере одним контролируемым окном;
- после переключения дорабатывать отдельные модули без переделки общей архитектуры.

## 2. Что считается уже принятым

### [Проверено]

1. `OT11 Heating Setpoint` должен иметь одного writer.
2. K1...K6 должны иметь явных владельцев.
3. Потребитель сообщает потребность, а не пишет котлу уставку.
4. Невалидные данные не превращаются в обычные `0/1`; используется три состояния `ACTIVE / INACTIVE / UNKNOWN`.
5. K5 — рециркуляция ГВС, не heat-demand контур.
6. PID тёплого пола доказал работоспособность при корректных датчиках и должен быть сохранён.
7. Массовые отказы 1-Wire реально происходят; физическая причина будет устраняться на объекте. Software должен корректно диагностировать `UNKNOWN`, а не маскировать проблему.
8. БКН имеет как минимум `IDLE / SUPPORT / ACCELERATED`; `SUPPORT` не обязан отключать отопление.
9. Пакетная/адаптивная внутренняя стратегия источника остаётся заменяемой реализацией `Heat Source Manager`. Общая архитектура от неё не зависит.
10. Пользовательский интерфейс не является редактором внутренних коэффициентов алгоритма.
11. Наблюдаемость и эксплуатационная диагностика проектируются вместе с алгоритмом, а не после запуска.
12. **Жилая зона K4 физически связана с приточной вентиляцией:** часть внутрипольных конвекторов принимает приточный воздух. Запрос жилой зоны нельзя определять только по водяному приводу; требуется учитывать разрешение/состояние воздушного тракта.
13. После `restart wb-rules`, reboot WB или возврата питания старым retained-состояниям нельзя доверять как свежим запросам. Нужен явный `STARTUP_VALIDATION`.
14. Потеря HA/устаревание зональных команд не должна превращать последнее состояние NO-привода или заслонки в бесконечный heat demand.
15. Режим ДГУ является внешним interlock для отопления: **электрический котёл запрещён при работе от ДГУ**, пока отдельным проектом не доказано обратное. Для вентиляции должен поддерживаться сигнал load-shedding/ограничения.
16. Пожар и протечка должны иметь зарезервированные входы внешних interlock. Конкретные действия нельзя выдумывать до подтверждения event source и проектной матрицы отключений.

## 6. Интерфейс WB после очистки

### 6.1. Эксплуатационный уровень

Не создавать второй набор сервисных ВУ с теми же данными.

Оставить понятные устройства:

1. `Отопление / Состояние`
   - режим системы;
   - активные потребители;
   - победивший запрос;
   - источник;
   - текущая общая подача;
   - требуемая подача;
   - авария/ограничение;
   - только чтение.

2. `ГВС`
   - температура БКН;
   - целевая температура воды;
   - `IDLE / SUPPORT / ACCELERATED`;
   - K1 command/status;
   - пользовательский `Ускоренный нагрев` только если он реально нужен;
   - без ручной уставки котла и внутренних дельт.

3. `Тёплый пол`
   - фактическая подача;
   - эффективная цель;
   - PID output;
   - K2;
   - запрос тепла;
   - валидность датчика;
   - без десятков PID-ползунков.

4. `Источник тепла`
   - состояние;
   - OT command;
   - OT temperature;
   - flame;
   - cycle state;
   - причина перехода;
   - только чтение.

5. `Безопасность отопления`
   - 1-Wire health;
   - OT health;
   - floor transfer;
   - DHW transfer;
   - AHU frost state;
   - текущая блокировка;
   - только чтение.

`House_mode` и `ГВС / Рециркуляция` остаются отдельными уже существующими устройствами.

### 6.2. Сервисные настройки

Отдельное ВУ `Отопление / Сервис`.

В него попадает только параметр, который:

- реально требуется менять при ПНР/эксплуатации;
- имеет понятный смысл;
- имеет безопасный диапазон;
- не может быть надёжно вычислен автоматически.

Внутренние коэффициенты state-machine, антидребезг, безопасные дельты, TTL, PID tuning после завершения ПНР и т.п. по умолчанию остаются в коде.

Если допустимость настройки зависит от другой настройки — предпочтительно убрать лишнюю степень свободы, а не строить сложную валидацию ради ползунка.

## 7. Контракты запросов

Каждый потребитель публикует минимум:

```text
state              ACTIVE / INACTIVE / UNKNOWN
valid              0/1
requested_supply   °C или NOT_READY
priority_class
grant_required     0/1
reason
updated_at
```

Дополнительные поля только по смыслу конкретного потребителя.

### Жилая зона / внутрипольные конвекторы

[Проверено] По проекту ВиК часть внутрипольных конвекторов жилой зоны одновременно является воздушным путём приточной вентиляции. Поэтому для соответствующей зоны недостаточно видеть только команду водяного NO-привода.

Для зоны с подачей воздуха запрос тепла считается полноценным только при согласовании как минимум трёх составляющих:

```text
свежий запрос комнатного термостата
AND
водяной путь должен быть открыт/разрешён
AND
воздушный путь должен быть разрешён
```

До появления подтверждённого датчика расхода допустим `airflow_estimated`:

```text
заслонка зоны выше минимального порога
AND
ПВУ подтверждённо работает
```

Если помещение просит нагрев, но воздушный путь закрыт/недостоверен:

```text
не повышать температуру источника в попытке компенсировать отсутствие воздуха;
не считать запрос полноценным;
публиковать SUPPRESSED_BY_AIRFLOW или UNKNOWN с причиной.
```

`Heating_living_manager.js` не становится владельцем заслонок HA/Breezart. Он только читает их свежие состояния и формирует корректный тепловой запрос.

Для K3/цоколя это правило применяется только к тем зонам, для которых фактически подтверждена аналогичная связь с притоком; автоматически переносить его на все радиаторы цоколя нельзя.

### БКН

```text
mode: IDLE / SUPPORT / ACCELERATED
target_water_temperature
current_water_temperature
pause_heating_requested
```

`SUPPORT` по умолчанию не означает паузу отопления.

### ПВУ

До cutover должен быть закрыт один из двух вариантов:

1. подтверждён нормальный температурный запрос ПВУ;
2. задан консервативный fail-safe fallback, явно отличимый от нормального расчёта.

Production не должен молча исключать активный водяной калорифер из источника тепла в холодную погоду.

### STARTUP / потеря HA / внешние interlock

После загрузки `wb-rules`, перезапуска контроллера или возврата питания система сначала входит в:

```text
STARTUP_VALIDATION
```

В этом состоянии:

- retained `heat_demand=true` не считается свежим;
- ждём новые timestamps/TTL от обязательных входов;
- frost-вход ПВУ обрабатывается немедленно и имеет право прервать startup;
- OT writer не начинает обычную работу до завершения проверки;
- владельцы физических каналов используют только заранее определённые безопасные стартовые состояния.

Если HA перестал обновлять комнатные термостаты, NO-приводы или воздушные заслонки:

```text
последнее значение != свежий запрос
```

Запрос соответствующей зоны становится `UNKNOWN`/`SUPPRESSED`, а не продолжает бесконечно греть дом по старому состоянию.

Входы внешних interlock резервируются в общем контракте:

```text
generator_active
fire_alarm
leak_alarm
```

На текущем этапе доказан только проектный смысл, а не фактические MQTT/event source. Поэтому:

- `generator_active=true` должен запрещать будущий электрический резерв и передавать ограничение ПВУ/load shedding;
- `fire_alarm` и `leak_alarm` нельзя реализовывать конкретными командами до подтверждения проектной матрицы, но Heating 2.0 обязан иметь место, куда эти запреты подключаются без появления второго writer.

## 8. Тёплый пол

### [Проверено]

PID сохраняется.

Новый `Heating_floor_manager.js` объединяет:

- владение K2;
- текущий доказавший работоспособность PID;
- управление 0–10 В клапаном;
- вычисление запроса источнику;
- локальную диагностику.

При потере датчика подачи PID прекращает нормальное регулирование и переходит в принятый safe-state. Software не должен пытаться компенсировать физически ненадёжную 1-Wire линию выдуманным значением.

Причина перехода должна быть явно видна:

```text
sensor_status = UNKNOWN
control_state = SENSOR_FAILSAFE
```

## 9. Диспетчер запросов

`Heating_demand_arbiter.js`:

- не пишет насосы;
- не пишет OT;
- валидирует freshness/TTL;
- исключает `UNKNOWN`;
- применяет приоритеты;
- публикует:
  - активные requests;
  - grants/suppressed;
  - требуемую общую подачу;
  - причину выбора;
  - режим системы.

Арбитраж температуры и право временно ограничить другие контуры — разные решения.

## 10. Диспетчер источника

`Heating_source_manager.js`:

- единственный writer OT11;
- читает агрегированный target и состояние safety;
- реализует anti-cycling/adaptive/batch стратегию;
- сама внутренняя стратегия может дорабатываться после cutover без изменения остальных модулей;
- anti-cycle не должен существовать вторым скрытым writer через другой скрипт.

Для первой production-версии параметры выбираются по уже накопленным экспериментальным данным. Они считаются стартовой настройкой ПНР, а не «навсегда правильными».

Электрокотёл архитектурно предусмотрен, но автоматический failover не включается до подтверждения реального нагрева.

## 11. Safety Supervisor

`Heating_safety_supervisor.js` заменяет разрозненные watchdog/monitor-скрипты.

Контролирует:

- `STARTUP_VALIDATION` после restart/reboot/power restore;
- freshness/heartbeat HA и зональных входов;
- массовый 1-Wire outage;
- freshness requests;
- потерю OT;
- невозможные/противоречивые requests;
- отсутствие передачи тепла ТП;
- отсутствие нагрева БКН только при достоверном датчике;
- возможного второго writer OT;
- длительность режимов;
- зависший K1/K2/K3/K4/K6 command;
- AHU frost/interlock contract;
- `generator_active` как запрет электрического источника/load-shed interlock;
- зарезервированные `fire_alarm` / `leak_alarm` с действиями только после подтверждения матрицы.

Safety не пишет чужой физический канал. Он публикует interlock. Owner обязан выполнить его.

## 12. Логирование

Все production-модули используют единый формат:

```text
[отопление][script][context]; ТИП=...; причина=...; параметр=...
```

Логируем:

- загрузку;
- изменение состояния;
- изменение важной настройки;
- физическую команду;
- результат только при реальной обратной связи;
- error/warning;
- alarm/watchdog.

Не логируем каждый 5-секундный расчёт.

Главный принцип:

```text
Grafana = количественная история
journal = почему алгоритм принял решение
```

## 15. Home Assistant

До cutover проверяется и убирается прямой write-доступ HA к каналам, которым назначен WB-owner:

- K5;
- K6;
- EXT1_K10 — когда будет введён owner источника;
- любые другие прямые physical command topics, конфликтующие с ownership 2.0.

HA должен задавать пользовательское намерение/режим/уставку помещения, а не обходить менеджер физического ресурса.

Дополнительно до cutover фиксируется **контракт свежести HA**:

- какие room thermostat entities образуют heat demand;
- какие NO-приводы относятся к каждой зоне;
- какие приточные заслонки относятся к конвекторам жилой зоны;
- какой сигнал подтверждает работу ПВУ;
- heartbeat/availability или эквивалентный TTL.

При потере HA последнее состояние этих входов не должно считаться бессрочно действующим.

- DHW SUPPORT параллельно отоплению;

- OT outage;

- fire/leak interlock contract — только после появления подтверждённых event source.

## 17. Один controlled cutover

Это один заход на объект, но не «скопировать всё и надеяться».

### До окна

- скачать off-controller архив текущего `/etc/wb-rules`;
- скачать `/etc/wb-rules-modules`;
- сохранить `wb-mqtt-db.conf`;
- экспортировать Grafana v6/Shadow;
- сохранить HA-конфиг затрагиваемых MQTT switches;
- никаких постоянных backup-файлов на WB после окончания.

### В окне

1. read-only preflight:
   - OT;
   - K1...K6;
   - 1-Wire;
   - Breezart;
   - HA freshness/availability и зоны K4;
   - приточные заслонки, связанные с конвекторами;
   - текущие temperatures.
2. остановить `wb-rules`.
3. вывести старые отопительные `.js` из active set.
4. установить весь новый production set.
5. обновить `wb-mqtt-db.conf`.
6. запустить `wb-rules`.
7. проверить:
   - нет syntax/runtime errors;
   - все ВУ появились;
   - один writer на каждый ресурс;
   - initial state = `STARTUP_VALIDATION` до получения свежих входов;
   - retained demand не принят как свежий;
   - initial states физических владельцев разумны.
8. перезапустить `wb-mqtt-db` и cloud-metrics при необходимости.
9. проверить новые Grafana dashboards.
10. убрать конфликтующие HA command topics.
11. 30–60 минут наблюдать live.

### Rollback

Если не проходят smoke criteria:

- остановить `wb-rules`;
- восстановить старый комплект из off-controller snapshot;
- восстановить старый `wb-mqtt-db.conf`;
- запустить;
- проверить K1...K6 и OT;
- новую систему не «чинить на горячую» в аварийном режиме.

После успешной сдачи временные staging/backup-файлы на контроллере удалить.

## 18. Критерии успешного cutover

1. Нет второго writer OT/K1...K6.
2. Нет runtime errors `wb-rules`.
3. Запрос каждого потребителя понятен в UI/Grafana.
4. Можно объяснить каждое изменение OT по `winner + source_state + reason`.
5. PID ТП удерживает подачу без деградации относительно baseline.
6. DHW SUPPORT не создаёт необоснованную паузу отопления.
7. ACCELERATED ограничен и возвращается в нормальный режим.
8. 1-Wire UNKNOWN виден и приводит к заранее определённому safe-state.
9. ПВУ не остаётся без источника тепла в опасном режиме.
10. Grafana получает новые каналы в течение первого цикла cloud upload.
11. Уведомления не сообщают технологическую аварию на основании недостоверного первичного датчика.
12. Старые дублирующие ВУ исчезли вместе со старыми scripts.
13. Пользователь не может выставить внутреннюю комбинацию параметров, делающую алгоритм математически противоречивым.
14. Жилая зона не повышает запрос источнику при отсутствии подтверждённого воздушного пути через конвектор.
15. После restart/reboot система проходит `STARTUP_VALIDATION` и не доверяет retained demand.
16. Потеря HA переводит зависимые зональные запросы в понятный `UNKNOWN/SUPPRESSED`, а не оставляет вечный запрос.
17. Будущий электрический резерв имеет внешний запрет `generator_active`; ДГУ не может случайно получить электрокотёл как аварийную нагрузку.

## 19. Что НЕ делать

- не сохранять старые control scripts параллельно «на всякий случай»;
- не оставлять shadow и production writer одновременно;
- не дублировать физические каналы виртуальными только ради Grafana;
- не переносить старые десятки ползунков в новые ВУ;
- не строить один огромный `HeatingManager.js`;
- не внедрять PID источника только потому, что PID хорошо работает на подмесе;
- не считать физическую команду доказательством выполнения;
- не маскировать 1-Wire отказ программным значением;
- не включать OT12 failover до подтверждения реального нагрева электрическим котлом.

## 20. Результат сверки с полным аудитом

[Проверено]

Формальная сверка v1 плана с `05_16_ISET_SYSTEM_ARCHITECTURE_AUDIT.md`, runtime-аудитом и `HEATING_MANAGER_2_0_DESIGN.md` выявила один потерянный **рабочий отопительный сценарий** и несколько недоописанных системных interlock:

1. **Потерянный сценарий:** приточный воздух через внутрипольные конвекторы жилой зоны. В v1 `Heating_living_manager.js` был описан как обычный водяной контур K4, что недостаточно. В v2 введён airflow-permit/freshness contract.
2. `STARTUP_VALIDATION` после restart/reboot/power restore был недостаточно явно перенесён в план.
3. Потеря HA и stale NO-приводы/заслонки должны быть отдельным сценарием.
4. ДГУ/load shedding должен стать внешним запретом будущего электрического котла.
5. Пожар/протечка остаются внешними interlock с пока неподтверждёнными event source; конкретные команды не выдумываются.

Эти дополнения **не меняют основную архитектуру** `consumer → request → arbiter → source owner`. Они закрывают межсистемные зависимости, которые были явно обнаружены полным аудитом.
