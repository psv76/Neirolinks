# SATURN_Log.md

## 1. Назначение

Документ задаёт правила логирования для диспетчеризации теплового пункта с контроллерами Saturn-PLC через Wiren Board.

Задача логирования — быстро ответить на вопросы:

```text
какая система сработала;
какой скрипт принял решение;
к какому контуру / зоне / контроллеру относится событие;
что произошло;
почему произошло;
какие значения были в момент события;
какая команда была отправлена в канал WB/MQTT, если команда была.
```

Логи пишутся в системный журнал `wb-rules.service`.

Формат должен быть пригоден для:

```text
поиска в WebUI Wiren Board;
разбора аварий на объекте;
будущих уведомлений в MAX;
будущей передачи данных в SCADA.
```

Логирование не является заменой MQTT-каналов.  
SCADA и виджеты должны получать данные из нормальных каналов WB/MQTT, а не из текста системного журнала.

---

## 2. Базовый формат строки

Использовать общий формат проекта:

```text
[система][скрипт][контекст]; ТИП=событие; параметр=значение; параметр=значение
```

Пример:

```text
[отопление][620_saturn_heat1_dhw2][нижние]; АВАРИЯ=Неисправен датчик подачи; канал=S1_Status_3; значение=1
```

Правила:

```text
первый блок  = инженерная система;
второй блок  = скрипт / источник логики;
третий блок  = контекст объекта;
после `;`    = тип события и параметры.
```

Теги в квадратных скобках писать строчными буквами:

```text
[отопление]
[гвс]
[сатурн]
[электро]
[протечки]
[нижние]
[верхние]
[итп]
```

Причина: в WebUI Wiren Board поиск по журналу может учитывать регистр. Строчные теги проще искать без дополнительных настроек.

---

## 3. Системы объекта

Для объекта использовать пять систем.

| Система | Назначение |
|---|---|
| `[отопление]` | технологические события отопления, схема №1 Saturn |
| `[гвс]` | технологические события горячего водоснабжения, схема №2 Saturn |
| `[сатурн]` | связь, Modbus, состояние контроллеров Saturn, сервисные события, перезагрузка Saturn |
| `[электро]` | мониторинг электроснабжения ИТП и питания оборудования |
| `[протечки]` | контроль протечек и команды по защите от протечек |

Не использовать `[теплопункт]` как систему.

Тепловой пункт — это место / узел объекта, а не инженерная система. Для него использовать контекст `[итп]`.

---

## 4. Контексты объекта

Использовать три базовых контекста.

| Контекст | Назначение |
|---|---|
| `[нижние]` | Saturn нижних этажей |
| `[верхние]` | Saturn верхних этажей |
| `[итп]` | общие события теплового пункта |

Примеры:

```text
[отопление][620_saturn_heat1_dhw2][нижние]
[гвс][620_saturn_heat1_dhw2][верхние]
[сатурн][620_saturn_heat1_dhw2][нижние]
[электро][100_power_monitor][итп]
[протечки][400_leak_control][итп]
```

Если событие относится к конкретному контроллеру Saturn, использовать `[нижние]` или `[верхние]`.

Если событие относится ко всему шкафу / помещению / ИТП, использовать `[итп]`.

---

## 5. Рекомендуемые имена скриптов

Имена скриптов можно уточнить при реализации, но логика разделения должна остаться такой.

| Скрипт | Назначение |
|---|---|
| `620_saturn_heat1_dhw2` | чтение Saturn RAW, создание виртуальных устройств «Отопление» и «ГВС», контроль статусов |
| `100_power_monitor` | мониторинг электроснабжения |
| `400_leak_control` | контроль протечек |

Если часть логики будет объединена в один файл, в логах всё равно должен быть понятный источник решения.

---

## 6. Типы событий и уровни журнала

Использовать стандартные типы проекта.

| Тип | Уровень | Когда использовать |
|---|---|---|
| `СКРИПТ` | `log.info()` | запуск скрипта, инициализация, проверка конфигурации |
| `СОСТОЯНИЕ` | `log.info()` | нормальное изменение состояния |
| `НАСТРОЙКА` | `log.info()` | изменение важной настройки через WB |
| `КОМАНДА` | `log.info()` | скрипт отправил команду в канал |
| `РЕЗУЛЬТАТ` | `log.info()` | получено подтверждение результата по обратной связи |
| `ОШИБКА` | `log.warning()` | проблема, но система ещё может работать безопасно |
| `АВАРИЯ` | `log.error()` | состояние требует внимания или нормальная работа невозможна |
| `WATCHDOG` | `log.error()` | принудительное действие таймера безопасности |

Не вводить отдельные типы `ВОССТАНОВЛЕНИЕ`, `ДАТЧИК`, `ОТКАЗ`.

Восстановление писать как `СОСТОЯНИЕ` или `РЕЗУЛЬТАТ`:

```text
[сатурн][620_saturn_heat1_dhw2][нижние]; РЕЗУЛЬТАТ=Связь с Saturn восстановлена; адрес=48; простой_сек=124
[отопление][620_saturn_heat1_dhw2][нижние]; СОСТОЯНИЕ=Неисправность датчика подачи снята; канал=S1_Status_3; значение=0
```

## 7. Команда и подтверждение

`КОМАНДА` означает только попытку записи в канал.

Не писать:

```text
Saturn перезагружен
насос включён
клапан открыт
```

если нет подтверждения.

Писать:

```text
КОМАНДА=Включить реле перезагрузки Saturn
КОМАНДА=Остановить схему ГВС
КОМАНДА=Изменить уставку ГВС
```

Физический или технологический итог писать отдельной строкой `РЕЗУЛЬТАТ`, если есть обратная связь:

```text
[сатурн][620_saturn_heat1_dhw2][нижние]; КОМАНДА=Включить реле перезагрузки Saturn; причина=нет связи с Saturn; канал=...; значение в канал=ON
[сатурн][620_saturn_heat1_dhw2][нижние]; РЕЗУЛЬТАТ=Связь с Saturn восстановлена после перезагрузки; адрес=48; простой_сек=96
```

Если подтверждения нет, результат не выдумывать.

## 8. События системы `[отопление]`

Система `[отопление]` относится к схеме №1 Saturn.

Логировать только изменения состояния, а не каждый опрос.

### Логировать

```text
схема отопления разрешена / остановлена;
ошибка датчика подачи появилась / снята;
ошибка датчика наружного воздуха появилась / снята;
ошибка датчика обратной теплосети появилась / снята;
ошибка датчика давления подпитки появилась / снята;
насос 1 изменил состояние;
насос 2 изменил состояние;
насос перешёл в аварию;
клапан изменил положение существенно;
подпитка включилась / выключилась;
авария подпитки появилась / снята;
сухой ход / контроль насоса появился / снят;
режим заполнения системы включён / выключен;
дистанционный стоп отопления включён / снят;
уставка / коррекция отопления изменена через WB, если запись будет разрешена.
```

### Примеры

```text
[отопление][620_saturn_heat1_dhw2][нижние]; СКРИПТ=Инициализация отопления Saturn; адрес=48; схема=1
```

```text
[отопление][620_saturn_heat1_dhw2][нижние]; СОСТОЯНИЕ=Схема отопления разрешена; канал=S1_Status_1; значение=1
```

```text
[отопление][620_saturn_heat1_dhw2][нижние]; АВАРИЯ=Неисправен датчик подачи; канал=S1_Status_3; значение=1
```

```text
[отопление][620_saturn_heat1_dhw2][нижние]; СОСТОЯНИЕ=Неисправность датчика подачи снята; канал=S1_Status_3; значение=0
```

```text
[отопление][620_saturn_heat1_dhw2][верхние]; СОСТОЯНИЕ=Насос 1 включен; канал=S1_Pump1; значение=2
```

```text
[отопление][620_saturn_heat1_dhw2][верхние]; АВАРИЯ=Насос 1 в аварии по перепаду; канал=S1_Pump1; значение=3
```

```text
[отопление][620_saturn_heat1_dhw2][нижние]; СОСТОЯНИЕ=Положение клапана отопления изменилось; было=32; стало=41; единицы=%
```

```text
[отопление][620_saturn_heat1_dhw2][нижние]; СОСТОЯНИЕ=Подпитка включена; канал=S1_Status_9; значение=1
```

```text
[отопление][620_saturn_heat1_dhw2][нижние]; АВАРИЯ=Авария подпитки по времени; канал=S1_Status_7; значение=1
```

## 9. События системы `[гвс]`

Система `[гвс]` относится к схеме №2 Saturn.

Логировать только изменения состояния, а не каждый опрос.

### Логировать

```text
схема ГВС разрешена / остановлена;
ошибка датчика ГВС появилась / снята;
ошибка датчика наружного воздуха появилась / снята, если используется;
ошибка датчика обратной теплосети появилась / снята, если используется;
насос 1 изменил состояние;
насос 2 изменил состояние;
насос перешёл в аварию;
клапан изменил положение существенно;
дистанционный стоп ГВС включён / снят;
уставка ГВС изменена через WB, если запись будет разрешена;
приоритет ГВС включился / выключился, если он реально используется в конфигурации.
```

### Примеры

```text
[гвс][620_saturn_heat1_dhw2][нижние]; СКРИПТ=Инициализация ГВС Saturn; адрес=48; схема=2
```

```text
[гвс][620_saturn_heat1_dhw2][нижние]; СОСТОЯНИЕ=Схема ГВС разрешена; канал=S2_Status_1; значение=1
```

```text
[гвс][620_saturn_heat1_dhw2][верхние]; АВАРИЯ=Неисправен датчик ГВС; канал=S2_Status_3; значение=1
```

```text
[гвс][620_saturn_heat1_dhw2][верхние]; СОСТОЯНИЕ=Неисправность датчика ГВС снята; канал=S2_Status_3; значение=0
```

```text
[гвс][620_saturn_heat1_dhw2][нижние]; СОСТОЯНИЕ=Насос ГВС 1 включен; канал=S2_Pump1; значение=2
```

```text
[гвс][620_saturn_heat1_dhw2][нижние]; АВАРИЯ=Насос ГВС 1 в аварии по внешнему сигналу; канал=S2_Pump1; значение=4
```

```text
[гвс][620_saturn_heat1_dhw2][верхние]; НАСТРОЙКА=Изменена уставка ГВС; было=55; стало=58; единицы=°C
```

## 10. События системы `[сатурн]`

Система `[сатурн]` используется для сервисных событий контроллеров Saturn.

Это не технологические события отопления или ГВС.

### Логировать

```text
связь с Saturn потеряна / восстановлена;
ошибка чтения Modbus;
ошибка записи Modbus;
неверный режим схемы S1_ID / S2_ID;
низкое напряжение встроенной батарейки часов Saturn;
команда на включение реле перезагрузки;
команда на выключение реле перезагрузки.
```

### Связь

```text
[сатурн][620_saturn_heat1_dhw2][нижние]; СКРИПТ=Инициализация связи с Saturn; адрес=48; порт=/dev/ttyRS485-2; скорость=9600 8N1
```

```text
[сатурн][620_saturn_heat1_dhw2][нижние]; ОШИБКА=Связь с Saturn потеряна; адрес=48; таймаут_сек=60
```

```text
[сатурн][620_saturn_heat1_dhw2][нижние]; РЕЗУЛЬТАТ=Связь с Saturn восстановлена; адрес=48; простой_сек=124
```

### Неверный режим схем

Если `S1_ID` не соответствует отоплению или `S2_ID` не соответствует ГВС, это авария диспетчеризации.

```text
[сатурн][620_saturn_heat1_dhw2][нижние]; АВАРИЯ=Неверный режим схемы Saturn; канал=S1_ID; ожидалось=отопление; получено=0
```

```text
[сатурн][620_saturn_heat1_dhw2][нижние]; АВАРИЯ=Неверный режим схемы Saturn; канал=S2_ID; ожидалось=гвс; получено=0
```

### Встроенная батарейка часов

Это сервисное событие Saturn, а не отопление и не ГВС.

```text
[сатурн][620_saturn_heat1_dhw2][нижние]; ОШИБКА=Низкое напряжение встроенной батарейки часов Saturn; канал=V_battery; значение=2.45; единицы=В
```

Восстановление после замены:

```text
[сатурн][620_saturn_heat1_dhw2][нижние]; РЕЗУЛЬТАТ=Напряжение встроенной батарейки часов Saturn в норме; канал=V_battery; значение=3.05; единицы=В
```

### Перезагрузка Saturn через релейный модуль WB

На объекте планируется релейный модуль WB, который будет включать нормально разомкнутое реле для перезагрузки контроллера Saturn.

Алгоритм перезагрузки в этом документе не описывается.

В логировании нужно предусмотреть события:

```text
команда на включение реле перезагрузки;
команда на выключение реле перезагрузки.
```

Примеры:
```text
[сатурн][620_saturn_heat1_dhw2][нижние]; КОМАНДА=Включить реле перезагрузки Saturn; причина=нет связи с Saturn; канал=...; значение в канал=ON
```

```text
[сатурн][620_saturn_heat1_dhw2][нижние]; КОМАНДА=Выключить реле перезагрузки Saturn; канал=...; значение в канал=OFF
```Канал реле перезагрузки не указывать до фактического подключения и подтверждения канала.

## 11. События системы `[электро]`

Система `[электро]` используется для мониторинга электроснабжения ИТП.

### Логировать

```text
пропало питание 220 В;
питание 220 В восстановлено;
пропало питание конкретной группы, если есть отдельный контроль;
низкое напряжение / авария питания, если есть измерение;
питание контроллеров Saturn отсутствует, если это подтверждено отдельным входом контроля.
```

### Примеры

```text
[электро][100_power_monitor][итп]; АВАРИЯ=Пропало питание 220 В; канал=...; значение=0
```

```text
[электро][100_power_monitor][итп]; РЕЗУЛЬТАТ=Питание 220 В восстановлено; канал=...; значение=1
```

```text
[электро][100_power_monitor][итп]; ОШИБКА=Нет питания Saturn нижних этажей; канал=...; значение=0
```

Если событие является командой на перезагрузку Saturn через реле WB, оно относится к `[сатурн]`, а не к `[электро]`.

## 12. События системы `[протечки]`

Система `[протечки]` используется для контроля протечек и защитных команд.

### Логировать

```text
протечка обнаружена;
протечка снята;
команда закрыть воду;
команда открыть воду, если такая команда будет разрешена;
неисправность датчика протечки, если есть диагностика;
ручной режим / блокировка защиты, если такая функция будет реализована.
```

### Примеры

```text
[протечки][400_leak_control][итп]; АВАРИЯ=Обнаружена протечка; датчик=...
```

```text
[протечки][400_leak_control][итп]; КОМАНДА=Закрыть ввод воды; причина=обнаружена протечка; канал=...; значение в канал=ON
```

```text
[протечки][400_leak_control][итп]; РЕЗУЛЬТАТ=Протечка снята; датчик=...
```

## 13. Что не логировать

Не логировать:

```text
каждое значение температуры;
каждый успешный опрос Modbus;
каждый процент изменения клапана;
сырые битовые маски как отдельные события;
каждое чтение DI/DO;
каждую запись виртуального канала;
таблицы графиков, календарей и расписаний при обычном чтении;
одинаковые аварии повторно без изменения состояния.
```

Сырые значения должны быть доступны в каналах WB/MQTT.  
Журнал должен фиксировать события и решения, а не превращаться в архив телеметрии.

---

## 14. Порог для клапанов

Положение клапана может меняться часто. Логировать только существенные изменения.

Начальное правило:

```text
логировать изменение клапана, если изменение >= 5 %
или если клапан перешёл через важное состояние:
0 %;
100 %;
открытие после 0 %;
закрытие до 0 %.
```

Пример:

```text
[отопление][620_saturn_heat1_dhw2][нижние]; СОСТОЯНИЕ=Положение клапана отопления изменилось; было=32; стало=41; порог=5; единицы=%
```

Если на объекте журнал начнёт шуметь, порог увеличить.

---

## 15. Правила защиты от спама

Для каждого события хранить предыдущее состояние.

Писать событие только при изменении:

```text
0 → 1;
1 → 0;
старое состояние насоса → новое состояние насоса;
норма → авария;
авария → норма;
связь есть → связи нет;
связи нет → связь есть.
```

Не писать одну и ту же аварию циклически.

Для аварий связи допускается повторное сообщение только по отдельному таймеру эскалации, если такой механизм будет нужен для уведомлений.

## 16. Параметры строки

Рекомендуемые параметры:

| Параметр | Назначение |
|---|---|
| `причина` | почему принято решение |
| `канал` | MQTT control id или имя регистра Saturn |
| `значение` | текущее значение |
| `было` | старое значение |
| `стало` | новое значение |
| `единицы` | единицы измерения |
| `адрес` | Modbus-адрес Saturn |
| `порт` | порт RS-485 |
| `скорость` | параметры связи |
| `таймаут_сек` | время без связи |
| `простой_сек` | длительность простоя |
| `попытка` | номер попытки |
| `порог` | порог срабатывания |
| `значение в канал` | значение, отправленное командой |

Не добавлять в строку все данные подряд.  
Писать только параметры, которые помогают расследовать конкретное событие.

---

## 17. Уведомления MAX

Интеграция с MAX не реализуется в первом этапе.

Но структура событий должна быть пригодна для будущих уведомлений.

Правильная модель:

```text
одно событие в логике
→ запись в системный журнал
→ при необходимости отправка уведомления в MAX
```

Не парсить системный журнал как источник уведомлений.

В коде позже можно сделать общий обработчик событий:

```text
emitEvent(...)
writeLog(...)
notifyCritical(...)
```

Для будущих уведомлений потенциально критичны:

```text
АВАРИЯ по отоплению;
АВАРИЯ по ГВС;
потеря связи с Saturn;
пропало питание;
обнаружена протечка;
ошибка датчика подачи / ГВС;
авария насоса;
авария подпитки;
низкое напряжение встроенной батарейки часов Saturn.
```

Что именно отправлять в MAX, согласовывается отдельно.

## 18. SCADA

Будущая SCADA не меняет правила логирования.

SCADA должна получать данные из MQTT-каналов:

```text
температуры;
уставки;
статусы схем;
аварийные признаки;
состояния насосов;
положение клапанов;
состояние связи;
состояние питания;
состояние протечек.
```

Текст системного журнала не должен быть основным источником данных для SCADA.

Лог нужен для расследования:

```text
когда началась авария;
какой скрипт её увидел;
какое решение было принято;
какая команда была отправлена;
когда состояние восстановилось.
```

## 19. event_* каналы

В первом варианте интеграции Saturn event_* каналы не обязательны.

Не добавлять event_* автоматически.

Допустимо вернуться к ним позже, если для расследования понадобится фиксировать снимок состояния в момент события:

```text
event_counter;
event_time_s;
event_type;
event_text;
event_saturn_address;
event_context;
```

До отдельного решения достаточно системного журнала `wb-rules` и истории MQTT по важным каналам.

## 20. Минимальный набор логов при запуске

При старте `620_saturn_heat1_dhw2` достаточно одного сообщения на каждый Saturn:

```text
[сатурн][620_saturn_heat1_dhw2][нижние]; СКРИПТ=Запущен мониторинг Saturn; адрес=48; схема1=отопление; схема2=гвс
```

```text
[сатурн][620_saturn_heat1_dhw2][верхние]; СКРИПТ=Запущен мониторинг Saturn; адрес=49; схема1=отопление; схема2=гвс
```

Если адрес верхнего Saturn неизвестен, не выдумывать его.  
Адрес должен быть взят из конфигурации.

## 21. Проверка логирования

После внедрения проверить:

```text
в системном журнале видны строки wb-rules;
поиск `[отопление]` показывает только отопление;
поиск `[гвс]` показывает только ГВС;
поиск `[сатурн]` показывает связь, ошибки Modbus и сервисные события Saturn;
поиск `[нижние]` показывает все события нижнего Saturn;
поиск `[верхние]` показывает все события верхнего Saturn;
поиск `[итп]` показывает общие события теплового пункта;
аварии отображаются уровнем error;
ошибки отображаются уровнем warning;
нормальные события отображаются уровнем info.
```

## 22. Короткое правило для разработчика

Если событие отвечает на вопрос “что произошло с инженерной системой” — использовать систему:

```text
[отопление]
[гвс]
[протечки]
[электро]
```

Если событие отвечает на вопрос “что произошло с контроллером Saturn как устройством” — использовать:

```text
[сатурн]
```

Если событие является командой на релейную перезагрузку Saturn, это:

```text
[сатурн]
```

а не `[электро]`.

Если событие относится к нижнему или верхнему контроллеру — контекст:

```text
[нижние]
[верхние]
```

Если событие относится ко всему ИТП — контекст:

```text
[итп]
```
