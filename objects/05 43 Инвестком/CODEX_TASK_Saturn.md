## Типовое решение

На объекте используются два контроллера Saturn-PLC.

Каждый контроллер Saturn-PLC работает в режиме «Отопление + ГВС»:

```text
схема №1 Saturn = Отопление
схема №2 Saturn = ГВС
```

Физическое разделение:

```text
первый Saturn = нижние этажи
второй Saturn = верхние этажи
```

В WB один физический Saturn должен отображаться как два смысловых устройства:

```text
Отопление
ГВС
```

При подключении двух Saturn в WB должны появиться четыре смысловых устройства:

```text
Отопление нижних этажей
ГВС нижних этажей
Отопление верхних этажей
ГВС верхних этажей
```

## Архитектура решения

Использовать архитектуру:

```text
Saturn-PLC по Modbus RTU
↓
RAW-шаблон wb-mqtt-serial
↓
одно техническое RAW-устройство Saturn в WB
↓
wb-rules скрипт
↓
два виртуальных устройства WB:
- Отопление
- ГВС
```

Для двух Saturn используется тот же RAW-шаблон, но два экземпляра RAW-устройства с разными Modbus-адресами и разными MQTT device id.

Скрипт `wb-rules` должен поддерживать конфигурацию нескольких Saturn-контроллеров на одном WB.

Пример структуры конфигурации внутри скрипта:

```javascript
var SATURN_CONTROLLERS = [
    {
        rawDevice: "saturn_lower_raw",
        titleSuffix: "нижних этажей",
        heatingDevice: "saturn_lower_heating",
        dhwDevice: "saturn_lower_dhw"
    },
    {
        rawDevice: "saturn_upper_raw",
        titleSuffix: "верхних этажей",
        heatingDevice: "saturn_upper_heating",
        dhwDevice: "saturn_upper_dhw"
    }
];
```

Имена можно уточнить по стилю WB, но логика должна остаться такой:

```text
один rawDevice
→ одно виртуальное устройство отопления
→ одно виртуальное устройство ГВС
```

## Типы данных и endian

Для `_TFloat` использовать проверенный на стенде вариант:

```text
format: float32 / IEEE754
register_count: 2
word_order: little-endian
byte_order: little-endian
```

Для `_TWord`, `_TSWord`, `_TDWord` учитывать, что Saturn хранит типы в формате Little Endian.

Практический контроль endian:

```text
T1 должен показывать реальную температуру PT1000.
ADC_error при подключенном только T1 должен соответствовать ошибкам остальных неподключенных аналоговых каналов.
Значения вроде 1280 вместо 5 или 12288 вместо 48 означают неправильный порядок байтов для integer-регистров.
```

## Виртуальное устройство «Отопление»

Виртуальное устройство «Отопление» строится по данным схемы №1 Saturn.

В устройстве должны быть понятные поля:

```text
разрешено управление;
ID схемы;
статус схемы текстом;
температура подачи отопления;
уставка подачи;
коррекция уставки;
насос 1;
насос 2;
положение клапана, %;
насос подпитки 1;
насос подпитки 2;
количество включений подпитки за сутки;
время работы подпитки за сутки;
ошибка датчика подачи;
ошибка датчика наружного воздуха;
ошибка датчика обратной теплосети;
ошибка датчика давления подпитки;
авария подпитки;
подпитка включена;
сухой ход / контроль насоса;
разрешена подпитка;
режим заполнения системы;
дистанционный стоп;
наработка насосов, если регистры читаются стабильно.
```

Статусы насосов выводить текстом по карте Saturn:

```text
0 = Запрещена работа
1 = Остановлен
2 = Включен
3 = Авария насоса по перепаду / времени подпитки
4 = Авария насоса по внешнему сигналу
```

Если для конкретного регистра доступны не все значения, использовать только значения из документации.

## Управление из WB

Первый рабочий вариант не должен давать полное управление всеми настройками Saturn.

Разрешённый набор записи:

```text
S1_T_correct
S2_T_correct
S2_T_preset
S1_RemoteStop
S2_RemoteStop
```

Условия:

```text
S1_T_correct — коррекция уставки отопления.
S2_T_correct — коррекция уставки ГВС.
S2_T_preset — уставка ГВС.
S1_RemoteStop / S2_RemoteStop — отдельные команды остановки схем, должны быть явно подписаны как команды.
```

Не добавлять запись:

```text
температурные графики;
таблицы ограничения;
расписания;
календарь;
праздники;
ручное управление DO/AO;
ManualControl;
ManualControlTime;
параметры клапанов;
параметры ротации;
наработки;
сервисные параметры.
```

Если в документации указано, что параметр должен записываться одной командой сразу группой регистров, не делать для него одиночный control в WB.

## Коррекция показаний датчиков температуры

Проверить по `Saturn PLC_re3.pdf`, как выполняется коррекция датчиков T1–T5 в самом Saturn.

В документации Saturn есть меню настройки датчиков T1–T5, где задаются:

```text
тип датчика;
коррекция температуры, °С;
MIN допустимое значение;
MAX допустимое значение.
```

Нужно:

```text
1. Описать в README, что технологическая коррекция датчиков должна выполняться в Saturn.
2. Не делать отдельную коррекцию показаний датчиков в WB, если она влияет только на отображение и не влияет на алгоритм Saturn.
3. Не добавлять T1_correction, T2_correction и подобные виртуальные поправки в WB.
```

Причина: если Saturn сам регулирует отопление и ГВС, коррекция только в WB исправит экран диспетчера, но не исправит алгоритм Saturn.

## wb-rules скрипт

Файл:

```text
Templates/Saturn/620_saturn_heat1_dhw2.js
```

Требования:

```text
совместимость с wb-rules;
ECMAScript 5;
var вместо let/const;
обычные function;
без стрелочных функций;
без sleep();
без скрытых зависимостей от других скриптов;
полный файл, готовый к копированию в /etc/wb-rules.
```

Скрипт должен:

```text
читать каналы RAW-устройства Saturn;
создавать виртуальное устройство отопления;
создавать виртуальное устройство ГВС;
преобразовывать битовые статусы в отдельные понятные признаки;
преобразовывать числовые состояния насосов в текст;
отображать основные температуры, уставки, насосы, клапан, аварии;
вести логирование по стандарту проекта;
поддерживать несколько Saturn-контроллеров через конфигурационный массив.
```

## MAX-уведомления

Интеграцию с MAX не делать.

Код событий должен быть организован так, чтобы позже можно было добавить отправку уведомлений из того же места, где пишется событие в журнал.

Не использовать парсинг системного журнала как источник уведомлений.

## SCADA

SCADA не реализовывать.

Текущее решение должно давать стабильные MQTT-каналы WB:

```text
понятные device id;
понятные control id;
единицы измерения;
отдельные аварийные признаки;
отдельные состояния насосов, клапанов и схем.
```

SCADA в будущем должна брать данные из этих каналов, а не из текста логов и не из виджетов WB.

## Ограничения

Не выдумывать регистры.

Не переносить каналы с других объектов.

Не делать запись опасных параметров без явного основания.
